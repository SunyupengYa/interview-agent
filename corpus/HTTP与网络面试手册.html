① TCP 连接管理 三次握手 · 四次挥手 · TIME_WAIT · 可靠传输

三次握手的详细过程？为什么必须是三次，两次不行吗？必考已掌握

报文级流程

客户端                          服务端
  |---- SYN, seq=x -------------->|   第一次：客户端进入 SYN_SENT
  |<--- SYN+ACK, seq=y, ack=x+1 --|   第二次：服务端进入 SYN_RCVD
  |---- ACK, seq=x+1, ack=y+1 --->|   第三次：双方进入 ESTABLISHED
  |---- (可携带数据) -------------->|
  • seq（序列号）：本报文所发送数据的第一个字节的编号；ack：期望对方下一个字节的编号（= 收到的最后序号 + 1）。
  • 前两次握手不能携带数据，第三次可以（第三次 ACK 已让服务端确认连接建立）。

为什么是三次（三个独立原因，面试一个都别说漏）

  1. 防历史连接（RFC 793 给出的根本原因）：客户端发的一个旧 SYN（网络中滞留的重复包）比新 SYN 先到服务端。若「两次握手」，服务端回复 ACK 就直接建立连接、分配缓存——但这是个废连接，浪费资源。三次握手时，客户端收到 ACK 后发现确认号对不上当前连接，会回 RST 拒绝，服务端释放资源。
  2. 同步初始序列号（ISN）：TCP 可靠传输依赖序列号。ISN 同步需要「我发你确认、你发我确认」，本质是两个方向的各一次确认，共 4 步，中间的 SYN 和 ACK 合并成 SYN+ACK，所以最少 3 步。
  3. 确认双方收发能力：两次只能证明「客户端→服务端」通 +「服务端→客户端」发得出去，无法证明「服务端→客户端」收得到（第三次 ACK 证明之）。

追问：四次行不行？

行，但没必要。SYN 和 ACK 可以合并（半双工协议里才需要拆开），多一次只增加延迟不增加可靠性——三次是「达到目的的最小次数」。

追问：ISN 为什么是随机的？

  • 固定 ISN 的话，上一个相同四元组连接的旧报文会落到新连接的序列号窗口里，被当成新连接的数据（安全+数据错乱）。
  • 随机 ISN + 递增规律，也让攻击者难以伪造合法序列号（RST 攻击的前提是猜到 seq）。
追问：第三次握手丢了会怎样？—— 客户端发完 ACK 就认为连接建立（可直接发数据）；服务端收不到，停在 SYN_RCVD，会超时重传 SYN+ACK（次数由 tcp_synack_retries 控制，默认 5 次，间隔指数退避）。若客户端在此期间发数据，数据包自带 ACK，服务端收到后照样建立连接。
易错：别说「三次握手是为了确认服务端能收到」就完了——面试官会立刻问「那历史 SYN 的问题呢」。根本原因是 RFC 793 明说的防历史连接初始化，序列号同步是第二原因，能力确认只是顺带结果。
四次挥手的过程？为什么是四次？TIME_WAIT 为什么要等 2MSL？必考已掌握

报文级流程（假设客户端主动关闭）

客户端                                服务端
ESTABLISHED                          ESTABLISHED
  |---- FIN, seq=u ------------------->|  客户端进入 FIN_WAIT_1
  |<--- ACK, ack=u+1 ------------------|  服务端进入 CLOSE_WAIT
  |     (此时服务端还可继续发数据)        |  客户端进入 FIN_WAIT_2
  |<--- FIN, seq=w, ack=u+1 -----------|  服务端进入 LAST_ACK
  |---- ACK, ack=w+1 ----------------->|  客户端进入 TIME_WAIT，等 2MSL
  |                                    |  服务端收到 ACK 后 CLOSED
(2MSL 后) 客户端 CLOSED

为什么挥手要四次（握手三次就行）

  • TCP 是全双工：两个方向的数据流要分别关闭。
  • 收到 FIN 只说明「对方不再发数据」，自己可能还有数据没发完，所以 ACK 和自己的 FIN 不能像握手那样合并——中间隔着「发完剩余数据」的动作。
  • 只有当被动方没有数据要发时，ACK 和 FIN 才可能合并（延迟确认机制下有时抓包看到 3 次）。

TIME_WAIT 为什么等 2MSL（两个原因）

  • MSL（Maximum Segment Lifetime）：报文在网络中的最大存活时间，Linux 默认 30 秒，2MSL = 60 秒。
  • 原因一：保证最后的 ACK 可达。主动方发的最后一个 ACK 若丢失，被动方会重传 FIN。主动方只有在 TIME_WAIT 期间才能响应这个重传。等 2MSL = 「一来一回的最大时间」：ACK 最多 1MSL 到对方，对方重传 FIN 再 1MSL 回来。
  • 原因二：让旧连接的报文在网络中自然消亡。等待期间，这条连接的所有报文都超过 MSL 死光了，不会污染之后相同四元组的新连接。
追问：TIME_WAIT 过多怎么办？—— ① 根因是高频短连接主动断开，最优解是改用长连接/连接池复用（HTTP keep-alive、数据库连接池、Feign 底层连接池）；② 内核参数缓解：tcp_tw_reuse=1（允许复用 TIME_WAIT 端口，仅客户端方向有效且依赖时间戳）、扩大 tcp_max_tw_buckets；③ 让服务端主动关（把 TIME_WAIT 挪到有更强连接管理能力的一方），但本质没消除。
追问：大量 CLOSE_WAIT 呢？—— CLOSE_WAIT 是被动关闭方收到 FIN 后的状态，堆积意味着应用程序收到连接关闭通知后一直不调 close()——典型是代码 bug：异常分支没关闭连接、连接池满导致连接泄漏、下游服务重启后本服务未处理。这不是调内核参数能解决的，必须查代码。「TIME_WAIT 多是正常现象，CLOSE_WAIT 多一定是 bug」这句话是面试分水岭。
易错：① 主动关闭的是谁，谁进 TIME_WAIT（不是固定客户端）；② FIN_WAIT_1 和 FIN_WAIT_2 的区别：1 是等 ACK，2 是「自己 FIN 已被确认、还在等对方 FIN」；③ TIME_WAIT 是主动关闭方的状态，LAST_ACK 是被动关闭方的最终等待状态，别混。
TCP 和 UDP 的区别？TCP 如何保证可靠传输？必考已掌握

TCP vs UDP

维度TCPUDP
连接面向连接（三次握手）无连接（发就走）
可靠性确认+重传+有序尽最大努力交付，可能丢/乱序
数据形式字节流（无消息边界 → 粘包）报文（一个包一个边界）
速度/开销慢、头部 20+ 字节、有状态快、头部 8 字节、无状态
拥塞控制有（慢启动/拥塞避免/快重传/快恢复）无（可打满带宽）
典型场景HTTP、数据库连接、文件传输DNS、视频/语音直播、游戏、QUIC 底座

TCP 可靠传输的四大机制

  1. 序列号 + 确认应答（ACK）：每个字节有编号，接收方 ACK 确认「下一个期望的字节」，发送方据此知道哪些已送达；乱序可重排，重复可去重。
  2. 超时重传 + 快速重传：发出后启动定时器，超时未确认则重传（RTO 根据 RTT 动态计算）；收到 3 个重复 ACK 立即重传丢失报文（不等超时，SACK 还能精确告知收到了哪些段）。
  3. 滑动窗口（流量控制）：接收方通过 rwnd 告知自己剩余缓冲区大小，发送方未确认的数据不能超过窗口——防止发送过快把接收方打爆。
  4. 拥塞控制：防止把网络打爆。四个算法：慢启动（指数增长）→ 拥塞避免（到达阈值后线性增长）→ 快重传（3 个重复 ACK 立即重传）→ 快恢复（而非重新慢启动，阈值减半后线性增长）。
追问：UDP 场景怎么保证可靠性？—— 在应用层自己做：QUIC（HTTP/3 底座）就是范例——在 UDP 上实现了序号、确认、重传、拥塞控制，且避免了 TCP 的队头阻塞和僵死的内核实现，连接迁移还摆脱了四元组绑定（WiFi 切 4G 不断连）。
易错：「TCP 可靠」≠「应用收到的数据都正确处理」。TCP 只保证传输层送达且有序，应用层还要处理重复幂等、报文完整性（校验和只能查传输错误，防不了业务错误）。
什么是粘包/拆包？怎么解决？高频已掌握

根因：TCP 是字节流，没有消息边界

  • 发送方 Nagle 算法把多个小包合并发送；接收方一次 read 可能读到多条消息（粘包）或半条消息（拆包）。
  • 严格说这是「应用层消息边界问题」，不是 TCP 的 bug——TCP 的定位就是字节流，边界是应用层的事。UDP 天然按报文收发，无此问题。

三种解决方案（本质都是「约定边界」）

  1. 固定长度：每条消息定长，不足补位。简单但浪费带宽，用得少。
  2. 分隔符：如换行符 \n（Redis 协议、文本协议常用）。缺点：内容里出现分隔符需转义。
  3. 长度前缀（最通用）：消息头带 body 长度（如 4 字节 int），先读长度再按长度读 body。HTTP 的 Content-Length、Dubbo/RocketMQ 协议都是这个思路。

Netty 内置解码器（Java 面试必提）

pipeline.addLast(new FixedLengthFrameDecoder(1024));      // 固定长度
pipeline.addLast(new DelimiterBasedFrameDecoder(8192, Unpooled.wrappedBuffer("\n".getBytes())));
pipeline.addLast(new LengthFieldBasedFrameDecoder(
        1024*1024, 0, 4, 0, 4));   // 长度前缀：最大长度、长度字段偏移、长度字段大小、调整、剥离字节数
易错：两个独立概念别混——「粘包」是应用层消息边界问题；「Nagle 算法 + 延迟确认」是发送策略（小包合并），TCP_NODELAY 关闭 Nagle 只能减少粘包概率，不能根治，根治靠应用层协议设计。
半连接队列和 SYN Flood 攻击？如何防御？加分已掌握

两个队列

  • 半连接队列（SYN 队列）：收到 SYN、回复 SYN+ACK 后，连接处于 SYN_RCVD，放在这里等第三次 ACK。大小由 tcp_max_syn_backlog 控制。
  • 全连接队列（Accept 队列）：收到第三次 ACK、连接进入 ESTABLISHED，等待应用层 accept() 取走。大小为 min(backlog, somaxconn)。Accept 队列满了，新连接会被拒绝或丢弃（tcp_abort_on_overflow）。

SYN Flood 攻击

攻击者伪造源 IP 发海量 SYN、不回第三次 ACK，半连接队列被占满，正常用户无法建立连接。伪造 IP 导致服务端的 SYN+ACK 重传全部石沉大海，每条占位要持续几十秒。

防御：SYN Cookie（Linux 默认开启 tcp_syncookies=1）

  • 队列满时不分配资源，把连接信息编码进 SYN+ACK 的初始序列号里返回（如源 IP/端口/时间戳的 hash）。
  • 收到第三次 ACK 时从确认号里反解校验，合法才建立连接——不占队列就能完成握手，攻击者的伪造包无法正确回应。
  • 代价：丢弃了部分 TCP 选项（如大窗口、SACK），所以是兜底手段而非常态。
延伸：其他配套手段——调大 tcp_max_syn_backlog + somaxconn、减小 tcp_synack_retries（缩短占位时间）、防火墙/云清洗、应用前面挂 LB。

HTTP 报文结构？GET 和 POST 的区别？高频已掌握

报文结构（请求与响应同构）

POST /api/orders HTTP/1.1          # 请求行：方法 + 路径 + 版本
Host: api.example.com              # --- 以下为请求头（Header）
Content-Type: application/json
Authorization: Bearer eyJhbG...
Content-Length: 42
                                   # 空行（CRLF），头与体分隔
{"userId":1,"amount":99}           # 消息体（Body）

响应把请求行换成状态行（HTTP/1.1 200 OK），其余同构。Header 是 key: value 文本，Body 二进制/文本皆可。

GET vs POST：本质区别 + 常见误解

维度GETPOST
语义（RFC）安全且幂等：只获取，不改变服务端状态不安全不幂等：提交数据/触发处理
参数位置URL query string请求体
长度限制受 URL 长度限制（浏览器约 2K~8K，HTTP 协议本身不限）体量受服务端配置限制（如 Nginx client_max_body_size）
缓存可被浏览器/代理缓存、收藏、历史记录默认不缓存
编码application/x-www-form-urlencoded任意（JSON、multipart 文件上传…）
误解澄清（加分点）：①「GET 参数有长度限制」——HTTP 协议不限制，是浏览器/服务器的实现限制；②「POST 比 GET 安全」——只是参数不在 URL 里（不进日志/历史记录），抓包一样是明文，安全要靠 HTTPS；③「GET 产生一个 TCP 包、POST 两个」——这是某些浏览器（Firefox）的发送时序差异，不是协议规定，跨浏览器不成立。
易错：GET 能带 body（协议允许但语义上无意义、多数实现忽略）；DELETE/PUT 也应设计为幂等。「幂等」= 执行一次和执行多次效果一致，是接口设计和重试策略的基石。

易错：301 永久重定向会被浏览器强缓存，跳错了很难挽回（用户端清缓存前一直跳），所以不确定要不要永久跳转时先用 302 观察，再升 301。
HTTP 1.0 / 1.1 / 2 / 3 的演进？各解决了什么问题？必考已掌握
版本关键特性解决了什么 / 遗留什么
1.0每请求一个 TCP 连接连接开销巨大
1.1keep-alive 长连接、管道化（pipeline）、Host 头、Chunked 传输、更多缓存控制复用连接省握手；但管道化响应必须按序返回 → 应用层队头阻塞，实践中浏览器弃用管道化，改开多条并发连接（每域名 6~8 条）

3底座换 QUIC（基于 UDP）：流之间独立重传、0-RTT/1-RTT 建连、连接迁移（Connection ID 不绑四元组）、内置 TLS1.3彻底解决队头阻塞；UDP 被部分网络设备限速/拦截是落地阻力

面试主线一句话

「HTTP/1.1 的队头阻塞在应用层（响应按序），HTTP/2 用多路复用解决它，但把阻塞下沉到了 TCP 传输层（丢包全体等待），HTTP/3 换 QUIC 从根上解决。」——这条演进逻辑讲清了，比背特性列表高一档。

HTTP/2 多路复用 vs HTTP/1.1 keep-alive（易被追问）

  • keep-alive：一条连接上串行地「请求→响应→请求」，上一个响应没回来不能发下一个。
  • 多路复用：一条连接上多个流（Stream）并行，帧交织传输，二进制分帧让接收方能拆开重组。
易错：HTTP/2 只强制 HTTPS 的说法不准确——规范未强制，但主流浏览器只支持 TLS 上的 h2，实践中等于强制。HTTP/3 的 QUIC 把 TLS1.3 内置进协议，不再单独走 TLS 握手。

方案状态存哪工作方式优缺点
Cookie客户端浏览器服务端 Set-Cookie 下发，浏览器自动回带；可设 HttpOnly（防 XSS 读）、Secure（仅 HTTPS）、SameSite（防 CSRF）容量 4K、明文可被改，只适合存无敏感的标识

  2. Session 粘滞：Nginx ip_hash 把同一用户固定到同一节点。破坏负载均衡，节点下线会话全丢。

易错：「JWT 防 XSS」是错的——放 localStorage 的 JWT 能被 XSS 脚本读走；放 HttpOnly Cookie 防 XSS 但要单独防 CSRF（SameSite + CSRF Token）。两害相权：敏感系统用 HttpOnly Cookie，并配 CSRF 防护。
强缓存和协商缓存？304 是怎么来的？高频已掌握

两级缓存决策流程

浏览器请求资源
  ├─ 本地有缓存副本，且强缓存未过期？
  │     ├─ 是 → 直接用副本，不发请求（200 from disk/memory cache）
  │     └─ 否 → 发请求，带上缓存标识（If-None-Match / If-Modified-Since）
  │              服务端比对：
  │              ├─ 没变 → 304 Not Modified（无 body），用本地副本
  │              └─ 变了 → 200 + 新资源 + 新 ETag

强缓存（不发请求）

  • Cache-Control: max-age=31536000（秒，HTTP/1.1，优先）｜Expires: 具体时间（HTTP/1.0，受本地时钟影响，被淘汰）。
  • 常用组合：Cache-Control: no-cache（可缓存但每次协商验证，注意不是不缓存）；no-store 才是真不缓存；private/public 控制代理能否缓存。

协商缓存（问服务器有没有变）

对比项Last-Modified / If-Modified-SinceETag / If-None-Match（优先）
判断依据文件最后修改时间（秒级）内容指纹（hash），内容变了才变
缺陷1 秒内多次修改感知不到；文件内容回滚时间反而变小会误判需服务端计算 hash，有开销；分布式下多节点需保证生成一致
工程实践（前端配合）：HTML 用 no-cache（每次协商，保证引用最新），JS/CSS/图片带内容 hash 文件名（app.a3f9c2.js）+ 一年强缓存——内容变则 URL 变，天然解决更新。这是「指纹文件 + 强缓存」的标准方案。
易错：304 省的是传输流量，不省请求数（往返 RTT 还在）；强缓存两者都省。所以静态资源优化核心是「能用强缓存就别协商」。

HTTPS 的握手流程？为什么既用非对称又用对称加密？必考已掌握

TLS 1.2 握手（2-RTT）

客户端                                服务端
  |--① ClientHello ------------------>|  支持的TLS版本、加密套件、客户端随机数
  |<-② ServerHello + 证书 + ServerHelloDone |  选定套件、服务端随机数、证书(含公钥)
  |  ③ 客户端验证证书
  |  ④ 客户端生成预主密钥(pre-master)，
  |     用服务端公钥加密后发送          |
  |---- ClientKeyExchange ------------>|
  |---- ChangeCipherSpec + Finished -->|  双方用 随机数1+随机数2+pre-master
  |<--- ChangeCipherSpec + Finished --|   派生出对称会话密钥，之后对称加密通信

为什么混合加密（核心考点）

  • 非对称（RSA/ECDHE）安全但慢（比对称慢 2~3 个数量级），只用来交换密钥这一小步。
  • 对称（AES）快，用来加密后续全部应用数据（量大）。
  • 会话密钥 = 两个随机数 + pre-master 经 PRF 派生，每次连接都不同（前向安全的基础，配合 ECDHE 更彻底：密钥交换用临时密钥对，私钥泄露也解不开历史流量）。

追问：ECDHE 和 RSA 密钥交换的区别？

维度RSA 交换ECDHE 交换
方式客户端用服务器公钥加密 pre-master双方交换临时椭圆曲线公钥，各自算出相同密钥
前向安全无：服务端私钥泄露，历史抓包可被解密有：临时密钥用完即弃，历史流量无法回溯解密
现状已弃用主流（TLS 1.3 只留 ECDHE）

TLS 1.3 的改进（加分）

  • 1-RTT 完成握手（ClientHello 就带上密钥交换材料）；会话恢复可 0-RTT（有重放风险，只用于幂等请求）。
  • 砍掉不安全套件（RSA 交换、CBC 等），只留 AEAD（AES-GCM / ChaCha20-Poly1305）。
追问：HTTPS 就完全安全了吗？—— 不。加密解决的是「传输被窃听/篡改」，防不了：① 客户端环境被植入根证书/代理（中间人，如公司内网抓包、木马）；② 服务器自身被攻破；③ 流量分析（大小、频率仍可见）。HTTPS 是必要条件非充分条件。
易错：「HTTPS 握手用非对称、传输用对称」的原因要说全——非对称只慢在计算，且能解决「不安全信道上协商出共享密钥」这个死结；对称快但没有安全的密钥分发手段。两者结合各取所长。
数字证书是什么？如何验证？中间人攻击怎么防？加分已掌握

证书解决的根本问题：公钥是谁的？

密钥交换最大的坑：你怎么知道拿到的公钥真的是目标服务器的？中间人可以把自己的公钥发给你（这就是中间人攻击 MITM）。CA（证书颁发机构）作为可信第三方为公钥背书。

证书内容与验证链

  • 证书 = 域名 + 公钥 + 有效期 + 签发者 + 签名（用 CA 私钥对证书内容 hash 加密）。
  • 证书链验证：站点证书 → 中间 CA 证书 → 根 CA。根 CA 公钥内置在操作系统/浏览器里（信任锚）。逐级「用上级公钥验下级签名」，链条任何一环失效即告警。

客户端验证四件事

  1. 域名匹配（证书的 CN/SAN 是否含当前域名）。
  2. 在有效期内、未被吊销（CRL / OCSP 在线验证）。
  3. 签名链能追溯到受信任的根 CA。
  4. 签名本身验得通（内容未被篡改）。

中间人攻击的完整链路与防护

攻击方式原理防护
伪造证书给客户端发自己签的证书客户端校验证书链，自签证书直接告警
降级攻击干扰协商，迫使双方用弱加密套件TLS 套件白名单、禁用旧版本；HSTS 强制 HTTPS
企业代理抓包给员工电脑装自签根证书，代理重签所有证书本质是「信任被合法植入」，防不了——所以说 HTTPS 防不了客户端被控的场景
加分项：证书透明度（CT）——CA 误签/私钥被冒用签出证书时，CT 日志让浏览器能发现「未公开签发」的证书；证书钉扎（Certificate Pinning）——App 内置服务端证书指纹，即使系统被装了假根证书也拒绝连接（银行/支付 App 常用）。
HTTP 和 HTTPS 的区别？HTTPS 的开销有多大？高频已掌握
维度HTTPHTTPS
端口 / 数据80 / 明文443 / TLS 加密

工程上如何摊薄 HTTPS 开销

  • 会话复用：Session ID / Session Ticket / TLS1.3 PSK，恢复连接免重新做完整密钥交换。
  • 长连接 + HTTP/2：一次握手，后续全部复用，握手成本被摊到无数请求。
  • TLS 卸载：网关/负载均衡统一终结 TLS，后端内网走 HTTP。
  • OCSP Stapling：服务端主动获取吊销状态随握手带上，客户端免 OCSP 查询 RTT。
结论化表达：「HTTPS 的额外延迟主要是建连阶段的 1~2 个 RTT，长连接下摊薄到可忽略；计算开销有硬件加速，现代互联网场景 HTTPS 已是默认配置（很多浏览器对 HTTP 直接标『不安全』，HSTS 普及）。」

数据封装与解封装

发送端自上而下逐层加头（应用数据 → +TCP 头=段 → +IP 头=包 → +帧头帧尾=帧 → 比特流）；接收端逐层拆头向上交付。每一层只处理本层头部，这正是分层的意义：各层独立演进（HTTP/3 换掉传输层下面，应用层代码不用改）。

追问：两台主机通信，中间经过路由器和交换机，各自用到哪层？—— 交换机工作在 L2（按 MAC 转发帧），路由器工作在 L3（按 IP 路由包）。所以跨网段通信：MAC 地址每经过一个路由器就换一跳，IP 地址全程不变（NAT 除外）。
易错：面试说「TCP/IP 四层」还是「OSI 七层」都行，但要能对应上；别把「HTTP 在传输层」这类话说出来。记法：应用层管内容、传输层管进程（端口）、网络层管主机（IP）、链路层管相邻节点（MAC）。
浏览器输入 URL 到页面展示，全过程发生了什么？（经典综合题）必考已掌握

标准答题骨架（按顺序，每一环都能被追问）

  1. URL 解析：判断合法性、HSTS 检查（强制 HTTPS）、查缓存（强缓存命中直接渲染）。
  2. DNS 解析：浏览器缓存 → 系统 hosts → 本地 DNS 服务器（递归查询）→ 根/顶级/权威域名服务器（迭代查询）→ 得到 IP；有缓存用缓存，可被 CDN 的 CNAME 接管（就近分配边缘节点）。
  3. TCP 连接：三次握手建立连接（HTTPS 再加 TLS 握手：证书验证 + 密钥交换）。
  4. 发送 HTTP 请求：组装请求行/头/体发出；中间可能经 CDN 边缘、负载均衡、反向代理、网关（鉴权/限流）层层转发到应用服务器。
  5. 服务端处理：负载均衡分发给实例 → 应用处理（可能访问缓存/DB/MQ）→ 返回响应。
  6. 浏览器渲染：解析 HTML 构建 DOM 树 → 解析 CSS 构建 CSSOM → 合成渲染树 → 布局（Layout/Reflow）→ 绘制（Paint）→ 合成（Composite）。期间遇到 JS/CSS/图片等再发起子请求（走同样的网络流程，静态资源多命中 CDN/缓存）。
  7. 连接管理：HTTP/1.1 keep-alive 保持连接复用，空闲超时四次挥手断开。
答法建议：这题是「考你知识广度的钩子题」，讲完主线后主动点名可展开的支线：如「DNS 这步可以展开讲 CDN 调度」「TLS 这步可以展开讲 HTTPS 握手」「网关这步可以展开讲微服务链路」——把面试官引到你最熟的领域。结合项目时强调：请求先到 Nginx/网关做了鉴权限流，再转发到服务。
易错：别背「十几步」背到渲染就完事。5 年经验的人答这题，重点在中间链路（CDN/LB/网关/负载均衡）和性能点（缓存层级、长连接、TLS 复用），纯浏览器渲染一笔带过即可。
DNS 解析的过程？递归查询和迭代查询的区别？高频已掌握

解析链路

浏览器缓存 → 系统/hosts 缓存 → 本地 DNS(运营商/8.8.8.8)
      └─(缓存未命中)─> 根域名服务器 "." 返回 .com 服务器地址
                     └─> .com 顶级域服务器返回 example.com 权威服务器地址
                           └─> 权威服务器返回最终 IP
  • 递归查询（客户端 → 本地 DNS）：「你必须给我最终答案」，本地 DNS 代劳到底。
  • 迭代查询（本地 DNS → 根/顶级/权威）：「我不知道，但告诉你下一个该问谁」，逐级问。
  • 最终结果在本地 DNS 和浏览器都有 TTL 缓存，之后直接命中。

工程相关的 DNS 知识点

  • CDN 原理：域名 CNAME 到 CDN 域名，CDN 的智能调度 DNS 按「地理位置 + 运营商」返回最近边缘节点 IP——DNS 是 CDN 流量调度的入口。
  • 负载均衡：DNS 轮询返回多个 IP 实现最粗粒度的负载分发（无法感知单机健康，TTL 内不变化）。
  • 故障切换慢：DNS 有 TTL 缓存，摘掉故障节点要等 TTL 过期——所以生产上真正的健康检查靠 LB 层，DNS 只做粗调度。
易错：「DNS 用什么协议」——UDP 53 为主（查询报文小、追求快，超时自己重传），TCP 53 用于区域传送（主从同步）和响应超 512 字节（DNSSEC、长记录）。这题答「DNS 就是用 TCP」就露馅了。

CDN（内容分发网络）

  1. 调度：DNS CNAME 到 CDN 调度系统，按位置/运营商返回最近边缘节点。
  2. 缓存：边缘节点命中直接返回（L1 边缘 → L2 区域中心 → 回源）。
  3. 回源：未命中回源站拉取并缓存；用 Cache-Control + URL 指纹控制策略；刷新可用 API 主动 purge。
  4. 收益：静态资源就近访问省 RTT；动态内容可用 CDN 的链路优化（专线/长连接复用）加速（动态加速）。
结合项目：你的部署架构里 Nginx 就是反向代理——说清它做了什么：SSL 卸载、按路径转发到网关/静态资源、限流兜底；API 网关（Spring Cloud Gateway）是更上层的「业务反向代理」，多了鉴权/灰度/协议转换。

WebSocket 本质

  • 基于 TCP 的全双工协议：一次 HTTP 升级握手后，切换到 WebSocket 协议帧，双方任意时刻都能主动推送。
  • 握手借用 HTTP：Upgrade: websocket + Connection: Upgrade，服务端回 101 Switching Protocols，之后不再走 HTTP 语义。

SSE服务端单向推（基于 HTTP，文本流）轻量，自动重连行情推送、AI 打字机输出等只需服务端→客户端
WebSocket双向握手后帧开销极小IM、协作编辑、游戏、实时大屏
追问：WebSocket 连接怎么保活？—— 协议级 Ping/Pong 帧探测；中间的 Nginx/LB 要配较长的 proxy_read_timeout（或应用层心跳），否则空闲连接会被代理掐断——这是 WebSocket 上生产最常见的坑。
易错：「HTTP 长连接（keep-alive）≠ WebSocket」。keep-alive 只是复用 TCP 连接传多个 HTTP 请求，通信模型仍是一问一答、只能客户端发起；WebSocket 才是协议级的双向通道。
RESTful API 设计规范？常见的违反点？高频已掌握

核心原则：资源 + HTTP 语义

  • URL 是名词、方法是动词：GET /orders 列表、GET /orders/123 详情、POST /orders 创建、PUT /orders/123 全量更新、PATCH 部分更新、DELETE /orders/123 删除。
  • 用状态码表达结果，而不是所有响应都 200 + body 里包 code 字段（严格 RESTful 立场；国内实践常统一 200 + 业务码，要能说清两种取舍）。
  • 版本化：/api/v1/... 路径版本（简单直观）或 Header 版本（URL 干净）。
  • 过滤/分页/排序放 query：?page=2&size=20&sort=createdAt,desc&status=PAID。
  • 嵌套表达从属：GET /users/1/orders；嵌套不建议超两层。

常见违反点（面试爱挑）

  • URL 里带动词：POST /getUser?id=1 → 应为 GET /users/1。
  • 所有接口都 POST，动作靠 URL 区分（RPC 风格混进 RESTful）——不是错，但别自称 RESTful。
  • PUT 做部分更新（PUT 语义是幂等的全量替换，部分更新用 PATCH）。
  • 用状态码返回 200 却在 body 里报错，监控/网关无法按状态码统计错误率。
追问：PUT 和 PATCH 都是更新，幂等性区别？—— PUT 全量替换天然幂等；PATCH 若是「set 字段」幂等，若是「age+1」这类相对操作就不幂等——设计上尽量让 PATCH 操作也是绝对值语义。

排查顺序：先分段，再深入

# 1. 连通性与延迟（ICMP 层）
ping <host>              # 丢包率、RTT 是否异常
mtr <host>               # 逐跳延迟/丢包，定位是哪一段网络差

# 2. 端口与建连（传输层）
telnet <host> 8080       # 端口通不通、建连耗时
curl -o /dev/null -s -w 'DNS:%{time_namelookup} 建连:%{time_connect} TLS:%{time_appconnect} 首字节:%{time_starttransfer} 总:%{time_total}\n' https://api.example.com/health
# ↑ 分段时间定位慢点：DNS 慢→解析问题；connect 慢→网络/握手问题；
#   starttransfer 慢→服务端处理慢；total 远大于 starttransfer→传输下载慢

# 3. 链路追踪（应用层）
# 看 SkyWalking/日志：服务端处理耗时 vs 客户端总耗时，差值≈网络+传输开销

关键判断逻辑

  • 客户端总耗时 ≈ 服务端处理耗时 → 不是网络，查服务端（慢 SQL、锁、GC）。
  • 总耗时远大于服务端处理耗时 → 差在哪一段：time_connect 大=网络/握手问题；time_starttransfer - time_appconnect 大=服务端排队没算进处理耗时（线程池排队、队列堆积）。
  • 偶发超时、重试后恢复 → 抓包看是不是丢包重传（重传会让 RTT 翻倍）。

# 拿到 pcap 用 Wireshark 分析：
#   看重传(TCP Retransmission)、零窗口(ZeroWindow)、RST

服务器出现大量 TIME_WAIT / CLOSE_WAIT，分别说明什么？怎么处理？必考已掌握

先定位：谁主动关的

ss -s                          # 总览各状态连接数
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn   # 按状态统计
ss -tanp state time-wait       # 看 TIME_WAIT 明细
netstat -natp | grep CLOSE_WAIT | awk '{print $5}' | sort | uniq -c  # CLOSE_WAIT 对端分布
状态含义根因处理
TIME_WAIT 多本机主动关闭连接，等 2MSL（60s）高频短连接：每次请求新建连接、用完就关（HTTP 未开 keep-alive、未用连接池、脚本反复 curl）① 改长连接/连接池（治本）；② tcp_tw_reuse=1 + 时间戳（客户端复用出站 TIME_WAIT）；③ 让对端主动关（转移但未消除）
CLOSE_WAIT 多本机被动关闭：收到对方 FIN，回 ACK 后自己一直不调 close()代码 bug：连接泄漏——异常分支没 close、线程阻塞在业务没走到 close、连接池满且无回收、下游重启本服务未感知① 查代码：所有资源走 try-with-resources/finally；② 连接池配空闲检测+最大存活时间；③ arthas/jstack 看持有连接的线程在干嘛
一句话总结（面试金句）：「TIME_WAIT 多是架构问题（短连接太多），CLOSE_WAIT 多是代码问题（连接没关）。前者调优能缓解，后者调参数没用，必须改代码。」
易错：TIME_WAIT 是主动关闭方的状态——客户端大量出现说明是客户端在频繁断开（比如没复用连接），不是服务端的问题；别一上来就调服务端内核参数。
TCP keepalive 和 HTTP keep-alive 有什么区别？加分已掌握
维度TCP keepalive（保活探测）HTTP keep-alive（连接复用）
层的归属传输层机制应用层语义（HTTP/1.1 的头）
目的检测死连接（对端宕机/网络断），探测后回收复用 TCP 连接传多个请求，省握手开销
默认行为Linux 默认关闭；开启后默认 7200s 空闲才探测，探测间隔 75s×9 次——对业务太迟钝HTTP/1.1 默认开启（Connection: keep-alive）
参数tcp_keepalive_time/intvl/probesNginx keepalive_timeout；服务端空闲超时后主动四次挥手
  • 关键区别：TCP keepalive 发的是空探测包（无数据），只为判断对端死活；HTTP keep-alive 关心的是「这条连接还能不能继续传 HTTP 请求」。
  • 应用层一般不用系统默认的 TCP keepalive（太慢），而是自己实现心跳（Netty IdleStateHandler、Redis/DB 驱动的心跳、注册中心心跳），频率可控且能联动业务逻辑（踢下线、重连）。
易错：名字几乎一样但完全是两码事。面试官问「为什么有了 TCP keepalive 应用还要自己心跳」——因为默认参数太迟钝（2 小时），且探测结果应用层拿不到主动权（不知道连接是死了还是对端只是闲着）。
Feign/RPC 调用偶发超时，从网络视角怎么排查？高频已掌握

超时时间线拆解（一次调用 = 多段耗时）

调用方                                    提供方
| DNS解析 | 建连(TCP+TLS) | 排队(连接池) | 网络RTT | 服务端处理 | 响应传输 |
└────────────── 客户端看到的总耗时 ──────────────────────────────┘

逐段排查清单

  1. DNS 段：解析是否抖动（K8s 里 CoreDNS 超时、ndots:5 引起的多余查询）。改为缓存、调小 TTL 或用连接内 DNS。
  2. 建连段：是否每次都新建连接（连接池没生效）？连接池 maxTotal/maxPerRoute 是否太小，高峰在池里排队——这是「偶发超时」最常见根因。
  3. 网络段：RTT 是否变大（跨机房？丢包重传？mtr 看链路）。
  4. 服务端段：处理耗时是否抖动（GC 停顿、慢 SQL、线程池满排队）。SkyWalking 对比「客户端耗时」和「服务端 Span 耗时」，差值即网络+排队。
  5. 配置合理性：超时时间 < 下游 P99？重试是否放大故障（超时 1s + 重试 3 次 = 最坏占用连接 3s+）？读超时/连接超时要分开配（连接超时短如 1s，读超时按 P99 设置）。
面试加分：讲一个真实案例模板：「大促时 Feign 偶发超时 → 链路追踪发现客户端耗时与服务端 Span 差值大 → 排查是连接池 maxPerRoute 默认 5，单路由并发一高峰就在池里排队 → 调大连接池 + 开启 keep-alive 复用 → P99 从 800ms 降到 80ms。」数字可以换成你自己的，但「分段定位 → 找到池/连接层根因」的框架要讲出来。
易错：别只调大超时时间了事——超时调大只是「忍耐上限提高」，排队根因还在，且会拖垮上游线程池引发雪崩。先定位耗时段，再对症下药。

⑥ 综合场景 NIO/Reactor · 大文件传输 · 推送方案

BIO/NIO/AIO 的区别？Reactor 模型是什么？Netty 和 epoll 的关系？高频已掌握

三种 IO 模型

模型方式问题/优势
BIO一连接一线程，accept/read 阻塞等待线程随连接数线性增长，1 万连接 = 1 万线程，上下文切换和内存都爆（C10K 问题）
NIOChannel + Buffer + Selector，一个线程用 Selector 轮询管理成千上万连接，就绪才处理同步非阻塞：线程不阻塞在单个连接上，靠操作系统多路复用（Linux 上就是 epoll）
AIO内核完成 IO 后回调通知Linux 下 AIO 实现不成熟（epoll 本身是同步的），Java AIO 实际用得少；Windows IOCP 才是真异步

Reactor 模型（NIO 的工程化）

  • 单 Reactor 单线程：一个线程负责所有连接的 accept + 读写 + 业务（Redis 6.0 前的网络处理）。简单，但业务慢会卡全部。
  • 单 Reactor 多线程：Reactor 只管 IO 事件，业务扔线程池。
  • 主从 Reactor 多线程（Netty 默认）：Boss 组只管 accept 新连接，注册到 Worker 组；Worker 组各自的事件循环管已注册连接的读写。连接（accept）与 IO 分离，负载均匀。

epoll 为什么快（vs select/poll）

  • select/poll：每次调用把全部 fd 集合从用户态拷贝到内核态，内核线性扫描所有 fd——O(n)，连接多了白白消耗。
  • epoll：epoll_create 在内核建红黑树管 fd（一次注册，反复使用）；epoll_wait 只返回就绪的 fd（就绪链表，事件驱动回调动入）；百万连接也只处理活跃的——O(活跃数)。这就是「事件就绪通知」代替「遍历轮询」。
串联表达：「Java NIO 是对操作系统多路复用（Linux epoll）的封装；Netty 又是对 Java NIO 的工程化封装（主从 Reactor + 线程模型 + 零拷贝 + 优雅的 API）」。追问「Netty 零拷贝」时另指堆外内存/CompositeByteBuf/文件传输 sendfile，与 OS 层零拷贝（mmap、sendfile）区分层次。
易错：NIO 的「非阻塞」指 IO 事件获取不阻塞（Selector 醒着等就绪事件），数据读写阶段仍是同步的（read 会真正搬数据）——「NIO=非阻塞 IO」精确说是「同步非阻塞」；真异步是 AIO。这个区分是高频追问点。
大文件上传下载怎么设计？断点续传的原理？高频已掌握

下载端：HTTP Range 请求

# 客户端请求文件的某个字节区间
GET /file/big.mp4 HTTP/1.1
Range: bytes=10485760-20971519      # 第 10MB ~ 20MB

# 服务端响应
HTTP/1.1 206 Partial Content
Content-Range: bytes 10485760-20971519/104857600
Content-Length: 10485760
  • 支持并发分片下载（多线程各下一段）与断点续传（记录已下字节，恢复时从断点 Range 续传）。
  • 服务端校验 If-Range/ETag，保证文件未变才续传，否则回 200 全量重下。

上传端：分片上传（对象存储标准方案）

  1. 客户端请求初始化，拿到 uploadId；文件按 5MB 分片逐个上传（可并行）。
  2. 每片上传记录序号，服务端/存储端（OSS/S3 的 multipart）保存分片。
  3. 全部完成后发合并请求，服务端合并分片；用整文件 MD5/SHA 校验完整性。
  4. 断点续传 = 查询已成功分片列表，只补传缺失分片。

服务端转发大文件的坑

  • 别用 MultipartFile 全量读进内存/临时目录再转发——网关/应用要流式透传（Nginx 直接 proxy_pass，Java 用流拷贝）。
  • Nginx 上传限制 client_max_body_size、请求超时、临时目录磁盘要同步改。
追问：秒传怎么实现？—— 客户端先算文件 hash（MD5+SHA1，大文件只算头部采样+长度或分块 hash）上传比对，服务端已有相同 hash 文件则直接建立引用，不传数据。代价：hash 碰撞理论风险 + 隐私考量（hash 即指纹）。
实时推送怎么选型：短轮询、长轮询、SSE、WebSocket？高频已掌握
方案原理延迟服务端开销适用场景
短轮询客户端定时发请求= 轮询间隔大量空请求 + 反复建连（未复用时）状态刷新页、实时性无所谓
长轮询请求挂起，有数据/超时才返回，客户端立即再发接近实时挂着大量连接占线程/内存（BIO 下线程被占死，NIO 才扛得住）兼容性好的伪实时（老式 Web QQ）
SSEHTTP 响应为长文本流 text/event-stream，服务端持续写实时低（复用 HTTP，连接轻）单向推送：行情、通知、AI 流式输出
WebSocket升级为全双工独立协议实时低（帧开销小），但需连接管理/心跳/集群广播方案IM、协作、双向交互

WebSocket 集群化的坑（加分，5 年经验必问）

  • 连接在各自实例上，用户 A 连在节点 1、要给连在节点 3 的用户 B 推消息 → 需要跨节点广播：Redis Pub/Sub 或 MQ 做节点间消息总线，各节点只推给自己的在线连接。
  • 会话寻址：维护「userId → 节点实例」的路由表（Redis），定向推送不广播全量。
  • Nginx 反代要配 Upgrade 头透传 + 长超时；粘滞会话（ip_hash）可省但更好的是消息总线。
选型结论：单向推送优先 SSE（简单、纯 HTTP、自动重连）；双向交互才上 WebSocket；只有在老旧环境/追求极简时用长轮询兜底。别上来就说 WebSocket——说清代价（连接管理、心跳、集群广播）才是 5 年经验。
