① Nacos 注册中心 服务发现 · 健康检查 · AP/CP

Nacos 是做什么的？注册中心和配置中心分别解决什么问题？必考已掌握

一句话用途

Nacos（Naming and Configuration Service）是阿里开源的「注册中心 + 配置中心」二合一组件，微服务架构的基础设施。

两个核心能力

  • 注册中心（服务发现）：服务提供者启动时注册自己的地址，消费者从 Nacos 拉取可用服务列表。解决「服务 A 怎么找到服务 B 的地址」。
  • 配置中心（动态配置）：把配置集中管理在 Nacos，改配置后动态推送给所有实例，不用重启、不用重新打包。

为什么微服务离不开它

  • 服务实例的 IP/端口是动态变化的（扩容、缩容、重启、宕机），不能写死在代码里。
  • 几十上百个服务，配置散落在各自 application.yml，改一处要改几十处、还要重启。
一句话：注册中心解决「谁在、在哪」，配置中心解决「配置改了怎么不重启生效」。这是微服务的两个地基。
Nacos 如何实现服务注册与健康检查？实例下线的完整流程？必考已掌握

注册流程

  1. 服务提供者启动后，向 Nacos Server 发送 POST /nacos/v1/ns/instance 注册请求，携带 ip、port、服务名、权重、元数据。
  2. 默认注册为临时实例（ephemeral=true），走 AP 模式（Distro 协议）同步。
  3. 消费者通过 GET /nacos/v1/ns/instance/list 拉取服务列表，并本地缓存 + 定时拉取。

健康检查（两类实例不同机制）

实例类型检查方式原理
临时实例客户端主动心跳客户端每 5s 发心跳；15s 未收到标记不健康；30s 未收到自动摘除
持久实例服务端主动探测Nacos Server 主动发请求探测实例是否存活（走 Raft CP 模式）

下线流程

  1. 服务正常关闭时，主动发送注销请求（DELETE），立即摘除实例。
  2. 若进程被杀、机器宕机（来不及注销），靠心跳超时兜底：15s 不健康 → 30s 移除。
坑：临时实例依赖心跳，若客户端 GC 停顿、网络抖动导致心跳超时，会被误摘除。所以有了「15s 不健康 / 30s 才移除」的两级缓冲，避免误杀。
Nacos 和 Eureka、Zookeeper、Consul 的区别？CAP 取舍？必考已掌握

CAP 取舍对照

组件CAP一致性协议健康检查说明
EurekaAP无（弱一致，最终一致）客户端心跳2.0 停更，自我保护模式
NacosAP + CP 可切换Distro（AP）/ Raft（CP）临时心跳 + 持久探测注册+配置一体，国内主流
ZookeeperCPZAB（类 Raft）心跳 + 会话强一致，Leader 挂掉期间不可用
ConsulCPRaft服务端探测强一致，功能全但重

核心区别（面试要点）

  • Nacos vs Eureka：Nacos 是「注册 + 配置」一体，且 AP/CP 可切换；Eureka 只做注册、纯 AP、已停更。
  • AP vs CP 的本质：网络分区发生时，AP 系统保证「能响应但数据可能旧」，CP 系统保证「数据一致但可能拒绝服务」。注册中心选 AP 更合适——宁可拿到稍旧的服务列表，也不能整个注册中心不可用。
为什么注册中心倾向 AP：注册中心挂了服务就全乱。短暂拿到过期实例列表，最多调用失败再重试；但 CP 若在选举期间不可用，所有服务都无法发现，是致命的。Nacos 用「临时实例 AP + 持久实例 CP」兼顾两种场景。

② 配置中心 Nacos Config · Apollo · 动态刷新

Nacos 配置中心如何实现配置动态刷新？原理是什么？必考已掌握

动态刷新原理

  1. 客户端启动时，从 Nacos Server 拉取配置，本地缓存。
  2. 客户端通过长轮询（Long Polling）监听配置变化：发请求到 Nacos，Nacos 挂起 30s（Hold），期间配置有变更就立即返回，否则 30s 超时后再发下一次。
  3. 客户端发现配置变了，触发配置变更监听器。

让配置生效的两种方式

方式注解适用
属性刷新@Value + @RefreshScope普通配置项（如开关、阈值）
原生动态@NacosValue(autoRefreshed=true)Nacos 客户端原生支持，无需 RefreshScope

@RefreshScope 原理

给 Bean 套一层代理 + 缓存，配置变更事件触发时，销毁旧 Bean 并重建，下次访问拿到新值。

坑：@RefreshScope 生成代理有性能开销，且可能有「旧对象残留」问题；频繁刷新的配置项不要滥用。敏感配置（密码、密钥）要加密存储（Nacos 支持配置加密插件）。
配置的优先级顺序？不同环境（dev/prod）怎么隔离？高频已掌握

配置优先级（从高到低）

命令行参数 > JVM 系统属性 > 环境变量 > Nacos 配置中心 > 本地 application.yml > bootstrap.yml（旧版）。

环境隔离的三层

维度Nacos 概念用途
命名空间 Namespace隔离环境（dev/test/prod）不同环境完全隔离，prod 与 test 互不可见
分组 Group同一环境内分组不同应用 / 不同场景的配置分组
Data ID具体配置文件如 order-service.yaml，配 spring.profiles.active 区分

Data ID 命名规范

默认 ${spring.application.name}-${spring.profiles.active}.${file-extension}，如 order-service-dev.yaml。

最佳实践：Namespace 隔离环境（最彻底）、Group 隔离应用分组、Data ID 用 应用名-profile.后缀 区分。灰度配置可用「配置的灰度发布」按 IP 灰度。

③ 网关 Gateway 路由 · 断言 · 过滤器 · 非阻塞

Spring Cloud Gateway 的核心职责？三大核心概念？必考已掌握

核心职责（统一入口）

  • 路由转发：根据路径/Header 转发到下游服务。
  • 统一鉴权：JWT 校验、权限过滤，不用每个服务各自做。
  • 限流：基于 Redis + Lua 令牌桶/漏桶。
  • 熔断降级、灰度发布、日志审计、跨域统一处理。

三大核心概念

概念作用
Route 路由转发规则：匹配条件 + 目标地址
Predicate 断言匹配条件（路径、Header、Method、时间、Cookie 等）
Filter 过滤器请求/响应处理（全局 GlobalFilter / 局部 GatewayFilter）

请求进来：先过 Predicate 匹配路由 → 再过 Filter 链处理 → 转发到下游。

追问：全局过滤（如 Token 校验）用 GlobalFilter，实现 filter(ServerWebExchange, GatewayFilterChain)，注意 Order 控制执行顺序。
Spring Cloud Gateway 和 Zuul 的区别？为什么 Gateway 性能更好？必考已掌握
维度Spring Cloud GatewayZuul 1.x
底层技术WebFlux + Reactor（Netty）Servlet 阻塞 IO（Tomcat）
模型非阻塞、异步、响应式同步阻塞
高并发性能优（线程开销小）差（每请求一线程）
WebSocket 长连接支持支持有限
维护状态活跃（官方主推）Zuul 1.x 停更（Zuul 2 迟迟未稳定）

为什么非阻塞性能更好

  • Zuul 1.x 是 Servlet 同步模型：每个请求占用一个线程，请求转发要等下游响应，线程阻塞。
  • Gateway 用 Netty + Reactor 非阻塞：少量事件循环线程处理海量并发，线程不阻塞等待，吞吐更高。
注意：Gateway 底层是 WebFlux，若网关里写了阻塞逻辑（如同步 JDBC 调用），会阻塞事件循环线程，反而性能变差。网关内要避免阻塞操作。
如何用 Gateway 实现限流、鉴权、灰度发布？高频已掌握

限流

用内置的 RequestRateLimiter 过滤器 + Redis，基于令牌桶算法（RedisRateLimiter），配置 replenishRate（每秒补充令牌数）和 burstCapacity（桶容量）。

spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/order/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100   # 每秒 100 个
                redis-rate-limiter.burstCapacity: 200   # 桶容量 200

鉴权

自定义 GlobalFilter：拦截请求 → 校验 JWT Token（验签 + 过期时间）→ 解析用户信息放 Header 透传给下游 → 校验失败返回 401。

灰度发布

通过 Header 或 Cookie 断言匹配灰度用户，路由到灰度版本服务：- Header=X-Version, gray → uri: lb://order-service-gray。

核心：网关是「横切逻辑」的最佳落点——鉴权、限流、灰度、日志，都在这做，下游服务专注业务。这是网关存在的最大意义。

④ 负载均衡 Ribbon · LoadBalancer · 算法

客户端负载均衡和服务端负载均衡的区别？Ribbon 属于哪种？必考已掌握

两种负载均衡

维度客户端负载均衡服务端负载均衡
代表Ribbon / Spring Cloud LoadBalancerNginx / LVS / F5
决策位置调用方自己从实例列表选一个集中式代理选一个转发
实例列表来源从注册中心拉取，本地缓存由 Nginx 配置 upstream 维护
优点无额外网络跳转，灵活集中管理，配置简单
缺点每个客户端都要集成多一次网络跳转，代理本身是瓶颈/单点

Ribbon 原理

  1. 从注册中心（如 Nacos）拉取服务实例列表，本地维护。
  2. 调用时通过 IRule 接口从列表选一个实例。
  3. 发起请求，若失败可按重试策略换实例重试。
记忆点：微服务内部服务间调用用客户端负载均衡（Ribbon/LoadBalancer），对外入口用服务端负载均衡（Nginx）。两者配合使用。
负载均衡算法有哪些？各自特点和适用场景？必考已掌握
算法原理适用场景
轮询 RoundRobin依次轮流分配实例性能均等（默认）
随机 Random随机选一个简单场景
加权轮询按权重分配，权重高多分实例性能不均
最小连接 BestAvailable选并发最小的实例请求耗时差异大
响应时间加权响应越快的权重越高动态调整（WeightedResponseTime）
一致性哈希同 key 路由到同实例需要会话粘滞 / 缓存亲和
注意：Ribbon 已进入维护模式（不再开发新功能），Spring Cloud 官方用 Spring Cloud LoadBalancer 替代。面试要能说出「Ribbon 停更、主流用 LoadBalancer」。
Spring Cloud LoadBalancer 相比 Ribbon 有什么变化？加分已掌握

为什么要替换 Ribbon

  • Ribbon 由 Netflix 维护，已停止更新，且依赖过多、代码耦合重。
  • Spring Cloud 官方推出 Spring Cloud LoadBalancer，轻量、模块化、响应式支持。

LoadBalancer 特点

  • 核心接口 ReactiveLoadBalancer / ServiceInstanceListSupplier。
  • 默认提供轮询、随机，支持自定义 ServiceInstanceListSupplier 实现算法。
  • 与 Nacos、Eureka 等服务发现无缝集成。
面试表述：「我们项目用的是 Nacos + Spring Cloud LoadBalancer，因为 Ribbon 停更了。LoadBalancer 默认轮询，特殊场景自定义 ServiceInstanceListSupplier 实现加权/一致性哈希。」

⑤ OpenFeign 远程调用 动态代理 · 声明式 · 对比 Dubbo

OpenFeign 的原理？为什么接口方法能直接变成 HTTP 调用？必考已掌握

一句话用途

OpenFeign 是声明式 HTTP 客户端：在接口上写 @FeignClient，就能像调本地方法一样调远程服务，不用手动拼 URL、处理序列化。

原理（动态代理）

  1. 启动时扫描 @FeignClient 注解的接口。
  2. 为接口生成动态代理对象（JDK 动态代理）。
  3. 调用接口方法时，代理拦截 → 根据方法上的注解（@GetMapping、@RequestParam 等）拼出 HTTP 请求（方法、路径、参数）。
  4. 交给 Encoder 序列化请求体 → 经负载均衡选实例 → 发起 HTTP 请求。
  5. 拿到响应，Decoder 反序列化成返回值类型。
@FeignClient(name = "order-service")   // 服务名
public interface OrderClient {
  @GetMapping("/order/{id}")           // 映射为 GET http://order-service/order/{id}
  Order getById(@PathVariable("id") Long id);
}
核心：动态代理 + 注解解析 + 编解码器。名字里「Feign」意为「伪装」，把远程调用伪装成本地调用。
OpenFeign 和 Dubbo 的区别？如何选型？必考已掌握
维度OpenFeignDubbo
协议HTTP/REST自定义 RPC 协议（TCP 长连接）
序列化JSON 等Hessian2 / Protobuf 等二进制
性能较低（HTTP 文本开销）高（长连接 + 二进制）
生态Spring Cloud 体系阿里系，Dubbo 3 支持 Triple 协议（gRPC 兼容）
跨语言天然支持较弱（Triple 协议改进）

选型：Spring Cloud 体系、需要 HTTP 网关、可能跨语言 → Feign；内部高并发、强服务治理、Java 统一栈 → Dubbo。也可混用：对外 HTTP（Feign/网关），内部 RPC（Dubbo）。
Feign 调用超时、重试、日志、拦截器怎么配置？有什么坑？高频已掌握

常用配置

feign:
  client:
    config:
      default:
        connectTimeout: 2000      # 连接超时
        readTimeout: 5000         # 读取超时
        loggerLevel: basic        # 日志级别
  # 重试（Feign 本身不重试，需集成 Spring Retry）

三个坑

  • 超时与重试叠加导致雪崩：重试次数 × 超时时间 会放大下游压力，要合理设置（幂等接口才重试）。
  • Feign 的线程池隔离：默认不隔离，大量慢调用会耗尽调用方线程，需配合 Sentinel/Hystrix 隔离。
  • 请求头丢失：Feign 调用默认不传递上游请求的 Header（如 Token、TraceId），需配 RequestInterceptor 手动透传。
拦截器（透传 Header）：实现 RequestInterceptor，从 RequestContextHolder 拿当前请求的 Header，塞进 Feign 请求，保证 Token、TraceId 全链路透传。

⑥ Sentinel 熔断降级 限流 · 熔断 · 降级 · 对比 Hystrix

Sentinel 的限流、熔断、降级分别是什么？怎么区分？必考已掌握

三个概念（易混淆，务必分清）

概念触发条件动作目的
限流QPS / 并发数超阈值拒绝或排队保护自己不被流量打垮
熔断错误率 / 慢调用比例超阈值快速失败，进入 open 状态保护下游，防止级联故障
降级调用失败 / 超时 / 熔断走 fallback 兜底逻辑保证核心功能可用

熔断状态机

  1. Closed（关闭）：正常调用，统计错误率/慢调用。
  2. Open（打开）：超阈值，快速失败（不再真实调用下游）。
  3. Half-Open（半开）：过一段时间，放少量探测请求，成功则转 Closed，失败继续 Open。
一句话区分：限流管「进来的流量」，熔断管「出去的下游」，降级是「失败后的兜底」。三者配合构建完整容错体系。

Sentinel 的限流算法

默认滑动窗口（LeapArray 结构）统计，支持令牌桶（预热模式 Warm Up）和漏桶（排队等待）。

核心优势：规则可动态调整（不用重启）、限流维度丰富、性能开销小（信号量优先）。Hystrix 线程池隔离虽彻底但线程切换开销大，停更后国内主流转向 Sentinel。
Sentinel 的滑动窗口限流是怎么实现的？为什么比固定窗口准？高频已掌握

固定窗口的「临界突刺」问题

固定窗口按整秒统计，前 1 秒的末尾和后 1 秒的开头，各来一波请求，2 倍阈值的流量会穿过，统计不准。

滑动窗口原理

  1. 把时间窗口（如 1 秒）切成多个小窗口（bucket），如 1 秒切 20 个，每个 50ms。
  2. 每个 bucket 独立计数，随着时间滑动，淘汰过期的 bucket。
  3. 统计时累加当前窗口内所有 bucket 的计数。
  4. 核心数据结构 LeapArray（环形数组），按当前时间定位 bucket。

优点

精度高（窗口越小越平滑），避免了固定窗口的边界突刺，也避免了漏桶/令牌桶的「精确计时」复杂度，是工程上精度与性能的折中。

追问：Sentinel 支持 QPS 和并发线程数两种阈值；QPS 用滑动窗口计数，线程数用当前活跃线程判断。预热模式（Warm Up）用令牌桶思想，让系统冷启动时流量缓升。

⑦ Seata 分布式事务 AT 模式 · 三组件 · undo_log

Seata 是什么？四种事务模式分别是什么？必考已掌握

一句话用途

Seata 是阿里开源的分布式事务解决方案，解决「跨多个微服务/数据库的操作如何保证一致性」。

四种模式

模式侵入性原理适用
AT无侵入（默认）自动生成反向 SQL（undo_log）通用，最常用
TCC高侵入业务自己实现 Try/Confirm/Cancel强一致性、性能要求高
SAGA中长事务拆多步 + 补偿长流程、多系统
XA无侵入数据库层两阶段提交数据库支持 XA 协议
选型：默认 AT（无侵入、够用）；需要强预留（冻结库存）→ TCC；长流程 → SAGA；老系统 + 数据库原生 XA → XA。
Seata AT 模式的原理？三个组件（TC/TM/RM）各自作用？必考已掌握

三个组件

组件全称作用
TCTransaction Coordinator事务协调器（Seata Server），维护全局事务状态
TMTransaction Manager事务管理器，发起全局事务（@GlobalTransactional）
RMResource Manager资源管理器，各分支事务，负责 undo_log 和分支注册

AT 模式两阶段流程

  1. 一阶段（业务 SQL 正常执行）：Seata 拦截业务 SQL，解析出 before image（改前数据）和 after image（改后数据），存入 undo_log 表，并注册分支事务到 TC。
  2. 二阶段提交：TC 通知各 RM 删除 undo_log（异步完成）。
  3. 二阶段回滚：TC 通知各 RM 用 before image 生成反向 SQL，把数据改回去。

无侵入的关键

业务代码只加一个 @GlobalTransactional 注解，其余全靠 Seata 数据源代理 + SQL 解析 + undo_log 自动完成，不用写回滚逻辑。

坑：AT 默认读未提交，全局事务未提交时其他事务可能读到脏数据；写数据会加全局锁降低并发；回滚时若数据已被其他事务改过（脏写），需校验 after image 是否匹配。
AT 模式和 TCC 模式怎么选？各自优缺点？高频已掌握
维度ATTCC
侵入性无（加注解即可）高（每个接口写 3 个方法）
性能较低（SQL 解析 + 全局锁）高（无全局锁，资源预留）
隔离性弱（有脏读/脏写风险）强（Try 阶段资源预留）
适用通用业务，快速接入资金、库存等强一致 + 高并发

TCC 三个方法

  • Try：资源预留（冻结库存、预扣余额），做检查。
  • Confirm：确认执行，真正扣减。
  • Cancel：释放预留资源，回滚。
TCC 两个难题：①空回滚（Try 没执行成功，Cancel 却先到，要识别并直接返回）；②悬挂（Cancel 先于 Try 执行，Try 后到却执行了，要防）。这两个是 TCC 必问的坑。

⑧ SkyWalking 链路追踪 TraceId · Span · 无侵入

链路追踪是做什么的？SkyWalking 的原理？必考已掌握

一句话用途

微服务下一个请求横跨多个服务，链路追踪把整个调用链可视化，快速定位「哪个服务、哪个方法」慢了或报错。

核心概念

概念含义
Trace一次完整请求，一个 TraceId 贯穿全程
Span一次调用（一个服务/一个方法），有父 Span 和子 Span
TraceId全局唯一，标识一次请求
SpanId标识一次调用在链中的位置

SkyWalking 原理（无侵入）

  1. 通过 Java Agent（字节码增强）启动时挂载，无需改业务代码、无需埋点。
  2. 自动拦截主流框架（Spring MVC、Dubbo、Feign、MyBatis、Redis、MQ 等），生成 Span。
  3. TraceId 通过请求头（如 sw8）在服务间透传。
  4. 数据上报到 OAP（后端分析平台），聚合存储，通过 UI 展示调用拓扑、耗时、错误。
优势：无侵入（Agent 探针）、全栈支持、可视化拓扑。对比 Zipkin 需埋点、Sleuth 是埋点规范（已并入 Micrometer Tracing）。

组件定位侵入性说明
SkyWalking完整 APM（追踪 + 指标 + 日志）无（Agent）国内主流，功能全面

关系：Sleuth 是「埋点 + TraceId 生成」，Zipkin/SkyWalking 是「收集 + 展示」。SkyWalking 一体化（埋点 + 收集 + 展示全包），所以最省事。5 年经验要能说清「Sleuth 是规范、SkyWalking 是完整方案」。
TraceId 如何在服务间透传？异步、线程池场景会丢吗？加分已掌握

同步调用透传

TraceId 存在 ThreadLocal 里（Sleuth 的 TraceContext），跨服务时通过请求头（HTTP Header / MQ 消息属性 / Dubbo attachment）传递，下游从 Header 取出继续。

会丢的场景（高频坑）

  • 异步线程池：ThreadLocal 不跨线程，新线程拿不到 TraceId → 用 TaskDecorator 包装线程池，提交任务时把 TraceId 传入。
  • MQ 消费：生产者把 TraceId 放消息 Header，消费者取出后重新设置到 ThreadLocal。
  • Feign 调用：需 RequestInterceptor 手动透传（Feign 默认不传 Header）。
核心：TraceId 的本质是「请求上下文跨线程、跨进程传递」。任何打破「同线程 + 同进程」的边界（线程池、异步、MQ），都要手动透传，否则链路就断了。

⑨ RocketMQ 消息 削峰 · 解耦 · 最终一致

消息队列在微服务中的作用？RocketMQ 的核心概念？必考已掌握

三大作用

  • 削峰填谷：高并发请求先入 MQ，消费者按自身能力消费，保护下游 DB。
  • 异步解耦：下单后异步发短信、加积分，主流程不用等。
  • 最终一致：配合本地消息表/事务消息，实现跨服务最终一致。

RocketMQ 核心概念

概念含义
Producer消息生产者
Consumer消息消费者（支持 Pull / Push）
Broker消息存储 + 转发节点
NameServer路由注册中心（轻量，非 ZooKeeper）
Topic / Tag主题（消息分类）/ 标签（二级分类）
Message Queue主题下的队列，实现并行消费
为什么选 RocketMQ：阿里开源、事务消息支持好、吞吐高（万级 TPS）、延迟低，是国内 Java 微服务消息场景的主流。
如何保证消息不丢失？生产、存储、消费三段分析。必考已掌握

三段式分析（RocketMQ）

  1. 生产端：用同步发送（SendResult 返回 OK 才算成功），失败重试；避免 oneway 单向发送。
  2. Broker 端：同步刷盘（SYNC_FLUSH，落盘才返回）+ 主从同步复制（master 同步到 slave 才确认）。
  3. 消费端：手动 ACK，业务处理成功后再提交 offset；避免自动 ACK（消息一到就确认，处理失败会丢）。

代价

「不丢失」的代价是性能下降（同步刷盘、同步复制都是延迟换可靠）。核心业务（支付、订单）才需要这么严格的配置。

核心认知：消息系统的可靠性是「木桶效应」，三段任何一段漏了都会丢。面试要能完整说三段，而不是只说「手动 ACK」。
如何保证消息不重复消费、不乱序？必考已掌握

不重复消费（幂等）

  • 消息系统是「至少一次投递」（at-least-once），重复不可避免，消费端必须幂等。
  • 方案：用业务唯一 ID（订单号、消息 key）去重——数据库唯一索引 / Redis setnx / 去重表。

不乱序

  • 乱序原因：多队列并行消费，顺序天然无法保证。
  • 全局有序：单一队列（牺牲吞吐，一般不这么干）。
  • 局部有序：同一业务 key（订单 ID）路由到同一队列（MessageQueueSelector），队列内 FIFO 保证顺序。
面试金句：「不丢 + 不重 + 有序 + 高吞吐」四者不可兼得。工程上「至少一次 + 消费端幂等 + 按业务 key 局部有序」是最务实组合。
RocketMQ 的事务消息是怎么实现最终一致的？高频已掌握

事务消息流程

  1. 生产者发送半消息（half message），此时消费者看不到。
  2. 生产者执行本地事务。
  3. 本地事务成功 → 提交（commit）半消息，消费者可见；失败 → 回滚（rollback）。
  4. Broker 长时间未收到确认，会回查（回调生产者的 checkLocalTransaction 接口）确认本地事务状态。

解决的问题

「本地事务成功」和「消息发送成功」无法原子。事务消息通过「半消息 + 本地事务 + 回查」保证两者最终一致。

对比本地消息表：事务消息更优雅（无需本地表 + 定时扫描），但依赖 RocketMQ 特性。本地消息表方案通用，任何 MQ 都能用。

完整架构叙述（面试直接背）

  1. 请求进入：客户端 → Nginx → Gateway 网关（鉴权、限流、灰度、路由）。
  2. 服务发现：所有服务启动时注册到 Nacos，网关和调用方从 Nacos 拉取实例列表。

  5. 容错保护：Sentinel 做限流、熔断、降级，防止雪崩。
  6. 数据一致性：跨服务事务用 Seata；异步解耦、削峰用 RocketMQ。
  7. 可观测：SkyWalking 链路追踪 + Prometheus 监控 + ELK 日志。
