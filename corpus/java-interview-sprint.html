高频面试题

Q1JVM 内存区域怎么划分？哪些是线程私有的？必考

线程私有：程序计数器、虚拟机栈、本地方法栈；线程共享：堆、方法区。

程序计数器
记录当前线程执行到哪条字节码，线程切换后靠它恢复现场。唯一不会抛 OOM 的区域。
虚拟机栈
每个方法一个栈帧：局部变量表、操作数栈、动态链接、返回地址。递归太深抛 StackOverflowError，栈无法扩展抛 OOM。
本地方法栈
为 native 方法服务，HotSpot 里和虚拟机栈合并实现。
堆
对象实例的主战场，分新生代（Eden + 2 个 Survivor）和老年代。JDK7 起字符串常量池、静态变量已经挪到堆里。
方法区
JDK7 叫永久代（在堆内），JDK8 换成元空间（在本地内存），所以元空间溢出报的是 Metaspace 而不是 heap space。
追问 · JDK8 为什么用元空间替代永久代？① 永久代大小难预估，调参靠猜；② 永久代的回收和 Full GC 绑定，效率低；③ 合并 JRockit 后统一实现。换成元空间后默认只受物理内存限制（-XX:MaxMetaspaceSize 可限制）。
踩坑 · 别说"方法区就是永久代"。方法区是规范里的概念，永久代/元空间是 HotSpot 的两种实现。这是在考察你有没有版本意识。
Q2一个对象从 new 出来到进入堆，经历了什么？高频

五步：类加载检查 → 分配内存 → 内存置零 → 设置对象头 → 执行构造方法。

  • 分配内存用指针碰撞（内存规整，Serial/ParNew）或空闲列表（内存碎片化，CMS）。
  • 并发分配靠 CAS + 失败重试，或者 TLAB（Thread Local Allocation Buffer）：每个线程在 Eden 里预划一小块私有区域，分配不用加锁。默认占 Eden 的 1%，-XX:±UseTLAB 控制。
  • 对象头 = Mark Word（哈希码 + GC 分代年龄 + 锁状态，32/64 位）+ 类型指针（指向 Class）。数组对象多一个长度字段。
  • 实例数据会按类型重排（long/double 在前，减少 padding），最后对齐填充到 8 字节倍数。
追问 · 为什么堆不要设成 32G 以上？因为 -XX:+UseCompressedOops 指针压缩在堆大于 32G 时失效，对象引用从 4 字节变 8 字节，对象变大、缓存命中率下降，性能反而倒退。这是很典型的"以为加内存就能解决问题"的反例。
Q3怎么判断一个对象可以回收？为什么不用引用计数？必考

HotSpot 用可达性分析：从 GC Roots 出发遍历引用链，遍历不到的就可以回收。

GC Roots 包括：虚拟机栈中的局部变量、本地方法栈中 JNI 引用、方法区静态属性、常量引用、被 synchronized 持有的对象、Class 对象、JVM 内部引用。

为什么不用引用计数：① 循环引用无法回收（A 引用 B、B 引用 A，计数都不为 0）；② 每次赋值都要增减计数，写操作开销大、还要保证原子性。

追问 · 不可达就一定回收吗？不是。要经历两次标记：不可达后判断是否重写了 finalize()，若重写则放入 F-Queue 尝试自救，第二次标记仍不可达才真正回收。finalize() 在 JDK9 已标记废弃，面试可以主动提一句"现在基本用 try-with-resources / Cleaner 替代"。
Q4强、软、弱、虚四种引用分别用在哪？高频
  • 强引用：new 出来的默认引用，只要可达就不回收。内存不足时宁可 OOM 也不回收。
  • 软引用 SoftReference：内存不足时才回收，适合做缓存。但生产上做缓存更推荐 Caffeine/Guava Cache，能精确控制容量和淘汰策略。
  • 弱引用 WeakReference：下次 GC 必定回收。典型用途：ThreadLocalMap 的 key、WeakHashMap、Tomcat 的类加载器泄漏检测。
  • 虚引用 PhantomReference：唯一目的是对象被回收时收到通知（配合 ReferenceQueue），用于管理堆外内存 —— DirectByteBuffer 的 Cleaner 就是这么做的。
追问 · 软引用做缓存有什么问题？回收时机完全由 GC 决定，不可控。可能出现"刚放进缓存就被清掉"或者"堆积到内存快满才一次性清光"的抖动。所以还是要用带 LRU/LFU 的成熟缓存库。
Q5CMS 和 G1 的区别？线上你会怎么选？必考

CMS（并发标记清除，JDK9 已废弃、JDK14 移除）：

  • 四阶段：初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除。只有两次短暂 STW，追求低延迟。
  • 老年代用标记-清除 → 产生内存碎片 → 大对象分配失败触发 Concurrent Mode Failure，退化成 Serial Old 单线程 Full GC，停顿可能好几秒。
  • 还有"浮动垃圾"问题（并发清理期间用户线程又产生的垃圾只能等下次）。

G1（JDK9 起默认）：

  • 堆切成等大的 Region（1-32MB），逻辑分代、物理不分代。
  • 整体是标记-整理，Region 间是复制 → 没有碎片问题。
  • 可预测停顿：-XX:MaxGCPauseMillis 设定目标，G1 按回收收益排序选出本次要回收的 Region 集合（Garbage First 名字的来源）。
  • Mixed GC 会同时回收年轻代和部分老年代 Region。
选型话术：堆 4-16G、要求停顿可控 → G1；超大堆（几十 G）+ 极致低延迟 → ZGC（JDK17 后可生产用，停顿 <1ms，代价是吞吐略降和内存占用略高）；小堆（<4G）+ 吞吐优先 → Parallel Scavenge + Parallel Old。
Q6G1 的 RSet、SATB、TAMS 分别解决什么问题？高频

这三个是 G1 能"分 Region 却还能只扫部分区域"的关键。

  • RSet（记忆集）：记录"哪些别的 Region 有引用指向我"。回收单个 Region 时不用扫全堆找引用，直接查 RSet。代价是每个 Region 要占约 5-10% 的内存。
  • SATB（Snapshot At The Beginning）：并发标记期间，以标记开始那一刻的对象图为快照。通过写前屏障（pre-write barrier）把被覆盖的旧引用记进队列，保证不漏标。代价是产生浮动垃圾（快照后新产生的垃圾本轮不收）。
  • TAMS（Top At Mark Start）指针：每个 Region 记两个指针，标记期间新分配的对象默认就是存活的，不用再标记 —— 这就是 SATB 漏标问题在 G1 里的具体补法。
对比记忆：CMS 用增量更新（incremental update，记新引用）解决漏标，G1 用 SATB（记旧引用）。问法是"三色标记为什么会漏标、怎么解决"，答"漏标要同时满足：黑对象新增指向白对象的引用 + 灰对象到白对象的引用被删除；增量更新破坏前者，SATB 破坏后者"。
Q7线上 CPU 飙到 100%，你怎么排查？必考

标准四步（背下来）：

  1. top 找到高 CPU 的进程 PID
  2. top -Hp <pid> 找到该进程里高 CPU 的线程 TID
  3. printf "%x\n" <tid> 把 TID 转成 16 进制
  4. jstack <pid> | grep -A 30 <hex> 定位到具体代码栈

先判断是哪一类：

  • 业务线程忙：栈里能看到业务代码 → 死循环、正则灾难性回溯、超大 JSON 序列化、频繁对象创建。
  • GC 线程忙：jstat -gcutil <pid> 1000 看 FGC 次数和耗时，或 top -Hp 看到 "GC task thread"。→ 定位到内存问题。
  • 上下文切换高：vmstat 1 看 cs 列、pidstat -w。→ 线程数过多、锁竞争激烈。
有 Arthas 就更简单：thread -n 5 直接列出最忙的 5 个线程栈，dashboard 看整体。开口说 Arthas 是加分的，说明真上过生产。
踩坑：只答"用 jstack 看"是半步。面试官想听的是你如何区分"业务死循环"和"GC 打满"，因为这两条的后续动作完全不同。

Q9双亲委派模型是什么？它被"破坏"过几次？高频

机制：类加载器收到加载请求时，先委派给父加载器；父加载器加载不了，自己才尝试加载。

好处：① 保证核心类库不被篡改（你自己写一个 java.lang.String 永远不会被加载）；② 避免同一个类被重复加载。

层级：Bootstrap（C++ 实现，加载 java.base 等）→ Platform/Extension → Application → 自定义。

三次被破坏：

  • 第一次（JDK1.2 之前）：为了兼容老代码，允许子类覆写 loadClass()。后来通过新增 findClass() 让用户只覆写它来规避。
  • 第二次（SPI）：像 JDBC 的 DriverManager 由 Bootstrap 加载，但它要加载厂商实现类（Application 层）—— 父加载器看不到子加载器的类。解法是线程上下文类加载器 Thread.currentThread().getContextClassLoader()。
  • 第三次（热部署 / OSGi / Tomcat）：Tomcat 给每个 webapp 一个 WebappClassLoader，优先加载自己 WEB-INF/lib 下的类，实现应用间隔离和不同版本共存。
追问 · 为什么要破坏双亲委派？因为"父加载器无法访问子加载器的类"这个方向性是单向的，而实际场景里父子都需要互相可见（SPI 是父要子，Tomcat 是相互隔离）。
Q10逃逸分析能给代码带来什么优化？加分

JIT（C2）分析方法内 new 的对象是否会"逃逸"出方法或线程，不会逃逸就能做三件事：

  • 栈上分配：对象随栈帧销毁，减轻 GC 压力。注意：HotSpot 里这个其实很少真正落地。
  • 标量替换：把对象拆成若干个基本类型变量放在栈上 —— 这才是实际生效、收益最大的那个。所以"小对象分配没那么贵"。
  • 锁消除：对象只被本线程访问，synchronized 直接去掉。典型例子：StringBuffer 局部变量拼字符串，锁会被消除。

默认开启：-XX:+DoEscapeAnalysis。

追问 · 为什么你的代码里锁消除没生效？因为要 C2 编译后才有，解释执行阶段还是走原逻辑 —— 别用它来解释压测性能差异。
Q11volatile 保证原子性吗？它靠什么实现？必考

保证可见性和有序性，不保证原子性。

  • 可见性：写 volatile 变量后立即刷回主内存，并使其他 CPU 的缓存行失效（底层是 lock 前缀指令 + MESI 缓存一致性协议）。
  • 有序性：通过内存屏障禁止指令重排。写前插 StoreStore、写后插 StoreLoad；读后插 LoadLoad、读前插 LoadStore。
  • 不保证原子性：i++ 是"读-改-写"三步，volatile 只能保证每步读到最新值，不能保证三步不可分割。要原子性得用 AtomicInteger 或加锁。
必被追问 · DCL 单例为什么必须加 volatile？因为 new 分三步：分配内存 → 初始化对象 → 把引用赋给变量。② 和 ③ 可能重排，导致另一个线程在 ③ 完成后、② 未完成时拿到一个"非 null 但字段全是初始值"的对象。volatile 禁止了这个重排。
Q12说一下 synchronized 的锁升级过程必考

无锁 → 偏向锁 → 轻量级锁 → 重量级锁，状态记录在对象头 Mark Word 里。

  • 偏向锁：Mark Word 记录持有线程 ID，同一线程再进来只需比对 ID，不用任何同步操作。有第二个线程来竞争时撤销（撤销要 STW，代价不小）。JDK15 起默认禁用，JDK18 已彻底移除 —— 原因是撤销成本高于收益。
  • 轻量级锁：CAS 把 Mark Word 指向当前线程栈中的 Lock Record。失败则自旋重试（自适应自旋）。
  • 重量级锁：竞争激烈时膨胀成 ObjectMonitor，未抢到的线程进入 EntryList 阻塞挂起，依赖操作系统 mutex → 涉及用户态/内核态切换，开销大。

两个优化：锁消除（JIT 判定无共享就不加锁）、锁粗化（相邻的加锁操作合并成一次）。

追问 · 锁能降级吗？基本不能。偏向锁撤销后不可逆；重量级锁理论上可在 safepoint 降为轻量级，但实际极少发生。所以设计上应该避免让锁频繁升级到重量级（减少临界区、降低竞争）。
踩坑：提一句"JDK18 移除了偏向锁"，说明你在跟进版本 —— 这是很廉价但很有效的加分点。
Q13AQS 的原理讲一下必考

核心三件套：一个 volatile int state + 一个 CLH 变体的双向 FIFO 队列 + 一套模板方法。

  • state 语义由子类定义：ReentrantLock 里 0/1 表示是否被占、>1 表示重入次数；Semaphore 里表示可用许可数；CountDownLatch 里表示剩余计数。
  • 子类只需实现 tryAcquire/tryRelease（独占）或 tryAcquireShared（共享），AQS 负责排队、阻塞、唤醒。
  • 节点 waitStatus：SIGNAL(-1) 表示"我的后继需要我唤醒"、CANCELLED(1)、CONDITION(-2)、PROPAGATE(-3)。

公平 vs 非公平（ReentrantLock）：非公平锁进来先抢一次，抢不到才入队 —— 吞吐高但可能饥饿；公平锁会先检查队列里有没有等待者。

Condition：每个 Condition 有独立的等待队列。await() 把节点从同步队列移到等待队列并释放锁；signal() 移回同步队列。这就是 BlockingQueue 的实现基础。

一次答全（体现体系感）：AQS 的共享模式还支撑了 CountDownLatch、Semaphore、ReentrantReadWriteLock（高 16 位表示读锁、低 16 位表示写锁）。面试只要说"我读过 AQS 源码"，就一定会被问到 ReentrantLock 的非公平锁抢锁逻辑，提前准备好。
Q14线程池的执行流程？核心线程数怎么定？必考

7 个参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。

执行流程（顺序不能错）：

  • 核心线程未满 → 直接新建核心线程执行
  • 核心线程已满 → 任务先入队列，而不是创建新线程（这是最容易答错的点）
  • 队列也满 → 创建非核心线程直到 maximumPoolSize
  • 线程数到上限且队列满 → 触发拒绝策略

四种拒绝策略：AbortPolicy（默认，抛 RejectedExecutionException）、CallerRunsPolicy（调用者线程自己执行，天然背压，最推荐用于不能丢任务的场景）、DiscardPolicy（静默丢弃，危险）、DiscardOldestPolicy（丢队列最老的）。

核心线程数怎么定：CPU 密集 N+1、IO 密集 2N —— 但这只是起点。靠谱答案是"压测 + 监控"：看 activeCount、queueSize、completedTaskCount、rejectCount，找到吞吐拐点。

追问 · 为什么不用 Executors 的工厂方法？newFixedThreadPool 用 LinkedBlockingQueue 无界队列 → 任务堆积导致 OOM；newCachedThreadPool 最大线程数是 Integer.MAX_VALUE → 可能创建海量线程。所以必须手写 ThreadPoolExecutor 并显式指定有界队列，同时自定义线程名（方便 jstack 定位）。
追问 · 线程池里的任务抛异常会怎样？线程会终止并被移除，然后新建一个线程。execute() 的异常会走到 UncaughtExceptionHandler；submit() 会包进 Future，不调用 get() 就永远看不到异常 —— 这是很隐蔽的坑。
Q15ThreadLocal 为什么会内存泄漏？必考

结构：每个 Thread 内部持有一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是强引用。

泄漏路径：ThreadLocal 对象被回收后，key 变成 null，但 value 还挂在 Thread 的 map 里 → 线程不死（线程池里的线程是长期存活的）→ value 越积越多 → 直到 OOM。

正确写法：

  • 必须 try-finally 里 remove()，这是唯一的可靠做法。
  • ThreadLocalMap 在 get/set/remove 时会顺带清理一些 key 为 null 的 Entry，但这是启发式清理，不能依赖。
追问 · key 为什么设计成弱引用？算是一种兜底：让 ThreadLocal 对象本身能被回收，不然连 key 都永远留着。但 value 还是强引用，所以依然要手动 remove。
追问 · InheritableThreadLocal 能用在线程池里吗？不能。它只在创建子线程那一刻拷贝父线程的值，线程池的线程是复用的，会拿到上一个任务的残留值。解法是阿里开源的 TransmittableThreadLocal（TTL），配合 TtlExecutors 包装线程池。
踩坑：MDC（日志链路 traceId）也是 ThreadLocal 实现，异步任务/线程池里会丢 —— 这是真实生产问题，主动说出来非常加分。
Q16ConcurrentHashMap 1.8 为什么放弃分段锁？高频

1.7 的做法：Segment 数组（继承 ReentrantLock），每个 Segment 锁住一部分 HashEntry，并发度 = Segment 数量（默认 16），扩容也只能段内进行。

1.8 的做法：

  • Node 数组 + CAS 初始化头节点 + synchronized 锁单个桶（链表头）
  • 链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树（否则先扩容）
  • 并发粒度从"段"细化到"桶"，理论上并发度 = 数组长度
  • size() 用 baseCount + CounterCell[] 分散计数，避免热点
  • 扩容支持多线程协助迁移，用 ForwardingNode 标记已迁移的桶
追问 · 为什么用 synchronized 而不是 ReentrantLock？① 1.8 后 synchronized 有锁升级优化，单桶粒度下竞争不激烈，性能足够；② 每个桶一个 ReentrantLock 对象会浪费大量内存（几百万个桶的场景）；③ 代码更简洁。
Q17CAS 有什么问题？LongAdder 为什么比 AtomicLong 快？高频

CAS 三大问题：

  • ABA 问题：值从 A 改成 B 又改回 A，CAS 认为没变过。解法：AtomicStampedReference 加版本号，或 AtomicMarkableReference 加布尔标记。
  • 自旋开销大：竞争激烈时大量线程空转，CPU 白白消耗。
  • 只能保证一个变量的原子性：多变量要 AtomicReference 包装成对象，或者直接加锁。

LongAdder 的思路：把热点拆开 —— 内部维护一个 Cell[] 数组，不同线程 CAS 到不同的 Cell 上，sum() 时把所有 Cell 累加。这样竞争被分散，吞吐大幅提升。

追问 · 那什么时候还用 AtomicLong？需要强一致的实时值时。LongAdder 的 sum() 是弱一致的（累加过程中可能读到中间态），适合做统计计数，不适合做序列号或需要精确判断的阈值。
Q18并发容器怎么选？虚拟线程了解吗？加分

容器选型：

  • CopyOnWriteArrayList：写时复制，读完全无锁。适合读极多写极少（配置、监听器列表）。写多会频繁复制且内存瞬时翻倍。
  • ConcurrentLinkedQueue：CAS 无锁队列，无界，适合高并发入队。
  • BlockingQueue 家族：ArrayBlockingQueue（有界，一把锁两个 Condition）、LinkedBlockingQueue（默认无界，读写分离两把锁）、SynchronousQueue（不存储直接移交）、DelayQueue（延迟任务）、PriorityBlockingQueue。

工具类：CountDownLatch（一次性，一等多）、CyclicBarrier（可重用，互相等）、Semaphore（限流/连接池）。

虚拟线程（JDK21 正式）：由 JVM 调度的轻量级线程，挂载到少量平台线程上。阻塞时会自动卸载（unmount）释放载体线程，所以能支持百万级线程。

追问 · 虚拟线程能解决什么、不能解决什么？能解决的是"IO 阻塞导致线程数不够，只能靠异步回调把代码写复杂"的问题 —— 用同步写法拿到异步吞吐。不能解决的是 CPU 密集和同步块（synchronized 会 pin 住载体线程，JDK21+ 建议换 ReentrantLock）。另一个坑是 ThreadLocal：百万虚拟线程各持一份会爆内存，官方建议改用 ScopedValue。预置线程池也不再需要（Executors.newVirtualThreadPerTaskExecutor()）。

Q1Spring 的启动流程（refresh 方法）讲一下高频

核心是 AbstractApplicationContext#refresh() 的 12 步，不用全背，记住 5 个关键步骤：

  1. prepareRefresh：准备上下文，记录启动时间、初始化属性源
  2. obtainFreshBeanFactory：创建并配置 BeanFactory（Boot 中复用已有的）
  3. prepareBeanFactory：设置 ClassLoader、SpEL 解析器、注册 BeanPostProcessor、添加忽略依赖（Aware 接口）
  4. postProcessBeanFactory：子类扩展点（如 MVC 注册 RequestMappingHandlerMapping）
  5. invokeBeanFactoryPostProcessors ← 关键 ①：执行 ConfigurationClassPostProcessor，扫描 @Component、解析 @Bean、@Import，生成 BeanDefinition；并给 @Configuration 类生成 CGLIB 代理，保证 @Bean 方法返回单例
  6. registerBeanPostProcessors ← 注册 AOP、@Autowired、@EventListener 等后置处理器（按 PriorityOrdered → Ordered → 普通 排序）
  7. initMessageSource / initApplicationEventMulticaster：国际化、事件广播器
  8. onRefresh：创建内嵌容器（Spring Boot 在这里启动 Tomcat）
  9. registerListeners：注册监听器
  10. finishBeanFactoryInitialization ← 关键 ②：实例化所有非懒加载单例（Bean 生命周期在这里跑）
  11. finishRefresh：发布 ContextRefreshedEvent、启动 LifecycleProcessor
记忆锚点：准备上下文 → 造工厂 → 扫 BeanDefinition → 装后置处理器 → 造单例 → 完工。两个"关键"是面试官真正想听的：BeanDefinition 什么时候来的、单例什么时候造的。
Q2Bean 的完整生命周期必考
  1. 实例化：调用构造器 / 工厂方法
  2. 属性填充：@Autowired、@Value 注入；回调 Aware 系列（BeanNameAware → BeanFactoryAware → ApplicationContextAware）
  3. 初始化（顺序很重要）：
    • BeanPostProcessor.postProcessBeforeInitialization（@PostConstruct 在这一步由 CommonAnnotationBeanPostProcessor 触发）
    • InitializingBean.afterPropertiesSet()
    • init-method（@Bean(initMethod=...)）
    • BeanPostProcessor.postProcessAfterInitialization ← AOP 代理在这里生成
  4. 使用中（放进单例池）
  5. 销毁：@PreDestroy → DisposableBean.destroy() → destroy-method
最容易被追问的点：AOP 代理是在 postProcessAfterInitialization 生成的。这意味着——你注入到别的 Bean 里的是代理对象，不是原始对象。这一条同时解释了"自调用为什么会让 AOP 失效"。
踩坑：@PostConstruct 和 afterPropertiesSet 的顺序别搞反。@PostConstruct 在前（它由 BeanPostProcessor 的 before 阶段触发），afterPropertiesSet 在后。
Q3Spring 怎么解决循环依赖？为什么需要三级缓存而不是二级？必考

先说结论：只能解决单例 + setter/字段注入的循环依赖。

三级缓存：

  • singletonObjects（一级）：完整的成品 Bean
  • earlySingletonObjects（二级）：半成品，属性还没填完
  • singletonFactories（三级）：ObjectFactory 工厂，延迟生产早期引用

流程（A 依赖 B、B 依赖 A）：A 实例化后，把"生产 A 早期引用的工厂"放进三级缓存 → 填充 A 的属性时发现要 B → 创建 B → B 填充属性时发现要 A → 从三级缓存拿到工厂并调用 getObject()，得到 A 的早期引用（此时如果需要 AOP，就提前生成代理）→ B 创建完成 → A 完成。

为什么不能只有二级？如果把"早期引用"直接放二级缓存，那就必须在 A 刚实例化完、还没走到 postProcessAfterInitialization 时就决定"要不要给它生成 AOP 代理"。而这个判断依赖后置处理器，此刻还没轮到。三级缓存的工厂把"是否代理"的决策推迟到真正被依赖的那一刻，并且保证同一个 Bean 只生成一次代理。
追问 · 为什么构造器注入解决不了？构造器注入要求"实例化时就得拿到依赖"，而 A 的实例化本身依赖 B → 形成死锁，Spring 直接抛 BeanCurrentlyInCreationException。prototype 作用域也无解（官方明确不解决）。
踩坑 · 这是送分也是送命题：Spring Boot 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false）。所以正确的收尾是"机制是这么实现的，但生产上应该通过重构（抽公共服务、用 @Lazy）来消除循环依赖，而不是依赖这个兜底"。
Q4@Autowired 和 @Resource 有什么区别？高频
来源
@Autowired 是 Spring 的注解；@Resource 是 JSR-250 标准（JDK 自带，jakarta.annotation）
装配方式
@Autowired 默认 byType，多个候选时配合 @Qualifier 指定名字；@Resource 默认 byName，找不到才 byType
可选性
@Autowired 有 required=false 可允许为空；@Resource 无此属性
适用范围
@Autowired 可用于构造器、方法、字段、参数；@Resource 主要用于字段和方法
实现
@Autowired 由 AutowiredAnnotationBeanPostProcessor 处理；@Resource 由 CommonAnnotationBeanPostProcessor 处理
追问 · @Autowired 注入集合会怎样？会把所有实现类都注入进来（List<XxxService>、Map<String, XxxService>，Map 的 key 是 Bean 名）。这是实现策略模式的常用技巧，主动说出来是加分项。
Q5AOP 有哪两种代理方式？Spring Boot 默认用哪个？必考
JDK 动态代理
Proxy.newProxyInstance，基于接口生成代理类。只能代理接口中声明的方法，目标类必须实现接口。
CGLIB
通过 ASM 生成目标类的子类并覆写方法。无法代理 final 类、final 方法、private 方法（子类看不到）。JDK17+ 上 CGLIB 也需要 --add-opens 处理反射限制。

Spring Boot 2.0 起默认 spring.aop.proxy-target-class=true，即 CGLIB。原因是：避免"注入时用实现类类型、但代理只实现了接口"导致的类型转换异常，开发者也不用被迫写接口。

追问 · 什么情况下 AOP 会失效？① 方法不是 public（默认只拦截 public）；② 自调用（this.xxx() 走的是原始对象）；③ final 方法/类（CGLIB 无法覆写）；④ static 方法；⑤ 对象不是 Spring 管理的（自己 new 出来的）；⑥ 类内部用了 @Transactional 但类本身没被代理。这六条要一口气说出来。
Q6同一个类里方法互相调用，为什么事务/AOP 会失效？怎么解决？必考

根因：AOP 的拦截发生在代理对象上。外部调用 aService.methodA() 走的是代理，代理再转发给目标对象。但目标对象内部执行 this.methodB() 时，this 是原始对象，不经过代理，所以 methodB 上的所有切面（事务、缓存、异步、日志）全部失效。

三种解法：

  1. 注入自己：@Autowired private XxxService self; 然后 self.methodB()。注意：Spring 4.3+ 支持自注入，但会产生循环依赖警告，可用 @Lazy 缓解。
  2. 暴露代理：@EnableAspectJAutoProxy(exposeProxy = true) 后用 AopContext.currentProxy() 调用。不优雅，但不用改结构。
  3. 拆成两个 Bean（最推荐）：把 methodB 挪到另一个 Service 里，由 Spring 自然注入代理。这也是面试官最想听的答案 —— 因为它是"设计问题用设计解决"。
追问 · @Async 也一样吗？完全一样，同一个根因。顺便提一句：@Async 还有另一个坑 —— 它的返回值必须是 void 或 Future/CompletableFuture，返回普通对象拿不到异步结果。
Q7@Transactional 有哪些失效场景？必考

这是必问题，也是最能体现实战经验的题。九种场景：

  1. 方法不是 public（默认只对 public 生效，其余静默失效，不报错）
  2. 自调用（上面 Q6）
  3. 异常被 try-catch 吞掉了，没往外抛
  4. 抛的是受检异常（默认只回滚 RuntimeException 和 Error）→ 必须写 rollbackFor = Exception.class
  5. 在 catch 里 return 了或者重新抛了别的异常类型
  6. 类没被 Spring 管理，或者你拿到的是原始对象不是代理
  7. 传播行为设成了 NOT_SUPPORTED / NEVER
  8. 多数据源没指定事务管理器（@Transactional(transactionManager = "xxx")）
  9. 数据库引擎不支持事务（MyISAM），或者方法里操作的是多个不同的数据源
追问 · 为什么受检异常默认不回滚？Spring 的设计假设是：受检异常属于"可预期的业务异常"，调用方应该处理；而 RuntimeException 属于"程序错误"，应当回滚。这是设计哲学，不是 bug。实际项目里统一写 rollbackFor = Exception.class 更省心。
Q8事务传播行为有哪些？REQUIRES_NEW 和 NESTED 的区别？必考

7 种：REQUIRED（默认，有则加入、无则新建）、REQUIRES_NEW（挂起当前，新建独立事务）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER、NESTED。

面试真正想考的是这两个的区别：

REQUIRES_NEW
开启一个完全独立的新事务（新数据库连接）。内外事务互不影响：外层回滚不影响内层（内层已提交），内层回滚也不影响外层。
NESTED
在同一个事务里打一个 savepoint。内层回滚只回滚到 savepoint，外层不受影响；但外层回滚会连带内层一起回滚。只对 JDBC 数据源生效，且需要数据库支持保存点。
踩坑 · 一定要主动说这个：REQUIRES_NEW 会占用两条数据库连接。如果外层方法在一个大循环里调用 REQUIRES_NEW 方法，或者并发量高，连接池很容易被打满，表现为获取连接超时。这是非常经典的生产事故，主动说出来直接拉高评价。
追问 · 记录操作日志为什么常用 REQUIRES_NEW？因为业务回滚时日志需要保留。但更稳的做法是"日志走异步 + 独立数据源 + 本地消息表"，避免连接占用和日志丢失。
Q9Spring MVC 一次请求的完整流程高频

入口是 DispatcherServlet（前端控制器），核心九步：

  1. 请求到达 DispatcherServlet
  2. HandlerMapping 根据 URL 找到 HandlerExecutionChain（Handler + 拦截器链）
  3. HandlerAdapter 适配调用（RequestMappingHandlerAdapter）
  4. 参数解析：HandlerMethodArgumentResolver 逐个解析方法参数（@RequestParam、@PathVariable、@RequestBody…）
  5. 执行拦截器的 preHandle
  6. 调用 Controller 方法
  7. 返回值处理：HandlerMethodReturnValueHandler。@ResponseBody 走 RequestResponseBodyMethodProcessor → HttpMessageConverter（Jackson）序列化
  8. 非 @ResponseBody 则走 ViewResolver 解析视图并渲染
  9. 拦截器 postHandle → afterCompletion

异常处理：HandlerExceptionResolver，@ControllerAdvice + @ExceptionHandler 就是通过 ExceptionHandlerExceptionResolver 生效的。

追问 · @RequestBody 只能读一次流，为什么？因为 Servlet 的 getInputStream() 只能读一次。AbstractMessageConverterMethodArgumentResolver 会检查 request 是否已经被包装成可重复读（ContentCachingRequestWrapper），没包装就只读一次。这就是"在拦截器里读 body 后 Controller 拿不到参数"的原因，解法是自定义 Filter 包一层 RequestWrapper。
Q10Spring Boot 自动装配的原理必考

@SpringBootApplication = @SpringBootConfiguration + @ComponentScan + @EnableAutoConfiguration。

链路：@EnableAutoConfiguration → @Import(AutoConfigurationImportSelector.class) → 读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Spring Boot 2.7 起；之前是 spring.factories）拿到所有自动配置类的全限定名 → 用 @Conditional 系列注解逐个过滤 → 符合条件的注册为 BeanDefinition。

关键条件注解：@ConditionalOnClass（类路径有才生效）、@ConditionalOnMissingBean（用户没自己定义才生效，这是"用户配置优先"的实现）、@ConditionalOnProperty、@ConditionalOnWebApplication。

追问 · 怎么调试自动装配？启动加 --debug，会打印自动配置报告：Positive matches（生效了）和 Negative matches（为什么没生效）。这是排查"我的配置为什么不生效"最快的方法，说出这个命令说明你真调试过。
追问 · 2.7 为什么换 imports 文件？原来 spring.factories 承载了太多职责（自动配置、监听器、初始化器、环境后置处理器都挤在一起），启动时要全部解析，很多无关类被提前加载。拆出独立的 imports 文件后，职责单一、加载更精准、启动更快。
Q11内嵌 Tomcat 是怎么启动起来的？加分

Spring Boot 不是"打包成 war 丢进外部容器"，而是把容器当普通对象来启动：

  • 应用类型判定为 Servlet → 创建 ServletWebServerApplicationContext
  • refresh() 走到 onRefresh() → 调用 createWebServer()
  • 通过 ServletWebServerFactory（默认 TomcatServletWebServerFactory）创建 Tomcat 实例
  • 把 DispatcherServlet 注册进 ServletContext
  • tomcat.start() 绑定端口，开始接收请求
  • refresh 的 finishRefresh() 启动 LifecycleProcessor，触发 WebServer 完全就绪事件
追问 · 怎么改成部署到外部 Tomcat？主类继承 SpringBootServletInitializer 并覆写 configure()，pom 里把 packaging 改成 war 且 tomcat 依赖 scope 设 provided。知道这个说明你处理过传统企业的部署环境（国企/银行常要求）。
Q12MyBatis 的一级缓存和二级缓存有什么坑？高频

一级缓存（SqlSession 级）：默认开启，同一 SqlSession 内相同 SQL + 参数只查一次数据库。任何 insert/update/delete 都会清空缓存。

二级缓存（namespace 级）：需显式开启（<cache/> 或 @CacheNamespace），跨 SqlSession 共享。

二级缓存的三个坑（这就是面试官要的答案）：

  • 必须提交事务才写入缓存，未提交的查询不进缓存
  • 多表关联时不同 namespace 的缓存不会同步 → 在 A 表改了数据，B 表 namespace 的缓存还是旧的 → 脏读
  • 缓存里存的是对象引用，返回给调用方后被修改，缓存里的值也跟着变了
结论（可以直接当答案收尾）：生产上基本不开二级缓存，需要缓存就用 Redis 自己封装（缓存 key 自己控制、能设 TTL、跨服务共享）。要关的话设 mybatis.configuration.cache-enabled=false。
踩坑：说"一级缓存会导致脏读"是不准确的 —— 一级缓存是 SqlSession 级的，Spring 里一个事务一个 SqlSession，事务内的可见性是符合预期的。真正的风险在跨 SqlSession，也就是二级缓存。
Q13MyBatis 的 #{} 和 ${} 有什么区别？高频
#{}
生成 PreparedStatement 的占位符 ?，参数由 JDBC 做类型处理和转义 → 防 SQL 注入，且能复用执行计划。
${}
字符串直接拼接进 SQL → 有注入风险。

${} 只能用在无法参数化的地方：表名、列名、动态排序字段（ORDER BY）、部分 LIMIT 场景。

追问 · ORDER BY 为什么不能用 #{}？因为预编译后它变成字符串常量，ORDER BY 'create_time' 等价于"按常量排序"，等于没排序。用 ${} 时必须加 Java 侧白名单校验（只允许枚举里的字段名），这是标准答案 —— 光说"用 ${}"会被继续追问注入风险。
追问 · LIKE 怎么写？CONCAT('%', #{keyword}, '%')，不要用 '%${keyword}%'。

Q1为什么 MySQL 索引用 B+ 树？必考

四个理由，按重要性排列：

  • 树矮 → IO 少。B+ 树非叶子节点只存 key 不存数据，一页 16KB 能放约 1170 个 key，三层结构能索引约 2000 万行，查任意一行最多 3 次磁盘 IO。
  • 叶子节点双向链表 → 范围查询快。where id between 100 and 200 只需定位起点然后顺着链表扫，B 树则要中序遍历回溯。
  • 查询性能稳定。所有数据都在叶子层，每次查询的 IO 次数一致。
  • 天然有序 → 支持排序和分组，也能做最左前缀匹配。
对比记忆（一句话一个）：B 树每个节点都存数据 → 同样页大小装的 key 更少 → 树更高；哈希索引不支持范围查询和排序，且哈希冲突后要遍历链表；红黑树/AVL 是二叉树，千万级数据高度 20+ 层 → IO 次数不可接受（放内存里才合适，比如 Java 的 TreeMap）；跳表在内存里表现好，磁盘上不如 B+ 树。
Q2什么是回表？覆盖索引怎么优化？必考

聚簇索引（主键索引）：叶子节点存放整行数据。二级索引（辅助索引）：叶子节点存放主键值。

所以通过二级索引查询非索引列时，要先在二级索引上找到主键，再回到聚簇索引取整行 —— 这就是回表，多一次（或多次）IO。

覆盖索引：查询涉及的所有列都在索引里，不需要回表。判断依据是 explain 的 Extra 显示 Using index。

优化手段（按收益排序）：① 把高频查询的列加进联合索引，做成覆盖索引；② 避免 select *（只取需要的列，才有可能覆盖）；③ 主键用自增（避免页分裂和碎片）；④ 用延迟关联（先用覆盖索引查主键，再 join 回原表）优化深分页。
踩坑：联合索引不是列越多越好 —— 每多一列，索引文件更大、写操作更慢。该说"按查询模式来定，而不是全塞进去"。
Q3联合索引的最左前缀原则，范围查询为什么会中断？必考

联合索引 (a, b, c) 在存储上先按 a 排序，a 相同再按 b，b 相同再按 c。所以它等价于多了 (a)、(a,b)、(a,b,c) 三个索引。

  • where a=1 ✓ 用到 a
  • where a=1 and b=2 ✓ 用到 a、b
  • where a=1 and c=3 △ 只用到 a，c 只能作为过滤条件（走索引下推在引擎层过滤）
  • where a=1 and b>2 and c=3 △ b 是范围 → 后面的 c 无法用于定位，只能过滤
  • where b=2 and c=3 ✗ 完全用不到

为什么范围会中断：b 是一个区间时，区间内的 b 值对应的 c 并不是全局有序的，无法用有序性做定位。

追问 · 索引下推（ICP）是什么？MySQL 5.6 引入。没有 ICP 时，存储引擎按索引找到记录后回表，再由 Server 层过滤；有 ICP 时，把能在索引上判断的条件下推到引擎层先过滤，减少回表次数。Extra 显示 Using index condition。这是"范围后面的列并非完全没用"的准确说法 —— 它不能定位，但能过滤。
Q4哪些情况会导致索引失效？必考
  1. 在索引列上做函数运算：where date(create_time) = '2026-01-01'、where id + 1 = 5。改写为范围查询：where create_time >= ... and create_time < ...
  2. 隐式类型转换：字段是 varchar 却传数字 where phone = 13800000000 → 相当于 CAST(phone AS signed) = ... → 索引失效。这是生产上最高频的坑。
  3. 前导模糊匹配：like '%abc' 无法用索引（like 'abc%' 可以）
  4. OR 两侧有一侧没索引：整个查询退化为全表扫描
  5. 不满足最左前缀
  6. !=、not in、is not null（可能失效，取决于优化器对回表成本的估算）
  7. order by / group by 的列与 where 用的索引不一致 → 产生 Using filesort / Using temporary
  8. 统计信息不准导致优化器选错索引 → ANALYZE TABLE 或临时 FORCE INDEX
  9. 索引列区分度太低（如性别、状态只有 0/1），优化器认为全表扫描更快
追问 · 隐式转换的方向为什么很重要？varchar 列比较数字时，MySQL 会把列转成数字（因为数字精度更高），于是每行都要转换，无法用索引。反之，数字列传字符串则会转常量，索引依然可用。结论：让列保持干净，类型要匹配。
Q5explain 你主要看哪些字段？高频
type
访问类型，从好到坏：system > const > eq_ref > ref > range > index > ALL。生产要求至少到 range，看到 ALL（全表）或 index（全索引扫描，依然是扫全表）就要优化。
key
实际使用的索引。如果是 NULL 说明没用上。
possible_keys
理论上可用的索引。若它有值但 key 为 NULL → 优化器选择了不用（可能是区分度低或统计信息不准）。
key_len
实际使用的索引长度，可以推算联合索引用到了几列。
rows
预估扫描行数。是估算值，但量级很有参考价值。
filtered
按条件过滤后剩余行数百分比，越低说明条件过滤性越差。
Extra
信息量最大的字段。重点关注：Using index（好，覆盖索引）、Using index condition（索引下推）、Using filesort（需优化排序）、Using temporary（需优化分组）、Using join buffer（被驱动表没索引）。
实战用法：先用 explain 看执行计划，再用 explain analyze（MySQL 8.0.18+）看实际耗时和预估的差异 —— 如果实际行数远大于预估，通常是统计信息过期或字段区分度估算错误，这时 ANALYZE TABLE 往往能解决。
Q6MVCC 是怎么实现的？RR 和 RC 的 ReadView 有什么区别？必考

基础结构：InnoDB 每行有隐藏列 —— DB_TRX_ID（最近修改它的事务 ID）、DB_ROLL_PTR（指向 undo log 的回滚指针）。

版本链：每次修改都把旧版本写进 undo log 并用回滚指针串起来，形成一条版本链。

ReadView 四个字段：m_ids（生成时活跃的事务 ID 列表）、min_trx_id、max_trx_id、creator_trx_id。

可见性判断：沿版本链找第一个"可见"的版本 —— 版本的 trx_id 小于 min 则可见；大于等于 max 则不可见；在中间则看是否在 m_ids 里（在 = 还活跃 = 不可见）。

RC（读已提交）
每次 select 都生成新的 ReadView → 能看到别人已提交的最新数据
RR（可重复读，默认）
第一次 select 生成并复用 → 整个事务看到的快照不变，实现可重复读
必须补的一句（决定分数高低）：RR 下 MVCC 只解决快照读的幻读；当前读（select ... for update、update、delete）读的是最新数据，幻读要靠间隙锁 / 临键锁来防。所以"RR 完全解决幻读"是错误说法。
追问 · 为什么 RR 是默认隔离级别？主要是历史原因：早期 binlog 默认是 STATEMENT 格式，RC 下会导致主从数据不一致（同一语句在主从库执行时读到的快照不同）。现代生产很多团队会改成 RC（减少间隙锁、提升并发），前提是 binlog 用 ROW 格式 —— 说出这一点非常加分。
Q7MySQL 有哪些锁？间隙锁解决什么问题？必考

按粒度：全局锁（FLUSH TABLES WITH READ LOCK，用于全库备份）、表锁（表级共享/排他、元数据锁 MDL）、行锁。

InnoDB 三种行锁：

  • Record Lock（记录锁）：锁住具体的一行
  • Gap Lock（间隙锁）：锁住开区间，比如 (5, 10)，目的是阻止其他事务在这个区间插入
  • Next-Key Lock（临键锁）：记录锁 + 该记录之前的间隙，左开右闭，如 (5, 10]。RR 下默认加的就是这个

间隙锁解决幻读：当前读时，只锁住已有的行无法阻止别人插入新行（即幻读），加间隙锁后插入会被阻塞。

关键细节：唯一索引等值命中时，Next-Key Lock 会退化成 Record Lock（因为唯一索引等值最多一行，不需要防插入）；非唯一索引或没命中唯一索引时才会加间隙锁。这就是"为什么用主键查不会锁一片"的原因。
追问 · 死锁怎么排查和预防？InnoDB 会自动检测死锁并回滚代价小的事务；SHOW ENGINE INNODB STATUS 能看到最近一次死锁的详细信息（两个事务各持什么锁、在等什么）。预防：① 按固定顺序访问多行/多表；② 缩短事务，避免事务里做 RPC；③ update 一定要走索引（没走索引会锁全表 → 极易死锁）；④ 用低隔离级别减少间隙锁。
踩坑：MDL（元数据锁）是很多"线上突然全阻塞"的元凶 —— 一个长事务持有 MDL，后续的 DDL 排队，而 DDL 排队会阻塞后面所有的 DML。所以 DDL 要避开业务高峰，且前面不要有长事务。
Q8一条 update 语句的执行流程？redo log 和 binlog 怎么保持一致？高频
  1. 执行器取到要改的行（从 Buffer Pool 内存中，没有则从磁盘读入）
  2. 把旧值写入 undo log（用于回滚和 MVCC）
  3. 修改内存中的页，把新值写入 redo log，状态标记为 prepare
  4. 写完 redo log 后、提交前，写入 binlog
  5. 提交事务，把 redo log 的状态改为 commit

这就是两阶段提交（2PC），目的是让 redo log 和 binlog 逻辑一致。

崩溃恢复规则：redo log 是 prepare 状态时，检查对应事务的 binlog 是否完整 —— 完整则提交，不完整则回滚。这样能保证"主库恢复后的数据"和"从库重放 binlog 后的数据"一致。

追问 · 两种日志的作用区别？redo log 是 InnoDB 层的物理逻辑日志，循环写（固定大小，写满就覆盖最旧的），保证崩溃恢复不丢数据（WAL 机制：先写日志再刷盘）。binlog 是 Server 层的逻辑日志，追加写（不覆盖），用于主从复制和基于时间点的数据恢复。
追问 · 为什么 redo log 循环写用完了会卡住？因为要等 checkpoint 推进（把脏页刷盘）才能覆盖。如果出现"脏页刷盘跟不上 redo 写入速度"，就会看到 InnoDB: Cannot allocate memory for the buffer pool 或写请求变慢 —— 调大 innodb_log_file_size 或提升磁盘 IO 能力。
Q9分库分表怎么做？分片键怎么选？加分

顺序：先垂直拆分（按业务拆库、拆大字段），再水平拆分（按分片键把同一张表拆到多个库/表）。不要一上来就水平拆。

分片键选择四原则：

  1. 查询必带：最核心的查询条件必须包含它，否则要路由到所有分片（全路由），等于白拆
  2. 分布均匀：避免数据倾斜
  3. 避免热点：不要用时间做哈希键（大促当天的数据全落一个分片）
  4. 高基数：取值足够多

举例：订单表按 buyer_id 分片 —— 保证"我的订单"这类高频查询能精确路由，同时同一买家的数据落同一分片。

分片后必须解决的四个问题：

  • 跨库 join → 冗余字段（下单时把商品名存进订单）、或者异构索引表（binlog 订阅同步到 ES）
  • 跨库分页 → 内存归并排序（深分页性能差）、或二次查询法（先在各分片取 offset/N 条，拿到最小时间戳，再回各分片查该时间戳之后的数据）
  • 全局唯一 ID → 雪花算法 / 号段模式
  • 扩容 → 一致性哈希，或双写迁移（新老双写 → 校验 → 切读 → 停旧写）
中间件：ShardingSphere（推荐，生态好）、MyCat。也可以应用层自己做（可控性最强，但工作量大）。面试时说"能不分就不分，分表优先于分库，垂直优先于水平"是很好的收尾。
Q10Redis 的持久化机制？RDB 和 AOF 怎么选？高频
RDB
某一时刻的全量快照。fork 子进程 + 写时复制（COW）。文件小、恢复快；缺点是会丢最后一次快照之后的数据。
AOF
追加写命令。三种刷盘策略：always（每条都刷，最安全最慢）、everysec（每秒刷，默认，最多丢 1 秒）、no（交给操作系统）。
AOF 重写
fork 子进程按当前内存状态生成"最小命令集"。重写期间主进程的新命令写入 AOF 重写缓冲区，重写完成后追加进去。
混合持久化
Redis 4.0+ 的 aof-use-rdb-preamble：AOF 文件前半是 RDB 格式（恢复快），后半是增量命令（丢得少）。生产推荐开启。

选型：纯缓存（数据可重建）→ 可以都不开或只开 RDB；有业务数据 → 混合持久化；极致安全（如金融流水）→ AOF always（但性能会掉很多，通常还是选 everysec + 业务侧对账）。

追问 · fork 有什么代价？① fork 本身要拷贝页表，内存越大阻塞越久（10G 内存可能阻塞几十到几百毫秒）；② COW 期间如果写入量大，内存占用可能接近翻倍（要留足余量，通常建议 Redis 内存不超过物理内存的 50-60%）；③ 主从全量同步也走 fork。所以 Redis 单实例不要放太大。
Q11缓存穿透、击穿、雪崩分别怎么解决？必考
问题场景方案

击穿 单个热点 key 过期瞬间，大量请求同时打到 DB ① 互斥锁 / 单飞重建（只放一个请求去查 DB，其余等待）② 逻辑过期（不设 TTL，value 里带过期时间，异步刷新）③ 热点 key 永不过期 + 后台定时更新
雪崩 大量 key 同时过期，或 Redis 集群宕机 ① 过期时间加随机值（打散）② 多级缓存（Caffeine 本地 + Redis）③ 熔断降级（Sentinel）④ Redis 高可用（哨兵 / Cluster）⑤ 缓存预热
追问 · 布隆过滤器的缺点？① 有误判：说"可能存在"但实际不存在（不会漏判）；② 不支持删除（因为 hash 位是共享的，删一个会影响别的）—— 需要删除就用 Counting Bloom Filter 或 Redis 的 bitmap 自己维护计数；③ 需要预估数据量来定 bitmap 大小，扩容要重建。
追问 · "互斥锁重建"和"逻辑过期"怎么选？互斥锁保证强一致但会阻塞请求（等待期间 RT 变长）；逻辑过期不阻塞、可用性高，但会短暂返回旧数据（最终一致）。热点商品详情这类可以接受短暂旧数据的场景，逻辑过期更好。
Q12怎么保证缓存和数据库的一致性？必考

先说结论（这句话本身就是答案的一半）：缓存与数据库只能做到最终一致，关键是评估业务能容忍多久的不一致，以及不一致时会不会造成资损。

方案演进：

  1. 先更新 DB 再删除缓存（Cache Aside 的标准做法）—— 并发窗口很小但存在：读请求在更新前读到旧值、在更新后把旧值写回缓存。
  2. 延迟双删：更新前删一次、更新后延迟几百毫秒再删一次。延迟是为了覆盖"读线程读到旧值但还没来得及写回"的窗口。缺点：延迟时间靠猜。
  3. 订阅 binlog（Canal）异步删缓存 —— 最推荐。业务无侵入，不依赖业务代码的正确性，天然覆盖所有写路径（包括手工改库、其它服务写入）。代价是引入 Canal 组件和轻微延迟。
  4. 强一致：只能靠分布式锁或读写走同一把锁，代价是性能大幅下降 —— 大部分业务不值得。
必须避开的错误答案："更新数据库的同时更新缓存"。并发下两次写的顺序不可控（A 先改 DB、B 后改 DB，但 B 先写缓存 → 缓存里是 A 的值），而且如果更新时算出的值不是最终值，还会留下永远不会被纠正的脏数据。"删除"比"更新"安全，因为删除是幂等的。
追问 · 先删缓存再更新 DB 行不行？更危险。删完缓存后、DB 还没更新时，另一个读请求会把旧值读出来写回缓存 → 缓存里长期是旧值。所以标准顺序是"先更新 DB，再删缓存"。
Q13Redis 分布式锁怎么实现？Redisson 的看门狗是什么？必考

标准实现要素（缺一不可）：

  1. 原子加锁：SET lock_key unique_value NX PX 30000。必须用这一步原子完成，不能 SETNX 后再 EXPIRE（中间宕机就死锁）。
  2. value 存持有者标识（UUID + threadId）：释放时校验，避免删掉"别人已超时后重新获取的锁"。
  3. Lua 脚本原子释放：先 get 比对再 del，两步必须原子。
  4. 续期机制：业务执行时间超过锁 TTL 就失去锁 → 需要续期。

Redisson 看门狗（watchdog）：不指定 leaseTime 时（默认 -1），Redisson 会启动一个后台任务，每 lockWatchdogTimeout/3（默认 30s/3 = 10s）续期一次到 30s，直到 unlock() 停止。如果显式指定了 leaseTime，看门狗不生效 —— 这是个常见误区。

Redisson 还支持可重入：内部用 Hash 结构，key 是锁名，field 是"线程标识"，value 是重入次数。

追问 · 主从架构下 Redis 锁会丢吗？会。主节点写入锁后、还没同步到从节点就宕机 → 从节点晋升 → 锁丢失 → 另一个客户端也能获取。这是异步复制的固有问题。
解法：① RedLock（向多数独立节点加锁）—— 但 Martin Kleppmann 认为它依赖系统时钟和 GC 停顿，安全性证明不成立，Antirez 反驳过，面试可以说"业界有争议，我们不依赖它保证绝对安全"；② 更务实的做法是加一层业务幂等兜底（唯一索引 / 状态机），让"锁失效"不至于造成资损。这就是"分布式锁解决性能问题、幂等解决正确性问题"的分工。
Q14大 key 和热 key 怎么发现和处理？高频
大 key
String 类型 value 超过 10KB，或集合类型元素超过 5000 个。
危害
网络传输阻塞（单线程模型）、删除时阻塞（del 是 O(n)）、Cluster 下数据倾斜（一个 key 只能落一个节点）、慢查询。
发现
redis-cli --bigkeys（采样扫描）、MEMORY USAGE key、RDB 离线分析（rdb-tools）、云厂商的 DAS 巡检。
处理
① String 大 value 拆成多个 key（哈希分桶）；② 集合类型按 hash 拆成多个子 key（如 user:hash:{id%10}）；③ 压缩后再存；④ 用 unlink 替代 del 异步删除。
热 key
某个 key 的 QPS 远超其它（如大促爆款商品、明星热搜）。危害是单节点 CPU 打满、Cluster 倾斜。
发现
redis-cli --hotkeys（需 LFU 淘汰策略）、MONITOR（慎用，会严重拖慢）、客户端 SDK 本地统计、京东 hotkey 中间件。
处理
① 本地缓存多级（Caffeine 挡住绝大部分读）；② key 加随机后缀打散到多个节点（读时合并，写时要写多份）；③ 读写分离 / 集群扩容；④ 热点 key 预加载到本地。
追问 · 怎么预防而不是事后治？① 写入前校验 value 大小，超阈值拒绝并告警；② 集合类型用 hscan 而不是 hgetall；③ 上线前做一次大 key 巡检并纳入 CI；④ 监控 latency，慢查询超阈值告警。
Q15怎么保证消息不丢？MQ 怎么保证幂等？必考

可靠性三段论（按链路顺序答，面试官要的就是这个结构）：

环节风险方案
生产端发送失败 / 结果未知① 同步发送并检查 SendResult；② 失败重试（含本地重试表）；③ 本地消息表 + 定时补偿（最可靠）；④ RocketMQ 事务消息
Broker宕机导致内存消息丢失RocketMQ：SYNC_FLUSH 同步刷盘 + SYNC_MASTER 主从同步复制；Kafka：acks=all + replication.factor>=3 + min.insync.replicas>=2 + unclean.leader.election=false
消费端处理失败但 offset 已提交① 关闭自动提交，业务处理成功后手动 ack；② 失败进重试队列 → 超过次数进死信队列；③ 死信人工/定时补偿

幂等（核心：MQ 只能保证 at-least-once，exactly-once 必须业务侧做）：

  1. 数据库唯一索引（业务幂等键，如订单号 + 操作类型）—— 最可靠，兜底方案
  2. Redis SETNX 记录消息 ID（注意：SETNX 和业务操作不在一个原子操作里，仍可能重复，所以仍要唯一索引兜底）
  3. 状态机 + 条件更新：update order set status=2 where id=? and status=1，看 affected rows
  4. 版本号乐观锁
加分收尾：MQ 侧的去重表 + DB 唯一索引兜底是标准组合，两者互补 —— 前者挡住绝大部分重复（避免打 DB），后者保证绝对不出错。
RocketMQ 自带的 MessageId 去重不可靠（重投时 MessageId 会变），要用业务唯一键自己构造。
Q16消息积压了几百万条，你怎么处理？高频

第一步一定是定位原因，不是急着扩容：

  • 消费太慢：下游 DB 慢查询、RPC 超时、消费线程里有重活（大对象、循环调接口）
  • 生产突增：大促流量、上游重试风暴（比如下游报错引发大量重试）
  • 消费者挂了 / 消费线程卡死：看消费位点和实例存活

处理手段（按见效速度排序）：

  1. 临时扩消费者实例 —— 但关键点：消费者数不能超过队列数（RocketMQ）/ 分区数（Kafka），否则多出来的实例抢不到队列，扩了也没用。所以如果需要扩更多，得先临时扩队列/分区。
  2. 提高单机消费能力：增大批量消费条数、提高消费线程数、减少单条消息的处理耗时。
  3. 降级处理：把非核心逻辑去掉（比如只落库、不实时发通知），或把消息转存到一个临时 Topic，先消费掉积压，再慢慢处理临时 Topic。
  4. 丢弃非核心消息：如果业务允许（比如统计类、日志类消息），直接快进 offset 丢掉。
  5. 处理死信/重试队列：积压往往集中在重试队列里，要单独处理。

根因治理：慢 SQL 加索引、RPC 加超时和熔断、消费线程里禁止做重活。

预防措施（主动说，体现体系感）：① 监控消费延迟（不只是队列长度，而是最新 offset 与消费 offset 的差值）并设告警；② 消费端要有背压/限流；③ 生产端做削峰（令牌桶）；④ 大促前压测消费能力并留出 3 倍余量。
踩坑：只说"加机器扩容"会被追问"队列数够不够" —— 这个细节是区分"背过答案"和"真处理过"的分水岭。

Q1谈谈你对 CAP 的理解？为什么不能同时满足三个？高频

Consistency 一致性、Availability 可用性、Partition tolerance 分区容错性。

为什么不能同时满足：分布式系统里网络分区（节点之间失去通信）是必然会发生的客观事实，所以 P 必须保留。当分区真的发生时，你只能二选一 —— 要么拒绝服务保证一致性（CP），要么继续服务但允许数据不一致（AP）。

归类：

  • CP：ZooKeeper（leader 选举期间整个集群不可用；写要过半 ack）、etcd、HBase
  • AP：Eureka、Nacos（AP 模式）、Cassandra、Redis Cluster（主从异步复制）
  • Nacos / Redis 属于可配置或场景相关，不要绝对化
高分回答（一定要补这一段）：CAP 不是非黑即白的投票，而是"在什么时间窗口内、对哪些数据、在一致性和可用性之间怎么取舍"的工程决策。同一个系统里不同模块可以有不同选择 —— 交易核心走 CP（宁可失败也不能算错钱），商品列表/推荐走 AP（宁可短暂旧数据也要可用）。
追问 · BASE 是什么？Basically Available（基本可用：降级、限流而不是完全不可用）+ Soft state（软状态：允许中间态）+ Eventually consistent（最终一致）。它是 AP 的工程化补充，告诉你"放弃强一致之后怎么做"。

选型原则（这是考官想听的）：
① 能不用就不用：先反问"能不能通过重新划分服务边界，把强一致需求收敛到单个数据库事务里" —— 这是最优解。
② 必须跨服务时，优先"最终一致 + 幂等 + 定时对账"，而不是上 2PC。
③ 只有资金类、且中间态不可接受时，才上 TCC。
④ 对账是最后一道防线 —— 任何最终一致方案都必须配一个对账任务，这体现你有兜底思维。

Q3TCC 的空回滚、幂等、悬挂分别怎么解决？高频

三个异常的共同解法都是一张事务控制表（事务 ID 唯一索引 + 状态字段）。

空回滚
问题：Try 还没执行（超时/网络问题），Cancel 先到了，如果不加判断就去回滚，会回滚掉根本没扣的资源（或者把别人的扣减反向加了）。
解法：Cancel 里先查事务控制表，没有 Try 记录就直接标记为"已回滚"并返回成功，不执行真正的回滚逻辑。
幂等
问题：Confirm / Cancel 可能被重复调用（网络重试、事务协调器重发）。
解法：事务控制表加状态机，用唯一索引防重。状态已是"已提交/已回滚"就直接返回成功，不再执行业务逻辑。
悬挂
问题：Cancel 比 Try 先到，Cancel 执行完后 Try 才成功 —— 资源被扣了，但回滚已经做过了，永远没人再回滚它，资源被永久占用。
解法：Try 执行前先查事务控制表，如果发现已有"已回滚"记录，直接拒绝执行 Try（返回失败或抛出异常）。
一句话总结（可以当收尾）：三个问题的本质都是"消息乱序 + 重复投递"，所以解法都是同一套：状态机 + 唯一索引 + 执行前校验。理解了这个，就不用死记三个名词。
Q4分布式 ID 有哪些方案？雪花算法的时钟回拨怎么处理？必考
方案优点缺点
UUID本地生成、无依赖无序 → 做 MySQL 主键会引发页分裂和碎片；占 36 字符

雪花算法结构（64 bit）：1 位符号（固定 0）+ 41 位时间戳（毫秒，约 69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（同一毫秒内最多 4096 个）。

时钟回拨的四种处理：

  1. 小幅回拨等一等：回拨小于阈值（如 5ms）就自旋等待时钟追上
  2. 大幅回拨直接拒绝：抛异常+告警，等运维处理（避免生成重复 ID）
  3. 备用位补偿：用扩展位记录"上一毫秒已用序列号"，回拨时从上次的序列继续递增
  4. Leaf 的做法：用 ZooKeeper 分配 workerId 并周期性上报时间戳；启动时若发现本机时间小于上次上报时间，判断是回拨并处理
追问 · 为什么很多业务 ID 不适合直接用自增主键？① 会泄露业务量（竞争对手看到订单号就知道你的日订单量）；② 分库分表后需要全局唯一；③ 敏感场景可以被遍历。所以常见做法是"内部主键用自增，对外暴露的业务号用雪花/号段生成的独立字段" —— 这就是数据库设计里的"业务键 + 技术键分离"。
Q5如何设计一个幂等接口？必考

幂等的本质：同一个请求执行多次，对系统状态的影响与执行一次相同。关键前提是"能唯一标识一次业务请求" —— 有的场景靠客户端传的幂等键，有的靠业务字段组合。

分层设计（从外到内，越靠内越可靠）：

  1. 前端：按钮置灰 / 防抖，只是体验优化，不能算幂等方案
  2. 网关层 token 机制：先申请一次性 token，提交时带上，服务端删除 token 成功才处理（DEL 返回 1 才继续）。防重复提交，但无法防"网络重试"
  3. 分布式锁：SETNX 业务键，处理完释放。缺点是锁失效或宕机后不可控
  4. 状态机 + 条件更新：update order set status=2 where id=? and status=1，判断 affected rows 是否为 1。适合状态流转类
  5. 去重表：独立表存"请求 ID"，唯一索引保证只插入一次
  6. 业务唯一索引（最终兜底，最可靠）：如 uk(order_no, operation_type)。数据库层面原子保证，即使前面全失效也不会重复
追问 · 为什么唯一索引是最可靠的？因为其它方案都是"先查后写"的两步操作，并发下有竞态窗口；唯一索引把判断和写入合并成一个原子操作，由数据库保证。所以工程上的标准做法是：能加唯一索引就一定加，其它方案用来减少无效请求、保护数据库。
追问 · 幂等键怎么设计？要满足"同一业务意图 → 同一键，不同业务意图 → 不同键"。常见：外部传入的 requestId、业务唯一号（订单号）、或 业务ID + 操作类型 + 版本。要注意别把时间戳放进去（否则每次请求键都不同，幂等失效）。
Q6限流的常见算法？令牌桶和漏桶有什么区别？必考
算法原理特点
固定窗口计数每 1 秒一个计数器，超阈值拒绝简单，但有临界问题（0:59 的 100 次 + 1:00 的 100 次 = 1 秒内 200 次）
滑动窗口把时间切成小格，滚动统计解决临界问题；格子越细越精确，内存开销越大。Sentinel 用它
漏桶请求先进桶，以固定速率流出，桶满丢弃强制平滑输出，不允许突发。适合保护脆弱的下游
令牌桶以固定速率往桶里放令牌，桶满则丢令牌；请求拿到令牌才能通过允许突发（桶里攒了令牌时可以一次性消费）。Guava RateLimiter、Sentinel 的默认效果
一句话区分（面试就答这句）：漏桶约束"流出速率"，令牌桶约束"平均速率、允许突发"。实际系统里更常用令牌桶，因为真实流量本来就是有突发的，一味削平会误伤正常用户。
追问 · 分布式限流怎么做？① Redis + Lua（原子性），注意 key 分片和 Redis 本身成为瓶颈；② 网关层统一限流（Nginx 的 limit_req 是漏桶、limit_conn 限制连接数；Sentinel 集群流控模式）；③ 单机限流 + 按实例数均分总阈值（简单但实例数变化时要重算）；④ Sentinel 的集群流控（有独立的 token server，解决了"总阈值怎么分摊"的问题）。
踩坑：别忘了限流要"分层" —— 网关限流挡恶意流量、应用限流保护自身、依赖调用限流保护下游、DB 连接池本身也是一层限流。说"限流是分层设计，不是单点配置"，立刻显得有体系。
Q7熔断和降级的区别？Sentinel 怎么做？必考
降级
主动放弃非核心功能，保证核心链路可用。例如双 11 关闭"商品评价"、"猜你喜欢"；库存查询失败时返回缓存值或"稍后重试"。触发方式：人工开关（大促前预演）、或自动（异常比例/RT 超阈值）。
熔断
被动保护。当依赖的下游服务错误率/慢调用比例超过阈值，直接"跳闸"—— 后续请求快速失败，不再打过去，给下游恢复时间。经过一段时间后进入半开状态，放少量请求试探，成功则恢复。

三态：Closed（正常）→ Open（熔断，直接拒绝）→ Half-Open（试探）→ 成功回 Closed / 失败回 Open。

Sentinel 的规则类型：流控规则（QPS/线程数 + 快速失败 / Warm Up 预热 / 排队等待）、熔断降级规则（慢调用比例 / 异常比例 / 异常数）、系统自适应保护（按 load、RT、线程数、入口 QPS 整体保护）、热点参数限流。

Sentinel vs Hystrix（会被追问）：Hystrix 用线程池隔离（资源开销大、线程切换成本高，已停止维护）；Sentinel 用信号量 + 滑动窗口统计，更轻量，且支持热点参数、系统自适应、集群流控。功能上 Sentinel 更全，性能更好。
追问 · @SentinelResource 的 blockHandler 和 fallback 有什么区别？blockHandler 处理规则触发（限流、熔断、系统保护）的兜底；fallback 处理业务异常的兜底。弄混这两个是很常见的失分点，两个同时配时，规则触发的走 blockHandler。

Q9一致性哈希的原理？为什么需要虚拟节点？加分

问题背景：普通哈希取模 hash(key) % N —— 只要节点数 N 变化，几乎所有 key 的归属都会改变，缓存大规模失效、数据需要全量迁移。

一致性哈希：把 0 ~ 2^32-1 组成一个环，节点和 key 都哈希到环上，key 顺时针找到第一个节点。节点增减时，只影响相邻区间的数据（平均只迁移 1/N）。

虚拟节点解决的问题：节点少时，哈希到环上的位置可能很集中，导致数据分布严重不均（某个节点承担 80% 的流量）。解法是每个物理节点映射成 N 个虚拟节点（N 通常 100-200）散布到环上，让分布趋于均匀。同时虚拟节点也让"性能不同的机器分配不同数量的虚拟节点"成为可能。

追问 · Redis Cluster 用一致性哈希吗？不用。Redis Cluster 用 16384 个 hash slot：CRC16(key) % 16384 决定 key 属于哪个槽，槽再分配给节点。
为什么不用一致性哈希：① 槽的映射是显式且可控的，便于精确迁移（CLUSTER SETSLOT）和 resharding；② 迁移粒度更细（可以按槽迁移单个 key）；③ 支持 hash tag（{user1}:a 和 {user1}:b 会落同一个槽，方便做多 key 操作）。说出 hash tag 是很强的加分项。
Q10设计一个秒杀系统（重点：防超卖、限流、削峰）必考

开口先做估算（这一步就能拉开差距）：假设 100 万人抢 1 万件商品，峰值 QPS 可能到 10 万级 —— 这个量级下单靠数据库是撑不住的，必须层层削峰。

分层设计（按流量经过的顺序）：

  1. 前端/客户端：按钮置灰、验证码/答题防脚本、页面静态化 + CDN、限流降级开关（大促前可预演）
  2. 接入层：Nginx 限流（limit_req / limit_conn）、IP 黑名单、Sentinel 热点参数限流（按活动 ID / 用户 ID 限）
  3. 服务层隔离：秒杀独立服务 + 独立线程池/集群隔离，避免把主站拖垮（这是"隔离"思想的体现）
  4. 库存层（核心）：活动开始前把库存预热到 Redis，用 Lua 脚本原子扣减（判断 + 扣减一步完成）。Redis 直接挡掉 99% 的流量
  5. 异步下单：扣减成功 → 发消息到 MQ → 订单服务串行/异步消费落库。接口立刻返回"排队中"，前端轮询结果
  6. 数据库兜底：update stock set count = count - 1 where id = ? and count > 0，判断 affected rows；订单表加 uk(user_id, activity_id) 防一人多单
  7. 结果反馈：轮询 or 长连接推送；返回"秒杀成功/已抢完/排队中"三种状态
追问 · 防超卖有哪几层？① Redis Lua 原子扣减（挡在入口，防超量）② MQ 串行化（同一商品的扣减消息进同一队列，天然串行）③ DB 条件更新 + 乐观锁（最终兜底）④ 对账任务（事后发现 Redis 和 DB 不一致就修复，并告警）。一定要说到第 ④ 层 —— 说明你知道任何方案都可能出错，必须有兜底。
追问 · 一人一单怎么保证？Redis 里用 SADD activity:{id}:users user_id 判断是否已参与（原子），DB 侧用唯一索引 uk(activity_id, user_id) 兜底。
追问 · 用户秒杀成功后不付款怎么办？超时关单（延迟消息）+ 库存回补（INCR Redis + DB 加回），回补时要用状态机保证不重复回补。
Q11如何防止库存超卖？必考

四种方案（说全 + 说清取舍）：

方案做法取舍
Redis 预扣减 + Luaif stock > 0 then decr; return 1 else return 0 end，脚本内判断+扣减原子完成性能最高，适合高并发。代价是要处理"Redis 与 DB 的一致性"和宕机丢数据
DB 悲观锁select ... for update 锁住行再判断绝对不超卖，但串行化严重，不适合高并发
DB 乐观锁update ... set count=count-1, version=version+1 where id=? and version=?无锁等待，但失败要重试；版本号方案在高冲突下重试率极高
DB 条件更新update ... set count=count-1 where id=? and count>0，看 affected rows不需要版本号，一条语句搞定，冲突下只是返回 0 行。实用、最常用

库存分段（进阶优化）：把 1000 件库存拆成 10 段，每段 100，不同请求落到不同段用不同的锁 → 把串行化打散成并行，并发度提升 10 倍。代价是可能出现"某段有剩余但整体显示售罄"，需要做段间调剂。

生产级组合（面试就答这个）：Redis Lua 挡在入口 → MQ 串行化 → DB 条件更新兜底 → 每日对账修复。四层各司其职：性能、顺序、正确性、最终一致。
踩坑：select 查库存再 update 是两个操作，中间有竞态窗口，必然超卖。这是新人最常见的错误，被问到要能立刻指出问题。
Q12设计一个短链系统加分

① 短码生成：

  • 发号器方案（推荐）：全局唯一 ID（雪花 / 号段）→ 转 62 进制。6 位 62 进制 = 568 亿种组合，足够用。优点：无冲突、可控、可预测长度。
  • 哈希方案：MurmurHash → 取模。缺点：有冲突要额外处理，且长度不可控。

② 存储：MySQL 存 (id, short_code, long_url, expire_time, creator, created_at)，short_code 建唯一索引。

③ 读路径（性能关键）：

  • 一级：Caffeine 本地缓存（抗住超热点）
  • 二级：Redis 缓存 short_code → long_url
  • 三级：MySQL
  • 布隆过滤器前置，挡住"不存在的短码"造成的缓存穿透

④ 重定向方式：

  • 302 临时重定向（推荐）：每次请求都到服务器，可以统计点击量
  • 301 永久重定向：浏览器会缓存，性能好但统计不准、也没法做失效控制
追问 · 怎么防止被别人遍历爬取所有链接？① 短码不连续（发号器加随机盐或使用非递增的映射）；② 对同一来源限流；③ 敏感链接单独做鉴权（需要登录态才能跳转）；④ 短链有效期 + 访问日志告警。
追问 · 发号器会成为瓶颈吗？会。优化：预生成一批短码放到内存池（业务侧批量取），或号段模式一次取 1000 个；发号器服务本身多实例 + 分段（每个实例负责一段 ID 空间）。
Q13设计一个订单系统加分

① 状态机是核心：待支付 → 已支付 → 待发货 → 已发货 → 已完成 / 已取消 / 退款中。
所有状态流转都必须用条件更新收口：update order set status = 新状态 where id = ? and status = 期望的旧状态，affected rows = 0 说明并发冲突或状态不合法。这一条同时解决了幂等和并发问题，是订单系统的基石。

② 幂等：外部订单号 + 唯一索引；支付回调按支付流水号做幂等（回调可能重复推送）。

③ 超时关单：延迟消息（RocketMQ 延迟消息 / RabbitMQ 死信队列 / Redis ZSet 轮询 / 定时任务扫表）。关闭时用状态机保证不会关掉已经支付的单（这是关键冲突点）。

④ 分库分表：按 buyer_id 分片（保证"我的订单"高频查询精确路由）。卖家维度用异构索引表（订阅 binlog → 同步到 ES 或从库的 seller 维度表）。

⑤ 冷热分离：近期订单在主库，历史订单归档到冷库/数仓，查询时按时间路由。

⑥ 数据一致性：下单扣库存 + 创建订单在同一本地事务；跨服务用事务消息或本地消息表 + 对账。

⑦ 金额：用 long 存"分"，禁止 double/float（浮点精度问题会导致对不上账）。

追问 · 订单和库存怎么保证一致？方案：下单时预占库存（而不是直接扣减）→ 支付成功后实扣 → 超时未支付则释放预占。预占/实扣/释放三步都要幂等。"预占 + 实扣 + 释放"是电商库存的标准三段式，说出来很唬人。
Q14设计一个 IM 消息系统加分

① 接入层：Netty 长连接网关。维护 userId → Channel 映射（本地 Map 加速，Redis 存全局路由实现多网关寻址）。心跳保活 + 断线重连。

② 消息投递链路：发送方 → 网关 → 消息服务 → 落库（消息表，会话 ID + seq）→ 发 MQ → 路由到接收方所在网关 → 推送。在线直接推，离线写"离线消息/收件箱"。

③ 有序性：单会话内用递增 seq（Redis INCR 或 DB 自增），接收方按 seq 排序 + 去重。只保证会话内有序，不追求全局有序 —— 这是正确且务实的答案。

④ 可靠性：上行和下行都要 ACK。服务端未收到 ACK 就重推（配合客户端本地去重）；消息先落库再投递（不丢）。

⑤ 已读回执：会话维度记录 lastReadSeq，未读数 = 最新 seq - lastReadSeq，前端本地计算避免频繁请求。

⑥ 多端同步：同一账号多设备 → 用"写扩散"到各端收件箱，或让各端订阅同一条会话序号流（读扩散，更省存储）。

追问 · 万人大群怎么设计？写扩散会放大 1 万倍（一条消息写 1 万份），不可行。改用读扩散：消息只存一份在群会话里，成员各自拉取并维护自己的已读位点。对大群还要做限流 + 分级（活跃成员推、不活跃成员拉）。

Q16系统设计题你怎么答？（答题方法论）必考

面试官要的不是标准答案，是你的思考过程。四步法，时间分配大约 3:5:10:3 分钟：

  1. 需求澄清 + 容量估算（3 分钟）
    问清楚：功能边界、用户量/DAU、读写比、峰值倍数、一致性要求、延迟要求。

    这一步是最大的区分点 —— 90% 的候选人会跳过它。
  2. 高层架构（5 分钟）
    画核心链路：接入层（LB/网关）→ 应用层（服务划分）→ 存储层（DB / 缓存）→ 中间件（MQ / 搜索）。说清数据怎么流、写在哪读在哪。
  3. 深入 2-3 个技术难点（10 分钟）

Q1服务跑在 Docker / K8s 里，JVM 内存参数要怎么配？必答

先讲版本坑（这是这个问题的核心）：JDK 8u191 之前，JVM 看不到容器的 cgroup 限制，会按物理机内存来设默认堆 —— 容器限了 2G，JVM 却以为有 64G，堆开到 16G，结果被内核 OOMKilled。

正确做法：

  • JDK 8u191+ / JDK 10+：-XX:+UseContainerSupport（默认开启），JVM 会读取 cgroup 限制
  • 显式指定百分比，而不是写死绝对值：-XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=70
  • 为什么是 70%：剩下 30% 要留给元空间、线程栈（每线程约 1M）、直接内存（Netty 的堆外缓冲）、JIT 代码缓存、GC 自身的辅助结构
  • K8s 里 resources.limits.memory 要略大于"堆 + 堆外"的总和
追问 · 容器被 OOMKilled（exit code 137）一定是堆溢出吗？不是。堆溢出会先抛 OutOfMemoryError 并留下 dump 文件；而 OOMKilled 是内核杀的，通常是堆外内存超了 limit（直接内存、Metaspace、线程栈、JNI）。
排查：kubectl describe pod 看 Reason 是不是 OOMKilled；kubectl top pod 看实际内存；配合 -XX:NativeMemoryTracking=summary + jcmd VM.native_memory 看堆外分布。"区分堆 OOM 和 OOMKilled"这一条能显著区分出真上过 K8s 的人。
Q2K8s 的三种探针怎么配？滚动更新怎么不丢请求？必答
livenessProbe
判断"要不要重启这个 Pod"。必须用轻量且不依赖外部组件的接口，比如 /actuator/health/liveness。千万不要把 DB / Redis 检查放进来 —— 否则数据库抖动会让所有 Pod 同时被判定为不健康并重启，形成雪崩。
readinessProbe
判断"能不能接流量"。可以包含依赖检查（/actuator/health/readiness）。失败则从 Service 的 Endpoints 中摘除，不重启。
startupProbe
给慢启动的 Java 应用足够时间。有它之后，liveness 的 initialDelay 就不用设很大了，避免启动慢被误杀。

滚动更新不丢请求，三个必须做的事：

  1. preStop hook：sleep 5~15s，等 kube-proxy / Ingress 把流量摘干净（摘除是异步的，这段时间还在进流量）
  2. 优雅停机：Spring Boot 2.3+ 配 server.shutdown=graceful + spring.lifecycle.timeout-per-shutdown-phase=30s
  3. 合理设置 maxSurge / maxUnavailable（如 25%/0），保证始终有足够实例在服务
原理补充：容器收到 SIGTERM 后，JVM 默认会直接退出，正在处理的请求会被切断 —— 这就是"发版时偶发 502"的根因。开启优雅停机 + preStop 是标准解法。

Q5日志和链路追踪你们怎么做的？高频

TraceId 贯穿全链路：网关/入口生成 TraceId → 放入 MDC → 日志格式里带上 → 跨服务调用时通过 HTTP Header / MQ 消息属性传递 → 下游重新放入 MDC。汇总查询用 SkyWalking / Zipkin / Jaeger。

日志规范：

  • 结构化（JSON 格式，方便采集和检索）
  • 分级合理：error 必须带堆栈和业务上下文（订单号、用户 ID、入参摘要），不要只打 e.getMessage()
  • 关键路径打点：耗时、状态、结果
  • 敏感信息脱敏（手机号、身份证、密码、银行卡），不要打全量入参
  • 切割与保留策略（按天/按大小滚动的 logback 配置），避免写满磁盘
追问 · MDC 有什么坑？MDC 底层是 ThreadLocal，在异步任务和线程池里会丢。表现为：异步逻辑的日志没有 TraceId，排查时断链。
解法：① 提交任务时手动拷贝 MDC.getCopyOfContextMap()，在 Runnable 里 setContextMap，用完 clear；② 用 Spring 的 TaskDecorator 统一包装线程池；③ 用 TransmittableThreadLocal（TTL）。这是很真实的生产细节，主动说出来非常加分。
Q6你们的 CI/CD 流程是怎样的？高频

流水线阶段：Git 提交/PR → 代码检查（SonarQube 静态扫描、Checkstyle）→ 单元测试 + 覆盖率门槛 → 构建（Maven/Gradle）→ 打 Docker 镜像并推仓库 → 部署到测试环境 → 自动化冒烟 → 人工/自动卡点 → 灰度上线。

两个能体现细节的优化：

  • Docker 分层缓存：Spring Boot 2.3+ 支持分层 jar（layertools），Dockerfile 先 COPY dependencies 再 COPY classes —— 只改了业务代码时，依赖层可以复用缓存，镜像构建从几分钟降到几十秒。
  • 数据库变更版本化：用 Flyway / Liquibase 管理 DDL，纳入代码仓库走同一个流水线。禁止手工改生产表结构（否则环境和代码状态不一致，回滚时无法回溯）。
追问 · 回滚怎么做？镜像回滚是最简单可靠的（kubectl rollout undo / 切回上一个 tag）。但前提是数据库变更向后兼容 —— 如果新版本删了字段、旧版本还在用，回滚就会失败。所以数据库变更必须走"扩展-迁移-收缩"三步。
Q7灰度发布怎么做？数据库变更有什么讲究？加分

灰度的三种切分维度：① 按流量比例（Istio / Service Mesh 权重路由，或 Nginx 权重）；② 按用户标识（用户 ID 取模、白名单、设备号）—— 最常用，因为同一用户始终落同一版本；③ 按机器分组（金丝雀机器，挂独立的一批 Pod）。

配套必备：

  • 功能开关（Nacos / Apollo 配置中心），出问题秒级切回，不用发版
  • 新老版本指标对比：错误率、RT、业务成功率，差异超阈值自动终止灰度
  • 可观测：按版本维度打标，否则分不清是新版还是旧版的问题

数据库变更的"扩展-迁移-收缩"三步（重点）：

  1. 扩展：加新字段，不删旧字段。新老代码同时运行都能工作
  2. 迁移：代码双写新老字段，后台任务回填历史数据
  3. 收缩：确认新版本全量后，再删除旧字段和不必要的兼容代码
为什么这么做（一句话）：因为在灰度期间新老两个版本同时存在，任何一方的不兼容都会导致另一方报错。所以数据库变更必须"向前兼容"，且至少跨两个发版周期。这是"能不能安全发版"的关键认知。
Q8线上出故障，你的处理流程是什么？必答
  1. 止损优先 —— 这是最重要的一条。先回滚 / 降级 / 切流量 / 扩容，不要在故障中查根因。故障期间每一分钟都在损失，恢复服务和定位问题是两件必须分开的事。
  2. 拉群对齐：通报影响面（哪些用户、哪些功能）、指定一个人指挥（避免多人同时操作）。
  3. 定位：按监控看板 → QPS / RT / 错误率 → GC / CPU / 内存 → DB 慢查询 / 连接数 → 链路追踪 → Arthas 的顺序排查。先看大盘再钻细节。
  4. 处理：优先用配置中心热修改（改限流阈值、关开关、调线程池），其次才发版。发版要有回滚预案。
  5. 复盘：写 RCA（时间线 / 根因 / 影响面 / 改进项），每个改进项要有负责人和截止时间。补监控告警（同类问题下次要能自动发现）、补测试用例、补文档。
面试加分技巧：别说流程，讲一个你真实经历的事故 —— 现象、你的排查路径、根因、你做的改进。哪怕是很小的事故（比如一次缓存雪崩、一次发版丢请求），讲得细节具体，可信度远高于背流程。
准备一个万能结构："某次大促/发版时，XX 指标异常 → 我通过 XX 手段定位到 XX → 根因是 XX → 我做了 XX 修复和 XX 预防"。
踩坑：说"先查日志找原因"会被扣分 —— 顺序错了。止损永远优先。

现象 → 排查过程（体现方法论）→ 根因 → 解决 → 沉淀

推荐的素材类型（都很有说服力）：

  • 线上 OOM / CPU 飙高：从 top 到 jstack 到代码定位到修复，体现完整排查能力
  • 慢 SQL 引发雪崩：一个没走索引的查询把 DB 连接池打满，导致整个服务不可用
  • 缓存一致性事故：改数据后缓存没清，用户看到旧价格，资损 / 客诉
  • 消息积压：消费者被慢 RPC 拖死，几百万消息堆积

  • 分布式事务不一致：订单成功但库存没扣，靠对账任务发现并修复
关键在"沉淀"这一步（多数人忽略，但最能加分）：不只是修好，而是"修复后我做了什么让它不再发生" —— 加了监控告警、加了单元测试、改了代码规范、写了复盘文档、在团队里做了分享。这一步体现的是"工程成熟度"和"影响力"，正是高级开发与中级的分界线。

Q3你为什么这么选型？高频

答题结构（五步）：

  1. 业务场景："我们日均 50 万条异步任务，需要保证不丢、且要支持定时和延迟消息"
  2. 候选方案对比（至少 3 个维度）：
    RocketMQ vs Kafka —— 事务消息（RocketMQ 开箱即用，Kafka 需自己实现）、延迟消息（RocketMQ 原生支持 18 个级别，Kafka 要自己做）、单机吞吐（Kafka 更强）、运维成本（团队已有 RocketMQ 运维经验）
  3. 决策依据：业务需要的恰好是 RocketMQ 的强项，而吞吐量我们远没到 Kafka 的必要线
  4. 落地效果：运行一年，消息零丢失，延迟消息支撑了超时关单
  5. 遗留问题 / 如果重来："集群规模扩到 10 个 broker 后，运维复杂度上升，如果重来我会考虑用云服务托管版"
加分动作：主动说"什么情况下我会选另一个"。这句话直接证明你理解技术边界，而不是在用"信仰"选型。反过来，"因为大家都用"、"因为公司要求"是减分答案。
Q4你遇到过最难排查的 bug 是什么？高频

准备一个"偶发性 bug"的案例 —— 因为偶发最能体现排查能力。

结构：现象（多偶发）→ 你用了哪些手段（日志、Arthas、二分、加埋点复现）→ 如何缩小范围 → 根因 → 修复 → 防复发。

三个高价值真实案例模板：

  • SimpleDateFormat 线程不安全：把静态 SimpleDateFormat 放在工具类里，并发下日期解析出乱码或抛异常。排查过程：偶发、只在压测时出现、堆栈指向 DateFormat 内部状态不一致。修复：换 DateTimeFormatter（不可变、线程安全）。这个案例同时体现了"并发意识"。
  • 事务里嵌套异步导致事务丢失：@Transactional 方法里起线程执行 DB 操作，子线程拿不到事务上下文。修复：把异步任务挪到事务提交后（TransactionSynchronizationManager.registerSynchronization 或 @TransactionalEventListener(phase = AFTER_COMMIT)）。这个答案很高级，能直接证明你理解事务的真实边界。
  • ThreadLocal 没清理导致用户串号：登录信息放 ThreadLocal，线程池复用时拿到上一个请求的用户信息，出现"A 看到 B 的数据"。修复：try-finally 里 remove。这个案例是事故级的，说服力极强，但要小心面试官追问"那安全风险怎么评估的"。
关键：讲排查过程时要说你排除了哪些可能性。例如"我先排除了 DB 层（因为日志里 SQL 参数是对的），再排除了网络（同机调用也复现），最后定位到应用层的共享对象"。展示的是排除法思维，而不是运气。
Q5为什么离职？你的职业规划是什么？必答

离职理由（三个原则：说积极的、说客观的、绝不说前公司坏话）：

  • ✅ 业务方向不匹配："现有业务以 CRUD 为主，我想深入高并发和中间件领域"
  • ✅ 成长空间："团队规模小，系统只有几千 QPS，想在有更大流量挑战的场景下打磨能力"
  • ✅ 技术栈："想接触更规范的技术体系（微服务治理、灰度发布、可观测性）"
  • ❌ 绝不说的："领导不行"、"同事水平差"、"加班太多"、"薪资低"（薪资留到 HR 面谈）

职业规划（要有具体路径，不要喊口号）：

  • 短期（1-2 年）：成为团队技术骨干，能独立负责一个核心系统的设计与演进
  • 中期（3-5 年）：往技术专家 / 架构方向走，具备复杂系统的技术决策能力，能带 2-3 人的小组
  • 锚定公司：一定要把规划和公司挂钩："我了解到贵司的 X 系统面临 Y 挑战，这正是我想深入的方向"
追问 · 你有什么缺点？说一个真实的、非致命的、且正在改进的缺点。推荐："我对非核心模块的文档整理不够及时，导致同事接手时要问我。现在我会强制自己每次改完代码就更新变更记录。"绝对不要说"我追求完美"、"我太拼命工作"。也别说"我不会拒绝人"（这是职场老好人，会被认为缺乏判断力）。
Q6如果让你重新做这个项目，你会怎么改？高频

这是考"反思能力"和"技术视野"的题，能答好直接拉高一个档次。分四类讲：

  • 架构层面：服务边界划得不合理（订单服务承担了太多职责）、缺少统一网关和鉴权、同步调用过多应该改异步
  • 技术层面：缓存一致性方案（当时用延迟双删，现在会改成 Canal 订阅 binlog）、引入可观测性（当时只靠日志 grep）、数据库分片键选择（应该更早考虑扩容）
  • 工程层面：没有自动化测试覆盖核心链路、缺少灰度发布机制、数据库变更靠手工执行
  • 业务层面：接口设计没有考虑向后兼容、缺少限流熔断的兜底
答题要点：每一条都要说清"当时为什么那么做" —— 不是当时错了，而是业务阶段不同。例如："当时只有几万 QPS，用延迟双删是合理的成本权衡；如果现在日订单到几百万，我会改用 binlog 订阅，因为业务代码不该承担缓存一致性的正确性责任。"
这样回答体现的是"具备与业务阶段匹配的技术判断力"，比否定过去高得多。
Q7面试官问"你还有什么想问我的吗"高频

这一问是加分题，不是客套。准备好 5 个，按面试轮次选着问。

技术面问这些：

  • "团队目前在技术上最大的挑战 / 瓶颈是什么？"（体现你关心问题，不只关心待遇）
  • "这个岗位负责的核心系统是什么？我入职后最可能先接手哪块？"
  • "团队的研发流程是怎样的 —— 需求评审、code review、测试、灰度上线这套跑得顺吗？"
  • "接着刚才聊的 XX，你们线上实际是怎么做的？"（把面试变成技术交流，非常好用）
  • "团队怎么定义'做得好'？技术晋升主要看什么？"

HR 面问这些：

  • "团队的人员构成和汇报关系？我未来的直接上级是什么背景？"
  • "这个岗位是新增编制还是补充？"（能看出团队的扩张/流失情况）
不要问：① "加班多吗"（换成"团队一般什么时候发版 / 值班机制是怎样的"）；② 薪资福利（留给 HR 主动谈）；③ "我表现怎么样"（场面尴尬，且拿不到真话）。
更不要反问"你们公司是做什么的" —— 说明你完全没做功课。
Q8简历怎么改才能通过筛选？加分

三条原则：

  1. 每条经历都要能扛住 3 层追问。写完一条自问：用了什么技术（1 层）→ 为什么这么选（2 层）→ 有什么坑/代价（3 层）。扛不住的就删掉或改弱，别为了好看写自己不懂的词（写了 Redis 分布式锁，就可能被问到 RedLock 争议）。
  2. 量化，但要真实且能自洽。❌"提升了系统性能" → ✅"下单接口 P99 从 800ms 降到 120ms"。数字要能被算术检验（日均量 / 86400 ≈ 平均 QPS，峰值一般是 3-10 倍）。
  3. 突出"我"的贡献而不是"我们"的成果。用"主导 / 负责 / 独立设计 / 推动"，而不是"参与 / 协助"。5 年经验必须有"独立负责"的表述，否则会被认为还停留在执行层。

5 年经验的简历应该体现的三件事：① 独立负责过一个完整系统的设计或重构；② 有突出问题排查/性能优化的具体案例；③ 有技术影响力（带过人、定过规范、做过技术分享）。

投递节奏建议：① 先投 2-3 家"不想去但能练手"的公司，用真实面试检验准备情况；② 根据反馈集中补漏一轮；③ 再投目标公司。不要一上来就投最想去的。另外准备好"最近有没有在面试别的公司 / 有几个 offer"的中性回答（不要报具体公司名，也不要说"只有你们一家"）。
