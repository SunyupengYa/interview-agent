核心名词速查表

先把 RocketMQ 的术语记牢，后面所有题目都在反复用这些词。面试时张冠李戴是硬伤。

名词是什么一句话记忆
Producer生产者，发消息的一方。分普通发送、顺序发送、事务发送。「造消息的人」
Consumer消费者，拉取并处理消息的一方。分 Push 模式（长轮询）和 Pull 模式。「用消息的人」
Broker消息存储与转发的中枢，RocketMQ 的核心。接收、持久化、投递消息。「消息的仓库 + 邮局」
NameServer路由元数据中心（无状态、对等）。存「Broker 地址 + Topic 的队列分布」。「轻量版注册中心，不存消息」
Topic消息的逻辑分类，类似「文件夹」。一个 Topic 下多个队列。「消息的分类标签」
MessageQueueTopic 的物理存储单元，RocketMQ 里叫「队列」而非「分区」。队列内有序。「Topic 拆成的小队列，顺序+并行的最小单位」
Tag消息的子标签，用于在同一个 Topic 下做二次分类和过滤。「Topic 的二级分类」
GroupId生产者/消费者分组的唯一标识。同一 GroupId 的生产者属同一集群；同一 GroupId 的消费者属同一消费组。「谁是一伙的，靠它区分」
CommitLogBroker 上所有消息的顺序追加写文件（全量）。所有 Topic 的消息都写这一个文件。「所有消息的大账本，只追加不修改」
ConsumeQueue每个队列的轻量索引文件，只存「offset + size + tag hash」，不存消息体。「查消息的目录，指路不存货」
Offset消息在 CommitLog 里的物理位置 / 队列里的消费位点。消费进度靠它记录。「书签，断点续传靠它」
Message Key消息的业务标识，用于定位/查询某条具体消息。「消息的身份证」
半消息（Half Message）事务消息第一阶段发到 Broker 但「暂不投递」的消息，对消费者不可见。「先存着，等确认再放行」
死信队列（DLQ）重试次数耗尽仍失败的消息的最终归宿，隔离「毒消息」。「处理不了的消息的垃圾桶」
消费组（Consumer Group）共享同一 GroupId 的消费者集合。组内负载均衡，组间广播。「组内抢着分，组间各自全收」

主从复制Master 写、Slave 同步备份。分同步复制（SYNC）和异步复制（ASYNC）。「主写从备，可靠性与延迟的取舍」

① 核心架构 角色 / NameServer / 收发链路 / 为什么快

Q1 RocketMQ 有哪些核心角色？各自职责？必考

四个核心角色 + 一个关键区分：

  • Producer：发消息，先查 NameServer 拿路由，再发到 Broker。
  • NameServer：轻量路由中心，存「Broker 地址 + Topic 队列分布」，不存消息、不参与转发。
  • Broker：消息存储和转发中枢，RocketMQ 的核心，承担真正的消息落盘。
  • Consumer：按消费组拉取并处理消息。

关键区分：NameServer 只做路由，不碰消息。这是它和 ZooKeeper（Kafka 的元数据中心）最大的差异——NameServer 无状态、对等、去中心化，够用即可。

追问：为什么 RocketMQ 用 NameServer 而不用 ZooKeeper？NameServer 无状态、对等、部署简单，不需要 ZK 那么重的强一致协调。它只存路由信息，Broker 定时心跳上报即可。
踩坑：把 NameServer 说成「消息中转站」或「注册中心存消息」都是错的。它只存路由元数据，消息只在 Broker 上。
Q2 一条消息从生产到消费，经历了哪些环节？必考
  1. 生产者发消息 → 先向 NameServer 查 Topic 的路由（哪个 Broker、哪个队列）。
  2. Broker 接收 → 写入 CommitLog（所有消息顺序追加），再异步构建 ConsumeQueue 索引。
  3. 持久化 → 刷盘（同步/异步）+ 主从同步（同步/异步复制）。
  4. 消费者拉取 → 根据 ConsumeQueue 索引定位 CommitLog 里的消息，返回。
  5. 消费 + ACK → 处理完返回成功，Broker 更新消费位点（offset）。
RocketMQ 消息收发主链路流程图
追问：CommitLog 和 ConsumeQueue 为什么分两个文件？CommitLog 全量顺序写（快），ConsumeQueue 是轻量索引（只存 offset+size+tag hash），消费时按索引定位，不用扫全量。
踩坑：这条链路答不全，是「可靠性」「存储」模块所有题的硬伤——先能完整串下来，再谈不丢。
Q3 RocketMQ 为什么快？吞吐为什么高？必考

四个核心原因，缺一不可：

  • 顺序写磁盘：CommitLog 是 append-only 追加写，顺序写比随机写快一个数量级，接近内存写。
  • 零拷贝（zero-copy）：消费时用 mmap（或 sendfile）把磁盘数据直接映射到网卡，减少用户态拷贝。
  • 页缓存（PageCache）：消息先写操作系统页缓存，读大多命中内存。
  • 异步刷盘 + 批量：默认异步刷盘，攒一批落盘；发送端批量 + 压缩降低网络开销。
RocketMQ 高吞吐四大原因图
追问：RocketMQ 的「单机吞吐」大概什么量级？十万级 TPS 的量级（具体看消息大小和机器配置），比 MySQL 高几个数量级，这正是它适合做削峰/异步的原因。
踩坑：别答「因为用了内存」。RocketMQ 持久化靠磁盘，快靠的是顺序写 + 零拷贝，不是内存数据库。
Q4 Topic、MessageQueue、Tag 三者什么关系？必考

三层关系：Topic（大类）→ MessageQueue（物理队列）→ Tag（子分类）。

  • Topic：消息的逻辑分类，如「订单 Topic」「支付 Topic」。一个 Topic 对应多个 MessageQueue。
  • MessageQueue：物理存储单元，消息真正落在队列里，队列内有序，跨队列无序。
  • Tag：同一个 Topic 下的二级分类，用于过滤，如「订单 Topic」下分「创建」「支付」「取消」三个 Tag。

为什么分这三层：Topic 太粗、队列负责并行和顺序、Tag 负责细粒度过滤——三者各司其职。

追问：为什么要用 Tag 而不是建很多 Topic？Topic 多了会增加 NameServer 路由压力和运维成本。Tag 在同一个 Topic 内做过滤，更轻量。但 Tag 也不能滥用——Tag 太多会退化成「分类混乱」，一般建议一个 Topic 下 Tag 不超过十几个。
踩坑：把 MessageQueue 叫「分区（Partition）」——那是 Kafka 的叫法。RocketMQ 叫「队列」，虽然机制类似，但面试里说混概念会显得没真正用过 RocketMQ。
Q5 GroupId 是什么？生产者和消费者的 GroupId 有什么区别？必考

GroupId 是「同一类角色」的分组标识，但生产者和消费者的语义完全不同：

  • 生产者 GroupId：标识「一组做同一件事的生产者」，主要用于事务消息回查时定位是哪个生产者发的半消息。普通消息下作用不大。
  • 消费者 GroupId：就是「消费组」的概念，决定消费模型——组内负载均衡（一条消息只被组内一人消费），组间广播（各自消费全量）。
维度生产者 GroupId消费者 GroupId
作用标识同类生产者，事务回查定位定义消费组，决定负载均衡/广播
关键规则同一 GroupId 的生产者功能应一致同一 GroupId 的消费者共享消费进度
追问：两个消费者用了同一个 GroupId 会怎样？它们会成为一个消费组，Topic 的消息在它们之间负载均衡分摊，一条消息只被其中一个消费。如果本意是「两个系统都要收到」，那必须用不同的 GroupId。
踩坑：「想广播却误用了同一个 GroupId」是经典事故——结果消息被分摊，第二个系统收不到。广播要不同 GroupId。
Q6 消费组（Consumer Group）的点对点 vs 广播怎么区分？必考

两条规则记住：

  • 组内（同一个 GroupId）：一条消息只能被组内一个消费者消费（负载均衡/点对点）。
  • 组间（不同 GroupId）：不同消费组各自独立消费全量消息（广播/发布订阅）。

所以「点对点 vs 广播」的区别不是消息类型，而是是不是同一个 GroupId：同组 = 点对点，不同组 = 广播。

追问：怎么实现广播？给每个想要独立消费的下游单独建一个 GroupId（各自一个消费组），各组互不影响。
踩坑：消费组内「一条消息只被一人消费」是正常消费时的语义，但消费者失败重试时同一条消息会再次投递，业务侧仍要做幂等。
Q7 Push 模式和 Pull 模式的区别？RocketMQ 的「长轮询」是什么？高频

本质区别：谁控制消费节奏。

PushPull
节奏Broker 主动推消费者自己拉
优点实时性高按能力消费，不压垮消费者
缺点Broker 不知道消费能力，易压垮消费者有拉取间隔延迟

RocketMQ 的「Push 模式」底层其实还是 Pull，只是封装了长轮询：消费者拉取时若没消息，Broker 会挂起请求（默认 15s）而不是立刻返回空，有消息立即唤醒——兼顾 pull 的自主性和 push 的实时性。

追问：长轮询和真正的 Push 差在哪？长轮询仍是消费者主动发起请求，只是 Broker 延迟响应；真正的 Push 是 Broker 单向推送，消费者被动接收。
踩坑：别简单说「pull 有延迟所以不如 push」。长轮询已经把 pull 的延迟问题基本消掉了，RocketMQ 默认就是长轮询。
Q8 消息过滤怎么做？Tag 过滤 vs SQL92 过滤？高频
  • Tag 过滤：消息打一个 Tag，消费者按 Tag 订阅。Tag 存在 ConsumeQueue 索引里，直接匹配，快。
  • SQL92 过滤：按消息属性（如 price > 100）过滤，要读消息体属性，开销大。

原则：能用 Tag 就用 Tag，SQL92 只有确实需要按属性过滤时才用。

追问：Tag 过滤为什么比 SQL92 快？Tag 存在 ConsumeQueue 索引里，直接匹配不读消息体；SQL92 要读消息属性，多了 IO。
踩坑：忽略「过滤放哪端」的性能差异。Broker 端过滤（Tag）省网络和消费端开销，消费端过滤浪费资源。

② 存储模型 CommitLog / ConsumeQueue / 刷盘 / 过期清理

Q1 CommitLog 和 ConsumeQueue 是什么？为什么这么设计？必考
  • CommitLog：所有 Topic 的消息共用一个文件，顺序追加写。全量消息都在这。
  • ConsumeQueue：每个队列一个轻量索引文件，只存「offset + size + tag hash」，不存消息体。

为什么这么设计：写入时只要顺序写一个 CommitLog，快；读取时按 ConsumeQueue 定位，不用扫全量。这是「写优化」和「读优化」的解耦。

追问：所有 Topic 共用一个 CommitLog 有什么好处？顺序写最大化利用磁盘，避免「每个 Topic 一个文件」导致的随机写。代价是消费时要靠 ConsumeQueue 索引定位。
踩坑：把 CommitLog 说成「每个 Topic 一个」，或把 ConsumeQueue 说成「存了消息内容」——都是错的。ConsumeQueue 只存索引。
Q2 同步刷盘和异步刷盘的区别？必考
维度同步刷盘异步刷盘
行为每条消息 fsync 落盘才返回成功写页缓存即返回，后台批量落盘
可靠性高，断电不丢低，宕机可能丢「还没落盘」的
吞吐低（磁盘 IO 是瓶颈）高
适用金融、支付等要求不丢日志、埋点等可容忍少量丢失

默认异步刷盘。要「不丢」就同步刷盘，代价是吞吐下降一个量级——「可靠性换性能」。

内存层次理解：消息落盘要经过「用户内存 → 页缓存（PageCache）→ 磁盘」三层。刷盘就是把「页缓存」刷到「磁盘」。同步 = 每次都刷，异步 = 攒一批再刷。

追问：异步刷盘丢了哪些消息？丢的是「已返回成功、但还在页缓存里没 fsync」的那批。宕机断电页缓存清空，这批就没了。
踩坑：「同步刷盘」和「同步复制」是两个层面的东西——刷盘管「内存到磁盘」，复制管「主到从」，别混。
Q3 消息过期/清理机制是什么？加分
  • RocketMQ 消息默认保留 72 小时（fileReservedTime 可配置）。
  • 过期后 CommitLog 文件被整体删除（按文件粒度，不是按条）。
  • 也可以按「磁盘水位」清理：磁盘占用到一定比例，优先删最旧的文件。

关键：RocketMQ 是「日志型」存储，消息保留一段时间供重放，而不是「消费即删」。

追问：为什么按文件删除而不是按条？CommitLog 是顺序追加的文件，整文件删除最简单高效；按条删除需要重写文件，代价大。
踩坑：把「保留策略」和「消费进度」混为一谈。保留策略决定消息存多久，和是否被消费无关——已消费的消息也还在 CommitLog 里，直到过期删除。

③ 可靠性与高可用 不丢 / 不重 / 有序 / 事务 / 主从 / 脑裂

Q1 消息在哪些环节可能丢失？怎么保证不丢？必考

三个环节各丢各的，逐一堵：

  • 生产端丢：发消息用同步发送，收到 Broker 的确认才返回成功；失败要重试。
  • Broker 端丢：异步刷盘可能宕机丢数据 → 同步刷盘；主从异步复制丢数据 → 同步复制。
  • 消费端丢：自动提交 offset，消息还没处理完就提交了 → 手动提交，处理完再提交。
消息丢失的三个环节图
追问：做到「完全不丢」的代价？性能下降。同步刷盘、同步复制、手动提交都会增加延迟。可靠性用性能换，没有既快又绝对不丢。
踩坑：三个环节答不全，或者只答「用事务」——「消息不丢」和「事务消息」是两回事，前者靠 ACK+刷盘+提交，后者靠两阶段。
Q2 消息为什么可能重复？怎么保证不重复消费？必考

重复的根源：「至少一次投递」语义下，ACK 丢失或超时会导致同一条消息被再次投递。消费者处理完了、但 ACK 没发出去（网络抖动），Broker 以为没消费，又投递一次。

解决：消费端做幂等

  • 业务唯一键去重：消息带业务唯一 ID，消费前查是否处理过（DB 唯一索引 / Redis setnx）。
  • 幂等表：建一张「消息 ID → 状态」表，先插入，唯一索引冲突说明处理过。
  • 状态机：把处理逻辑设计成幂等的（如「置为已支付」而不是「金额 +10」）。
追问：为什么 MQ 不做成「恰好一次」？「恰好一次」要么靠事务（性能差），要么靠幂等（业务自己保证）。业界主流是「至少一次 + 业务幂等」，成本最低。
踩坑：别指望 MQ 本身解决重复。MQ 只能保证「不丢」（至少一次），「不重」必须业务侧幂等。
Q3 怎么保证消息顺序？必考

核心原则：要保证顺序的消息，必须进同一个 MessageQueue，且同一时刻只能被一个消费者单线程消费。

  • 全局有序：Topic 只设 1 个队列。牺牲并行度，吞吐极低，几乎不用。
  • 局部有序（推荐）：用 MessageQueueSelector 按业务 key（如订单 ID）哈希路由到同一队列，保证「同一个订单的消息」有序，不同订单之间无所谓。
  • 消费端：单线程消费该队列，处理完再拉下一条，避免并发打乱。
RocketMQ 顺序消息机制图
追问：消费者重试会不会乱序？会。失败重试时后续消息可能先被处理。解决：用「顺序消费模式」，失败的消息会一直重试直到成功，阻塞后续消息——牺牲可用性保顺序。
踩坑：「队列内有序」被误答成「Topic 内有序」。Topic 多队列时跨队列是无序的，顺序只保证在单队列内。
Q4 事务消息是什么？解决什么问题？原理？必考

事务消息解决「本地事务和发消息的原子性」问题——要么「DB 提交 + 消息发出」都成功，要么都不成。典型：下单扣库存成功后，一定要发出「下单成功」消息。

RocketMQ 事务消息（两阶段 + 回查）

  1. 发「半消息」（half message），Broker 先存但不投递给消费者。
  2. 执行本地事务（扣库存）。
  3. 本地事务成功 → 提交半消息；失败 → 回滚。
  4. 若生产者宕机，Broker 定时回查本地事务状态，决定提交还是回滚。
RocketMQ 事务消息流程图（两阶段 + 回查）
追问：为什么需要「回查」？防止生产者执行完本地事务后、提交消息前宕机，导致状态未知。回查是事务消息可靠性的关键。
踩坑：事务消息不能保证「消费端一定成功」。它只管「本地事务 + 发消息」的原子，消费端失败仍要靠重试 + 幂等。
Q5 ACK 机制：自动提交和手动提交的区别？必考

ACK 是消费者告诉 Broker「我处理完了，可以把这条消息标记为已消费」。

方式行为风险
自动提交拉取后立即提交 offset处理失败消息已丢（丢消息）
手动提交处理成功后再提交提交前宕机会重复消费（要幂等）

结论：可靠性要求高的场景必须手动提交，同时配合幂等解决「提交前宕机」导致的重复。

追问：提交太频繁有什么问题？性能开销大。可以「处理一批、提交一次」，但要在「批量提交的吞吐」和「重复消费窗口」之间权衡。
踩坑：自动提交 + 没做幂等 = 既可能丢又可能重，是生产事故高发写法。
Q6 主从复制有哪两种模式？必考
  • 同步复制（SYNC）：主写成功 + 从也写成功才返回。可靠，延迟高。
  • 异步复制（ASYNC）：主写成功即返回，后台同步给从。快，但主挂可能丢消息。

早期 RocketMQ 主从是「主写从读」，主挂后从不能自动接管写（需人工切换），后来 DLedger（Raft 实现）补齐了自动选主。

RocketMQ 高可用：主从同步 + DLedger 选主流程图
追问：RocketMQ 从节点能读吗？早期主从架构下，从节点默认不提供读（读主），消费靠主；DLedger 架构下也是主负责读写。
踩坑：混淆「同步复制」和「同步刷盘」。复制是「主到从」，刷盘是「内存到磁盘」，是两个独立维度，可交叉组合。
Q7 什么是脑裂？RocketMQ 怎么避免？必考

脑裂 = 集群分裂成两个互不通信的部分，各自选出了自己的主（Master），同时对外服务，导致数据分叉、无法合并。

RocketMQ 怎么避免

  • DLedger（Raft）：靠「多数派投票」选主，只有获得「过半节点」投票才能当主。
  • 分裂后两边不可能同时过半，必有一边选不出主（放弃写），从根源上杜绝双主。
追问：为什么「过半」能防脑裂？N 个节点，任何分裂的两部分最多只有一边 ≥ N/2+1，所以最多一边能选出主，另一边自动降级。
踩坑：别答「网络断了就是脑裂」。脑裂的关键是「两边都认为自己是主、各自接受写」，单纯的网络抖动但没产生双主不算脑裂。
Q8 消息堆积（积压）了怎么办？必考
  1. 先看消费能力：是不是消费者太少或单消费者太慢（逻辑阻塞、慢 SQL）。
  2. 加消费者：扩消费组内消费者数，但不能超过队列数——超过的部分空转。
  3. 队列不够：扩队列（RocketMQ 队列数要提前规划，线上改成本高）。
  4. 紧急消峰：临时起一批「只消费不处理」的消费者把消息转存，先腾空队列。
  5. 根因：长期看，是下游处理能力不足还是消息设计不合理。
消息堆积排查流程图
追问：为什么「消费者数不能超过队列数」？一个队列同一时刻只能被组内一个消费者消费。消费者多于队列，多出来的拿不到任何消息。
踩坑：一上来就「加机器」。先搞清楚是「队列数限制了并行度」还是「单消费者逻辑慢」，加错方向白花钱。
Q9 消费位点（offset）怎么管理？断点续传怎么实现？高频

RocketMQ 的 offset 存 Broker 端，消费成功后上报，Broker 记录每个消费组的消费进度。

  • 意义：断点续传。消费者重启后从上次 offset 继续，不重不漏（配合幂等）。
  • 粒度：按「消费组 + 队列」记录，不同消费组各自独立。
追问：offset 提交了但消息没处理完就宕机，会怎样？消息会「丢」——因为 Broker 认为已消费。这就是为什么手动提交要在处理成功后。
踩坑：「offset 存 ZooKeeper」是 Kafka 老版本的说法，别套到 RocketMQ 上。RocketMQ 的 offset 存 Broker。

④ 特性与场景 延迟 / 死信 / 削峰 / 最终一致 / 踩坑

Q1 延迟消息怎么实现？应用场景？必考

延迟消息 = 发出去后，过指定时间才投递给消费者。

  • RocketMQ 原生支持 18 级延迟：1s、5s、10s、30s、1m...一直到 2h。发消息时指定延迟等级，Broker 暂存，到期投递。

应用场景

  • 订单超时关闭：下单 30 分钟未支付自动取消，释放库存。最经典。
  • 延迟重试：支付回调失败，延迟一段时间再查。
  • 延迟通知：会员到期前 3 天提醒、会议开始前 10 分钟提醒。
追问：18 级延迟够用吗？想延迟 3 小时怎么办？18 级最大到 2h。要更精确/更长的延迟，需要自己实现（如 RocketMQ 5.x 的定时消息，或外挂时间轮）。
踩坑：「订单超时取消」要配合「查询支付状态」而不是「直接取消」，避免延迟消息和支付成功的竞态。
Q2 死信队列（DLQ）是什么？什么时候会进死信？必考

死信队列是无法被正常消费的消息的最终归宿。在 RocketMQ 里，消费失败会进入重试队列（如 %RETRY%ConsumerGroup），重试次数耗尽（默认 16 次）仍失败，就进入死信队列（%DLQ%ConsumerGroup）。

价值

  • 把「毒消息」隔离起来，不让它无限重试阻塞队列。
  • 保留现场供人工排查、批量重放。
追问：死信消息怎么处理？告警 + 人工介入，或写脚本批量重放。死信本身不是 bug，是「兜底」，真正的 bug 在消费逻辑。
踩坑：别把「重试队列」和「死信队列」混为一谈。重试是临时退回，死信是彻底放弃。
Q3 削峰填谷怎么设计？必考

场景：秒杀/大促瞬时流量洪峰，下游（DB/订单系统）扛不住。

  1. 请求先进 MQ（生产者只负责快速投递）。
  2. 消费者按自己能力匀速消费。
  3. MQ 当「蓄水池」，把瞬时尖峰摊平成一段时间内的平滑流量。

配合：限流（网关/入口）控制进入量，容量规划（算清峰值、堆积时长、磁盘容量）。RocketMQ 天生为亿级堆积设计，最适合这个场景。

追问：削峰的代价？实时性下降。用户「下单成功」可能变成「下单受理中」，要异步通知结果。业务要能接受延迟。
踩坑：只答「用 MQ 削峰」不给数字。要能说出「峰值多少、下游扛多少、堆积多久、需要多大磁盘」。
Q4 分布式事务（最终一致性）用 MQ 怎么实现？必考

用「本地消息表」或「事务消息」实现最终一致，替代强一致的两阶段提交（2PC，性能差）。

本地消息表方案

  1. 本地事务里：业务写 DB + 往「消息表」插一条待发消息（同一事务，原子）。
  2. 定时任务扫描消息表，把「待发」消息发到 MQ。
  3. 消费方消费成功后，回写消息表状态为「已消费」。
  4. 配合幂等 + 重试，保证最终一致。

RocketMQ 的事务消息是它的「内置版」，省掉自己写消息表。

追问：和 2PC 比优势在哪？2PC 同步阻塞、锁定资源、协调者单点。MQ 方案异步、无锁、可用性高，代价是「最终」而非「强」一致。
踩坑：别把「最终一致」当「弱一致」。最终一致是有兜底机制（重试+幂等+对账）保证的收敛，不是「爱一致不一致」。
Q5 一个「下单 → 扣库存 → 发积分」的链路，用 MQ 怎么拆？高频

核心：区分「强一致的核心链路」和「可异步的非核心链路」。这道题考的就是「能不能分清哪些步骤必须同步、哪些可以异步」。

拆法

  1. 下单 + 扣库存：强一致，同一个本地事务，用事务消息保证原子性。
  2. 发积分、发通知、记埋点：异步解耦，订阅「下单成功」消息各自处理。

主流程只依赖核心事务，积分/通知/埋点挂了都不影响下单，各自独立重试。

追问：积分系统挂了怎么办？消息堆积在 MQ，积分系统恢复后继续消费，靠幂等保证不重复发积分。
踩坑：把「扣库存」也异步化是危险的——库存强一致关系到超卖，不能随便异步。
Q6 RocketMQ 能保证不丢、不重、有序吗？三者的取舍？必考

这是一道「综合能力」题。核心结论：三者不能同时免费获得，都是取舍。

目标手段代价
不丢同步刷盘 + 同步复制 + 手动提交性能下降
不重业务幂等（唯一键/幂等表）业务复杂度
有序单队列/顺序消费并行度下降

「不丢」由 MQ 保证，「不重」必须业务侧幂等，「有序」用单队列或局部有序。

追问：什么业务必须有序？状态机类业务（订单状态流转、账户余额变动）通常要「同一对象内有序」，用 key 哈希到同队列即可，不必全局有序。
踩坑：说「都能保证」是错的。要能清醒地讲清每个目标的代价和边界，这是高级开发和大厂的分水岭。
Q7 什么场景不适合用 RocketMQ？加分
  • 强一致、低延迟：实时转账、扣款，要求同步返回结果，MQ 的异步延迟不可接受。
  • 简单异步调用：就一个下游、量不大，线程池/异步框架够用，引 MQ 是杀鸡用牛刀。
  • 纯流式处理/日志采集：这种「海量数据流」场景 Kafka 更合适（RocketMQ 强在业务消息）。
  • 需要请求-响应语义：调用方要拿结果的 RPC 场景，MQ 是单向的。

判断标准（一句话）

问自己三个问题：① 能接受异步延迟吗？② 下游有多个且会变化吗？③ 流量有明显峰谷需要缓冲吗？三个都是「是」，才值得上 RocketMQ。

追问：引入 MQ 的隐性成本有哪些？运维（集群、监控、扩容）、一致性（丢/重/序）、排查复杂度（消息链路追踪）。
踩坑：把 MQ 当「万能异步」，所有解耦都上 MQ，导致系统里 MQ 泛滥、链路难排查。
Q8 你项目里 RocketMQ 踩过什么坑？怎么解决的？高频

这是「项目复盘」必问题，用 STAR 结构，提前准备 2-3 个真实案例。给三个高频坑模板：

  • 重复消费：消费端没做幂等，下游重复扣款/发货 → 加唯一键幂等。
  • 消息堆积：某次大促下游处理不过来 → 扩消费者 + 定位慢 SQL + 临时消峰。
  • 顺序错乱：多线程消费同订单消息导致状态错乱 → 按 key 哈希到同队列 + 单线程消费。

要点：带上具体数字（堆积了多少、消费了多少 QPS、优化后提升多少），才像真踩过。

追问：怎么监控 RocketMQ 的健康？看堆积量、消费延迟、消息失败率、Broker 磁盘水位、消费组 lag。这些指标要有告警。
踩坑：答「没踩过坑」——5 年经验说没踩过坑，要么项目太简单，要么没深入。宁可说「早期踩过 XX，后来规范成 YY」。

⑤ 三大 MQ 对比总结 Kafka / RocketMQ / RabbitMQ

虽然本手册只讲 RocketMQ，但面试几乎必考「三大 MQ 区别」。一句话定位 + 一张对比表记牢即可。

MQ一句话定位核心优势典型场景
Kafka分布式流处理平台超高吞吐、持久化、分区有序、生态成熟日志采集、埋点、流计算、大数据
RocketMQ金融级业务消息事务消息、延迟消息、亿级堆积电商下单、削峰、事务一致性
RabbitMQ通用消息中间件AMQP 标准、路由灵活、易上手中小厂解耦、任务分发、RPC

选型一句话：日志/埋点/流计算 → Kafka；业务消息/事务/延迟/削峰 → RocketMQ；中小厂简单解耦/RPC → RabbitMQ。
