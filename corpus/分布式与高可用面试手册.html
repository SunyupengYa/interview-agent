① 分布式理论 CAP · BASE · Raft · 时钟

CAP 理论：三个字母的精确含义 + 为什么不可兼得 + 常见误解必考已掌握

CAP 是 Eric Brewer 在 2000 年提出的猜想，2002 年被 Lynch 等人用数学严格证明（因此它是「定理」，不是「经验法则」）。三个字母都必须精确理解，否则一追问就露馅。

三个字母的精确定义（不是字面意思）

字母精确含义常见误解
C 一致性线性一致性（Linearizability）：所有节点在同一时刻看到的数据都一样，读操作总能读到「最近一次写」的结果，好像只有一个副本。误以为是「数据最终会一样」（那是最终一致），CAP 里的 C 是强一致。
A 可用性每个「非故障」节点都能在有限时间内返回一个非错误的响应（哪怕数据是旧的）。注意：它不要求返回的是「最新数据」。误以为「可用 = 永不宕机」。A 只要求「能响应」，不要求「响应正确/最新」。
P 分区容错网络发生分区（Partition）时——即节点间消息丢失、延迟，网络被切成互不连通的两半——系统仍能继续工作。误以为「P 是可选项」。分区不是「可能发生」而是「必然发生」的网络故障。

为什么「必然选 P」，C 和 A 不可兼得？

关键前提：分布式系统里，网络故障（消息丢失、交换机故障、机房断连）是物理上必然发生的，你无法消灭它。所以 P 是「被迫接受」的约束，而不是「可以放弃」的选项。真正要选的是——分区发生后，C 和 A 二选一。

用一个具体场景证明（这是面试官最爱追问的点）：

  1. 系统有 A、B 两个节点，各存一份数据 x = 1。
  2. 某时刻网络分区：A、B 之间消息不通，但两边都能正常对外服务。
  3. 客户端 1 连上 A，写入 x = 2；客户端 2 连上 B，要读 x。
  4. 此时 B 上 x 还是 1。系统只有两个选择：
  • 选 C（牺牲 A）：B 拒绝响应（返回错误或一直等），直到 A、B 恢复同步。→ 保证读到的 x 一定是最新的，但此刻 B 不可用。
  • 选 A（牺牲 C）：B 直接返回 x = 1（旧值）。→ B 可用，但读到的是过期数据，两节点数据不一致。

这就是「分区时刻，C 和 A 只能二选一」的数学本质：分区后，如果还想所有节点都响应（A），就不可能保证所有响应都是最新的（C）。

三种组合分别代表什么

组合含义典型代表
CP分区时宁可不可用，也要数据一致Zookeeper、etcd、Consul、HBase、MongoDB(默认)
AP分区时宁可短暂不一致，也要可用Eureka、Cassandra、DynamoDB、CouchDB
CA理论上存在（无分区时），分布式下无意义——因为分区必然发生，CA 等价于「单机系统」传统关系型数据库（单机 MySQL/Oracle）

三个高频误解（一定要主动澄清）

  • 误解 1「三选二」：不是「从三个里挑两个」，而是「P 必须选，剩下的 C/A 二选一」。真正的选择发生在分区发生的那一刻，平时三者可以同时满足。
  • 误解 2「选了 CP 就永远不可用」：错。分区是暂时的，分区恢复后 CP 系统恢复正常。CP/AP 说的是「分区期间」的取舍，不是永久状态。
  • 误解 3「CAP 和 ACID 冲突」：两者维度不同。ACID 是「单机事务」的保证，CAP 是「多副本分布式」的取舍，不矛盾。数据库的 ACID 是「数据库内部」的一致性，CAP 的 C 是「多副本之间」的一致性。

BASE 理论（AP 的工程化落地）

  • Basically Available（基本可用）：允许降级，如高峰时返回兜底页、排队、部分功能不可用，但核心流程不挂。
  • Soft state（软状态）：允许系统存在中间状态，数据有短暂不一致窗口（这是为了可用性主动放弃强一致的代价）。
  • Eventually consistent（最终一致）：经过一段时间后，数据最终收敛一致（如主从复制延迟最终追平）。

关系：CAP 是「理论」——告诉你在极端网络故障下 C/A 必须二选一；BASE 是「实践」——承认现实世界里做不到强一致，退而求其次追求最终一致 + 高可用。

一句话扛住追问：CAP 的 C 是「线性一致性」而非「最终一致」，A 是「能响应」而非「响应正确」，P 是「必然发生的网络故障」而非「可选」。系统在分区期间只能在 C 和 A 之间二选一，平时二者兼得。大多数互联网业务选 AP + BASE（最终一致），资金交易选 CP。
Raft 一致性算法：选举、日志复制、过半提交的完整原理高频已掌握

Raft 要解决的本质问题：让多个节点对「日志序列」达成一致，从而让多副本状态机输出一样的结果。Raft 把这个问题拆成三个可独立理解的子问题，这是它比 Paxos 好懂的原因。

角色与任期（Term）—— 一切的基础

  • 每个节点三种角色：Leader（领导者）、Follower（跟随者）、Candidate（候选者）。任期内最多一个 Leader。
  • Term（任期）：单调递增的整数，每次选举 +1。它是「逻辑时钟」，用来区分「新旧」——term 大的日志一定比 term 小的新，term 大的 Leader 一定比 term 小的权威。
  • 所有通信都带 term：收到更大 term，说明自己过期了，立即降为 Follower。

领导者选举（Leader Election）具体流程

  1. Follower 一段时间收不到 Leader 心跳，就超时，term+1，转成 Candidate，投自己一票。
  2. Candidate 向其他节点发投票请求，每个节点一个 term 只能投一票。
  3. 拿到多数票（过半）→ 当选 Leader；收到更大 term 的消息 → 转回 Follower；没人拿到多数 → 再等随机超时重新选举。
  4. 随机超时的作用（关键）：每个节点的超时时间随机（150~300ms），避免所有节点同时超时、同时竞选导致「永远选不出 Leader」的分裂问题。这是 Raft 设计的精髓。

日志复制（Log Replication）具体流程

  1. 客户端写请求只能发给 Leader，Leader 把命令追加到本地日志，同时发给所有 Follower。
  2. Follower 收到后追加到自己日志，返回确认。
  3. Leader 收到多数派（过半）确认后，这条日志标记为「已提交（committed）」，然后才应用到状态机并返回客户端。
  4. Leader 在后续心跳里带上「已提交到的索引」，Follower 据此也提交。

为什么是「过半提交」而不是「全部确认」？

这是最容易被追问、也最能体现理解深度的点：

  • 容错性：要求全部确认，任何一个节点故障就永远写不成功，系统不可用。过半提交允许最多 N/2-1 个节点宕机仍能正常写。
  • 唯一性保证（数学本质）：任意两个「多数派」集合必然有交集（比如 5 个节点，任何 3 个的集合，两两都至少共享 1 个节点）。这意味着：一旦某日志被「过半提交」，任何后续新 Leader（也必须是过半投票选出）一定包含这条日志，所以已提交的日志永远不会被覆盖或丢失。这就是「过半」能保证安全性的核心证明。

安全性（Safety）如何保证

  • 选举限制：Candidate 的日志必须「至少和多数派一样新」（term 更大，或 term 相同但索引更大），否则没资格当选。这保证新 Leader 一定包含所有已提交日志。
  • 日志匹配：Leader 通过「回退重试」强制 Follower 的日志与自己一致（发现不一致就把自己的日志往前推，直到找到一致点再覆盖）。

为什么本地时钟（墙上时钟）不可靠？

  • 漂移（Drift）：每台机器的晶振频率有微小差异，长时间运行后各机器时钟误差累积（一天可能差几秒到几十秒）。
  • 回拨（Jump back）：NTP 校时、管理员手动改时间、虚拟机迁移，时钟会往回调。
  • 后果：无法用 System.currentTimeMillis() 判断「跨机器的事件先后顺序」——A 机器 12:00:01 发生的事，B 机器可能记录成 11:59:59。

Lamport 逻辑时钟 —— 解决「因果顺序」

核心：不用真实时间，用「计数 + 消息传递修正」来定义事件先后。

  • 每个节点维护一个计数器 C，本地事件发生时 C = C + 1。
  • 发消息时带上自己的 C；收到消息时，C = max(自己的 C, 收到的 C) + 1。
  • 能保证：若事件 A「因果先于」事件 B（A 影响了 B），则 A 的时间戳 < B 的时间戳。
  • 不能保证：反推不成立——时间戳小不代表因果先于（两个并发事件可能时间戳一大一小）。所以 Lamport 时钟只能判断「偏序」，不能判断「全序」。

向量时钟 —— 解决「并发关系」

Lamport 的升级：每个节点维护一个向量 [C1, C2, ..., Cn]，记录「自己认为的每个节点的时钟」。

  • 本地事件：自己的分量 +1。
  • 收到消息：逐分量取 max，再自己的分量 +1。
  • 能判断并发：比较两个向量的每个分量——如果 A 全 ≤ B 且至少一个 <，则 A 先于 B；如果「A 有的分量大、B 有的分量大」互相交错，则 A、B 是并发事件（无因果关系）。

真实世界的方案

  • Google Spanner 的 TrueTime：用 GPS + 原子钟给每个数据中心提供全局误差有界的时钟（误差在毫秒级），配合「提交等待」实现跨机房强一致事务。这是「用硬件解决时钟问题」的极致。
  • 工程折中：大多数系统不追求严格全局时序，而是「用单调递增的 ID/版本号」替代「真实时间」。
关联雪花算法：雪花 ID 依赖机器时间戳，时钟回拨会生成重复 ID，这是分布式 ID 的核心难点（详见模块四）。这正是「本地时钟不可靠」在工程上最典型的体现。

② 分布式锁 Redis · Redisson · Zookeeper · RedLock

Redis 分布式锁：四个坑的具体场景 + 正确实现必考已掌握

坑 1：加锁非原子 → 死锁

错误写法：SETNX key value 成功后，再单独 EXPIRE key 30。如果两步之间进程崩溃（如 SETNX 后、EXPIRE 前宕机），这个 key 永远不过期，其他线程永远拿不到锁 → 死锁。

解决：用 SET key value NX EX 30，一条命令同时完成「互斥 + 过期」，原子性由 Redis 单线程保证。

坑 2：误删别人的锁

场景：线程 A 拿到锁，业务执行超过 30 秒，锁自动过期；线程 B 抢到锁开始执行；此时 A 执行完去 DEL key，把 B 的锁删掉了，导致 C 又能进来 → 三个线程同时执行。

解决：加锁时 value 存唯一标识（UUID + 线程 ID），释放时校验「是不是自己加的锁」再删。

坑 3：释放非原子（校验 + 删除分两步）

场景：A 先 GET 校验 value 是自己，正要 DEL 的瞬间，锁恰好过期、B 抢到锁；A 再 DEL，又把 B 的锁删了。校验和删除之间有时间窗口，仍可能误删。

解决：用 Lua 脚本把「判断 + 删除」合并成一次原子操作（Redis 单线程执行 Lua，中间不会被其他命令插入）。

坑 4：锁提前过期（业务没执行完）

场景：业务要执行 60 秒，锁 30 秒过期，前 30 秒后锁没了，其他线程进来 → 并发执行。

解决：看门狗自动续期（Redisson 的 Watch Dog），或把过期时间设得足够长（但太长又增加宕机后锁占用时间，本质是「续期」更优）。

正确实现（完整版）

// 加锁：原子（互斥 + 过期 + 唯一标识）
SET lock_key {uuid:threadId} NX EX 30

// 解锁：Lua 原子（校验 owner 再删）
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
四个坑一句话：加锁要原子（SET NX EX）、value 要唯一（防误删）、解锁要 Lua 原子（防竞态）、过期要续期（看门狗）。缺一个都有并发或死锁风险。面试把四个坑的场景讲清楚，比背命令强得多。
Redisson 看门狗：自动续期 + 可重入的底层实现高频已掌握

看门狗解决的核心矛盾

锁的过期时间是个两难：设短了业务没执行完锁就过期（并发）；设长了一旦客户端宕机，锁长时间占着（别人一直等）。看门狗用「自动续期」同时解决这两个问题——锁默认短，但只要业务还在跑，就一直续，不跑就自动过期。

续期机制（定时任务）

  • 加锁时不手动指定 leaseTime，Redisson 默认给锁设 30 秒过期。
  • 同时启动一个后台定时任务，每 30 / 3 = 10 秒执行一次。
  • 每次检查：锁是否还被当前线程持有？是 → 用 Lua 把过期时间重置回 30 秒。
  • 业务执行完 unlock 时，取消定时任务。
  • 为什么是 1/3：10 秒续一次，即使某次续期失败，也还有 20 秒缓冲，来得及下次续上，不会让锁在续期间隙过期。

可重入的底层结构（关键）

Redisson 的锁在 Redis 里不是一个普通 string，而是一个 Hash：

lock_key = {
  "线程ID": 2    // field 是线程标识，value 是「重入次数」
}
  • 同一个线程重复 lock，就把 value +1（重入）；每次 unlock 就 -1。
  • value 减到 0，才真正删除这个 Hash（真正释放锁）。
  • 用 Hash 而不是 string，才能同时记录「谁持锁 + 持了几层」，这是可重入的必要条件。

什么情况下看门狗不生效（易错）

  • 手动指定了 leaseTime：lock(10, TimeUnit.SECONDS)，此时不启动看门狗，锁到 10 秒就过期。
  • 所以：要么「不传时间，让看门狗自动续」，要么「自己算好时间，接受固定过期」。
易错点：看门狗只保护「未指定 leaseTime」的锁。很多人以为 Redisson 无条件自动续期，其实手动指定时间后就没了。这是面试官爱考的细节。

Zookeeper 加锁流程（临时顺序节点）

  1. 每个客户端在锁路径 /lock 下创建临时顺序节点，如 /lock/0000001。
  2. 判断自己是不是序号最小的节点：是 → 获锁；否 → watch 前一个节点（只盯前一个，避免惊群效应）。
  3. 前一个节点被删除（释放或宕机），自己被唤醒，再次判断，如此「排队」。

为什么 ZK 更「可靠」—— 会话（Session）机制

  • 客户端和 ZK 建立会话，客户端通过心跳维持会话。
  • 客户端宕机 → 心跳中断 → 会话超时 → ZK 自动删除该客户端创建的临时节点 → 锁自动释放。
  • 这是「靠服务端感知客户端存活」来释放锁，比 Redis「靠过期时间猜」更可靠——不依赖时钟，没有 GC 停顿导致的误判。

为什么 Redis 更快、ZK 更慢

  • Redis：加锁是单条命令、纯内存，几微秒到几十微秒。
  • ZK：写节点要过半同步 + 落盘（保证 CP），有网络往返和磁盘 IO，毫秒级。
选型一句话：「性能优先、能接受极低概率锁异常 + 业务幂等兜底」→ Redis；「一致性优先、锁的绝对正确性比性能重要（金融、主节点选举）」→ Zookeeper。面试关键不是背结论，而是说清「AP 丢锁 vs CP 慢」这个本质取舍。
RedLock 为什么有争议？Martin Kleppmann 的致命反驳加分已掌握

RedLock 想解决什么问题

Redis 单节点 + 主从架构有个隐患：主从切换丢锁。客户端在 master 上加锁成功，master 还没来得及同步给 slave 就宕机，slave 升主后锁不存在了，另一个客户端又能加锁 → 两个客户端同时持锁。RedLock 的思路是：不依赖主从，在 N 个独立节点（通常 5 个）上分别加锁，过半成功才算成功。

RedLock 的加锁流程

  1. 客户端向 5 个独立 Redis 节点依次尝试加锁（每个带过期时间）。
  2. 统计成功数：成功 ≥ 3（过半），且总耗时小于锁的有效期，才算加锁成功。
  3. 失败则向所有节点发释放请求，然后重试。

Martin Kleppmann 的反驳（这是面试加分点）

分布式系统权威 Martin Kleppmann 写了《How to do distributed locking》正面质疑 RedLock，核心论点是：RedLock 依赖「时钟」来保证互斥，而时钟本身不可靠，所以它的安全性假设是错的。

  • 反驳 1——GC 停顿：客户端 A 拿到锁后，发生 Full GC 停顿（STW 可能几秒甚至几十秒），超过锁的过期时间。等 A 恢复，锁早已过期、被 B 抢走，A 却以为自己还持有锁继续操作 → 两个客户端同时操作。任何依赖「过期时间」的锁都逃不掉这个问题，RedLock 也一样。
  • 反驳 2——时钟跳变：节点时钟回拨或跳变，会导致锁的「过期时间」判断失真，锁在「不该过期的时候」过期。
  • 反驳 3——核心结论：真正保证互斥的正确做法是 Fencing Token（栅栏令牌）——锁要返回一个单调递增的令牌，写数据时校验令牌，旧令牌的请求被拒绝。这样即使 A 停顿后锁被 B 抢走，A 恢复后拿旧令牌去写，也会被拒绝，从存储层兜住互斥，而不是依赖不可靠的时钟。

正确认识 RedLock

  • RedLock 确实解决了「主从切换丢锁」这一个具体问题，但没有解决「时钟/GC 导致的锁失效」这个更根本的问题。
  • Redis 官方作者 antirez 曾反驳 Kleppmann，但学界和工业界普遍更认可 Kleppmann 的论证。
  • 工业实践：RedLock 很少被真正采用。要么用 Zookeeper（强一致 + 会话机制），要么用「单节点 Redis + 看门狗 + 业务幂等 / Fencing Token」兜底。
面试高分答法：先承认 RedLock 解决「主从丢锁」，再点出它「依赖时钟、挡不住 GC 停顿」的根本缺陷，最后给出「Fencing Token / 业务幂等才是真正兜底」的结论。能讲到 Fencing Token，说明你真的懂分布式锁的本质。

③ 分布式事务 2PC · 3PC · TCC · SAGA · Seata

2PC / 3PC：两阶段提交的完整流程与致命缺陷高频已掌握

2PC（Two-Phase Commit，两阶段提交）

本质：一个协调者（Coordinator）+ 多个参与者（Participant），通过两轮通信达成「要么全提交，要么全回滚」。

  1. 阶段一 · 准备（Prepare）：协调者向所有参与者发「准备提交」请求；每个参与者执行本地事务但不提交，锁定所需资源，返回 ready 或 abort。
  2. 阶段二 · 提交/回滚（Commit/Rollback）：协调者收到全部 ready → 发「提交」指令，所有参与者提交；任一返回 abort → 发「回滚」指令，全部回滚。

2PC 的三个致命缺陷（面试重点）

  • 同步阻塞：阶段一所有参与者锁定资源，等待「最慢的那个参与者」响应。只要一个卡住，所有参与者一起阻塞，资源长时间占用，吞吐量极低。
  • 单点故障：协调者是整个事务的「大脑」。协调者在阶段二发出部分提交指令后宕机，参与者会陷入「不知道该提交还是回滚」的僵局，一直阻塞。
  • 数据不一致：阶段二协调者给 A 发了「提交」、给 B 的「提交」因网络丢失，此时 A 已提交、B 未提交 → 数据不一致。这是 2PC 无法用「重试」解决的（重试会导致 A 重复提交）。

3PC（三阶段提交）如何改进？改进有限

  1. CanCommit：先轻量询问「大家能不能提交」（不执行事务，不锁资源）。
  2. PreCommit：同 2PC 的准备阶段。
  3. DoCommit：提交阶段。

3PC 引入超时机制：参与者等待超时后自动提交（降低阻塞，避免 2PC 的「僵局」）。但代价是：如果协调者是因为「要回滚」才宕机的，参与者超时后却自动提交了，反而造成不一致。所以 3PC 只是缓解，没根治，而且多一轮通信、性能更差，实际很少用。

为什么互联网不用 2PC/3PC

  • 它追求「强一致 + 同步阻塞」，性能差、可用性差，与互联网「高并发、高可用」天然冲突。
  • 它适合「低并发、短事务、对一致性要求极高」的场景，典型是数据库的 XA 事务（跨库分布式事务）。
  • 互联网场景用「最终一致」方案（TCC、SAGA、消息事务）替代。
一句话扛住追问：2PC 的「同步阻塞 + 协调者单点 + 阶段二网络分区导致不一致」是三个无解的缺陷，3PC 加超时只是缓解阻塞、反而引入「自动提交导致不一致」的新问题。所以互联网场景弃用，转向最终一致。
TCC 和 SAGA：补偿式事务的原理、空回滚与悬挂必考已掌握

TCC（Try / Confirm / Cancel）

TCC 的核心思想：把「业务」本身设计成可预留、可确认、可撤销的三段，不依赖数据库事务，而是靠「业务补偿」实现一致性。

  • Try（预留）：检查资源、预留（如冻结库存、预扣余额），不改最终状态。
  • Confirm（确认）：真正扣减，把预留变成实际（如冻结 → 扣款）。
  • Cancel（取消）：释放预留，回滚（如解冻库存）。

优点：不锁数据库资源（预留是业务层面的），性能比 2PC 好，隔离性可控。缺点：每个业务要写三个方法，代码侵入大、开发成本高。

TCC 的两个经典难题（面试高分点）

  • 空回滚（Empty Rollback）：Try 阶段因网络超时没真正执行，但协调者以为失败了，调用了 Cancel。此时 Cancel 要「取消一个根本没发生的预留」，必须能识别并幂等处理（记录 Try 是否成功）。
  • 悬挂（Suspension）：Cancel 先于 Try 到达（网络乱序）。Cancel 执行完，迟到的 Try 才到并执行了预留 → 资源被预留了但没人会再取消，造成「悬挂」。解决：Cancel 后标记状态，Try 到达时发现已 Cancel 就直接拒绝。

SAGA（长事务补偿）

把长事务拆成一串本地事务 T1 → T2 → ... → Tn，每个本地事务对应一个补偿操作 C1 → C2 → ... → Cn。

  • 正向执行：T1 成功 → T2 成功 → ...。
  • 某步失败（如 T3 失败）：逆序执行补偿 C2 → C1，把前面已成功的步骤撤销。
  • 优点：无资源锁定（各本地事务独立提交），适合长流程（下单、跨系统审批）。
  • 缺点：无隔离性——T1 提交后、整个 SAGA 完成前，中间状态会被其他请求读到；且补偿操作本身也可能失败，需要「补偿的补偿」或人工介入。

TCC vs SAGA 怎么选

维度TCCSAGA
隔离性较好（Try 预留资源）无隔离（中间态可见）
代码侵入大（写三个方法）中（写补偿方法）
适用核心资金、需强预留（扣款、减库存）长流程、多步骤、允许中间态
一句话扛住追问：TCC 是「预留式」，靠 Try/Confirm/Cancel 保证隔离，但要处理「空回滚 + 悬挂」；SAGA 是「补偿式」，靠逆序补偿撤销，但没有隔离性。能说出空回滚和悬挂，说明你真正做过 TCC 而不是背概念。
本地消息表 / RocketMQ 事务消息：最终一致的完整链路高频已掌握

先理解核心矛盾

「本地事务」和「发消息」是两件事，如何保证「业务成功」和「消息发出」要么都成功、要么都不成功？这是消息最终一致要解决的根本问题。

方案一：本地消息表（最朴素，最可控）

  1. 业务操作 + 写消息记录，放在同一个本地数据库事务里（消息表字段：消息内容、状态=待发送、重试次数）。
  2. 事务提交后，后台定时任务扫描「待发送」消息，投递到 MQ。
  3. 消费方处理成功后，回调更新消息状态为「已完成」（或发确认消息）。
  4. 超时未完成的消息，重试；重试多次仍失败 → 人工对账。

优点：实现简单、不依赖特殊 MQ 能力，任何 MQ 都能用。缺点：要维护消息表、要写定时任务，有代码侵入。

方案二：RocketMQ 事务消息（把「本地事务 + 发消息」原子化）

  1. 发送半消息（half message）：消息先到 Broker，但消费者暂时看不到（处于中间态）。
  2. 执行本地事务（如扣款、减库存）。
  3. 本地事务成功 → commit，半消息变可见，消费者才能消费；失败 → rollback，半消息被丢弃。
  4. 若 Broker 长时间没收到 commit/rollback（如生产者宕机），Broker 主动回查（check）生产者的本地事务状态，决定提交还是回滚。

关键：「半消息 + 事务回查」机制，把「本地事务」和「消息」绑定成原子操作，生产者不用自己维护消息表和定时任务。

两种方案的共同前提（缺一不可）

  • 消息不丢：至少一次投递（同步发送 + 重试 + 落盘）。
  • 消费端幂等：消息可能重复投递，消费方必须幂等（去重表 / 唯一索引），否则重复消费造成数据错误。
核心认知：「最终一致」不是「不用保证一致性」，而是「用异步 + 重试 + 幂等，在可接受的时间内收敛到一致」。消息事务解决的只是「发消息和业务的一致性」，「消费处理的一致性」要靠幂等兜底。
Seata AT 模式：无侵入的底层原理 + 全局锁 + 脏写问题必考已掌握

AT 模式三角色（先理清架构）

  • TC（Transaction Coordinator）：Seata Server，全局事务的「总调度」，维护全局事务和分支事务的状态。
  • TM（Transaction Manager）：业务发起方，标注 @GlobalTransactional，负责开启/提交/回滚全局事务。
  • RM（Resource Manager）：每个参与的分支事务（各微服务），负责注册分支、生成 undo_log、执行本地提交/回滚。

无侵入的核心：SQL 解析 + undo_log（这是 AT 的精髓）

AT 模式不用改业务代码，靠的是在本地事务执行前后，自动拦截 SQL、记录数据的前后镜像：

  1. 一阶段：业务 SQL 执行时，Seata 代理解析 SQL，记录 before image（改前数据）；SQL 执行后记录 after image（改后数据），两者存入 undo_log 表（和业务数据在同一本地事务里）。
  2. 二阶段提交：全局事务所有分支都成功，TC 通知各 RM 删除 undo_log（异步，很快）。
  3. 二阶段回滚：任一分支失败，TC 通知各 RM 用 before image 生成反向 SQL，把数据改回去，然后删除 undo_log。

为什么无侵入：因为它只记录「数据快照」，回滚时「用快照反向还原」，不需要业务提供 Cancel 方法（对比 TCC 要写三个方法）。

AT 模式的三个代价/坑（面试高分点）

  • 全局锁（降低并发）：一阶段执行时，对涉及的数据加全局锁，防止其他全局事务同时修改同一行。锁直到全局事务结束才释放，写冲突时性能下降明显（比单机事务锁粒度更粗、时间更长）。
  • 脏读风险：AT 模式一阶段本地事务就「提交」了（暴露 after image），所以默认隔离级别相当于读未提交——其他请求在全局事务未结束时，可能读到「未提交」的中间数据。
  • 脏写风险（回滚冲突）：如果全局事务回滚时，数据已被「另一个全局事务」修改（after image 对不上），Seata 需要做冲突处理，否则会把别人的写入覆盖掉。

Seata 四种模式对比

模式侵入性隔离性性能适用
AT无（自动 SQL 解析）读未提交（有脏读）中（全局锁）多数业务通用
TCC高（写三方法）好（预留）高核心资金
SAGA中（写补偿）无高长流程
XA无（DB 原生）强一致低跨库强一致
一句话扛住追问：AT 模式「无侵入」的本质是「SQL 解析 + before/after 镜像 + undo_log」，回滚靠「反向 SQL 还原」而非业务补偿。代价是「全局锁降低并发 + 读未提交的脏读 + 脏写冲突」，这也是它和 TCC 的核心区别。

④ 分布式 ID 雪花 · 号段 · 时钟回拨

雪花算法：64 位结构的精确拆解 + 为什么趋势递增对 MySQL 友好必考已掌握

64 位结构逐位拆解

段位数精确含义
符号位1 bit固定 0，保证是正数（long 类型最高位）
时间戳41 bit相对某个起点（epoch）的毫秒数，可表示 2^41 ≈ 69.7 年
机器 ID10 bit2^10 = 1024 台（常拆成 5 位机房 + 5 位机器）
序列号12 bit2^12 = 4096，同一毫秒内最多 4096 个

为什么能全局唯一（三个维度各司其职）

  • 时间戳：毫秒不同 → ID 必不同；且保证整体趋势递增。
  • 机器 ID：不同机器生成 → 即便同一毫秒也不冲突（机器 ID 不同）。
  • 序列号：同一机器同一毫秒内，序列号从 0 递增到 4095，用尽则等下一毫秒。
  • 三者组合，无需中心协调，各机器「各算各的」也天然唯一。

为什么「趋势递增」对 MySQL 特别友好（高频追问）

  • InnoDB 主键是聚簇索引，数据按主键顺序物理存储（B+ 树叶子节点）。
  • 递增 ID：新数据总是追加到 B+ 树最右侧，顺序写入，几乎不产生页分裂，磁盘顺序 IO，插入性能高。
  • 随机 ID（如 UUID）：新数据随机插入 B+ 树中间，触发大量页分裂和随机 IO，还会导致索引碎片、写放大。
  • 所以雪花「趋势递增」虽然不像自增那样严格连续，但已足够让 MySQL 高效。

雪花的优缺点

  • 优点：无中心（不依赖 DB/Redis）、高性能（纯内存位运算）、趋势递增、可反解出时间戳和机器。
  • 缺点：ID 长（18-19 位）、依赖机器时钟（回拨会重复，见下一题）、不严格连续。
一句话扛住追问：雪花 = 41 位时间戳（趋势递增）+ 10 位机器 ID（隔离机器）+ 12 位序列号（同毫秒内区分），三者组合保证「无中心也全局唯一」。趋势递增对 InnoDB 聚簇索引友好——顺序写入减少页分裂，这是它优于 UUID 的根本原因。
雪花算法时钟回拨：四种对策的原理与权衡必考已掌握

为什么会时钟回拨

  • NTP 校时：系统定期向时间服务器同步，本地时钟快了就会被「往回拨」。
  • 人为改时间：运维手动调整系统时间。
  • 虚拟机迁移：虚拟机漂移时，宿主机的时钟可能比原宿主机慢。

危害：时间戳变小 → 可能生成和「之前某毫秒」相同的 ID → 全局唯一性被破坏。

四种对策（从简单到复杂）

  1. 等待法（回拨量小时）：记录「上一次生成的时间戳」，发现当前时间戳 < 上次，就自旋等待，等时钟追上后再生成。适合回拨几秒内的场景。
  2. 拒绝法（回拨量大时）：回拨量超过阈值（如 5 秒）直接抛异常，让上游重试或人工处理，避免生成重复 ID。
  3. 备用时钟（兜底）：维护一个「上次时间戳」作为逻辑基准，回拨时不用系统时钟，而是用「基准 + 1」继续递增。优点是不阻塞，缺点是 ID 的时间戳「不真实」，可能和真实时间脱节。
  4. 美团 Leaf-snowflake（分布式校准）：所有节点定时把时间戳上报到 Zookeeper，共享一个「全局时间基准」。生成 ID 时和 ZK 里的基准对比，发现本机时钟落后于全局基准，说明回拨了，就等待或报警。

工程上的组合策略

实践中通常是「小回拨等待 + 大回拨拒绝 + 监控告警」组合：回拨几毫秒就等，回拨几秒就报警并拒绝，同时监控时钟偏移。

关键认知（面试高分）：时钟回拨是雪花算法的「固有缺陷」，本质是「本地时钟不可靠」（呼应模块一的时钟问题）。它无法被彻底消除，只能「检测 + 缓解」。如果业务对 ID 唯一性要求极高、且接受不了时钟风险，就改用「号段模式」或「数据库自增」这类不依赖时钟的方案。
号段模式（美团 Leaf）：双 buffer 预取原理 + 与雪花对比高频已掌握

号段模式原理

  1. 数据库维护一张 segment 表，每个业务一个 key，记录当前的 max_id。
  2. 服务启动时，用 UPDATE ... SET max_id = max_id + step（原子）批量取一段 ID（如一次 1000 个），缓存在内存里。
  3. 内存里从 [max_id+1, max_id+step] 逐个分配，用完再去数据库取下一段。

双 buffer 预取（Leaf 的核心优化）

普通号段模式有个问题：当前段快用完时，去数据库取下一段会有网络延迟，可能让取号线程短暂阻塞。

  • Leaf 维护两个号段 buffer：当前段正在用，另一段提前异步预取好。
  • 当前段用尽时，无缝切换到已经预取好的段，同时后台再去补下一段。
  • 这样取号几乎永远不阻塞数据库，性能和纯内存的雪花接近。

号段模式 vs 雪花算法

维度号段模式雪花算法
ID 形态短、纯数字（严格递增）长（18-19 位）
时钟依赖不依赖时钟（无回拨问题）依赖时钟，有回拨风险
递增性严格连续递增趋势递增（大致有序）
依赖依赖数据库（有中心）无中心
性能高（批量 + 双 buffer）高（纯计算）

怎么选

  • 号段模式：需要「短、纯数字、严格连续」的 ID（如订单号、编号），且能接受数据库作为中心 → 用号段。
  • 雪花：需要「无中心、极致性能、可反解时间戳」，且能接受时钟风险 → 用雪花。
  • 美团 Leaf 实际上两种都提供（leaf-segment 和 leaf-snowflake），按业务选。
一句话扛住追问：号段模式是「数据库批量取号 + 双 buffer 异步预取」，用「有中心」换来了「不依赖时钟、严格递增、ID 短」，完美规避了雪花的时钟回拨缺陷。两者没有绝对优劣，看业务要「连续短 ID」还是「无中心高性能」。

⑤ 缓存三大问题 穿透 · 击穿 · 雪崩 · 一致性

缓存穿透 + 布隆过滤器：误判率的本质与为什么不能删除必考已掌握

缓存穿透是什么

查询一个缓存和数据库都不存在的数据（如恶意构造不存在的 ID）。因为缓存和 DB 都没有，每次请求都会穿透缓存直达 DB，大量请求能把 DB 打垮。

三种解决方案

  • 缓存空值：查不到也缓存一个「空标记」（短过期时间），下次直接返回空，不打 DB。缺点：空值缓存占内存，且若攻击者用大量不同 ID，空值缓存也扛不住。
  • 布隆过滤器：在缓存前加一道「可能存在」的判断，不存在直接拦截。
  • 参数校验：非法 ID（负数、超长、格式不对）直接拒绝，这是第一道也是最便宜的防线。

布隆过滤器原理（bitmap + 多个 hash）

  1. 底层是一个很长的 bit 数组（全 0），外加 k 个 hash 函数。
  2. 写入 key：用 k 个 hash 函数算出 k 个位置，把对应 bit 置 1。
  3. 查询 key：算出同样的 k 个位置，只要有一个是 0 → 一定不存在；全部是 1 → 可能存在。

误判的本质（面试高分点）

  • 只会「误判存在」，不会「误判不存在」——这是它最关键的数学性质。因为「存在」的判断是「k 个位置都是 1」，而这 k 个 1 可能是别的 key 写入时留下的（哈希碰撞），不代表这个 key 真的被写过。
  • 误判率受三个参数控制：bit 数组长度 m、hash 函数个数 k、元素数量 n。m 越大、k 合适、n 越小，误判率越低。最优 k ≈ (m/n) * ln2。
  • 为什么不能删除元素：一个 bit 可能被多个 key 共用，删掉它会影响别的 key 的判断。所以布隆过滤器要么「只增不删」，要么用「计数布隆（counting bloom filter）」或定期重建。

布隆过滤器的适用边界

  • 适合「大量 key 大概率不存在」的场景：缓存穿透防护、黑名单、爬虫 URL 去重、防止恶意查询。
  • 不适合「需要精确判断、需要删除、数据量大到内存装不下」的场景。
  • 因为会误判「存在」，所以布隆过滤器说「存在」时，后面仍要查 DB 兜底——它只负责「挡住确定不存在的」，不负责「确认存在」。
面试关键：能说清「布隆过滤器只会假阳性（误判存在）、不会假阴性（漏判不存在），所以它是『拦截器』而非『数据库』，后面永远要有真实数据源兜底」，说明你真正理解它，而不是背了个名字。
缓存击穿：互斥锁 vs 逻辑过期，本质是「一致性 vs 可用性」必考已掌握

击穿是什么

单个热点 key 过期的一瞬间，大量并发请求同时发现缓存失效，同时去查 DB 重建缓存，DB 瞬间承受巨大压力。区别于雪崩（大量 key 同时过期）和穿透（数据本来就不存在）。

方案一：互斥锁（保证一致性）

  1. 缓存未命中时，先抢一个分布式锁（如 SETNX）。
  2. 抢到锁的唯一线程去查 DB、重建缓存；其他线程抢锁失败，等待 + 重试读缓存。
  3. 重建完成后释放锁，其他线程从缓存读到新数据。

特点：只让一个线程打 DB，其余线程等待；保证「读到的一定是重建后的新数据」。代价：重建期间其他线程要等待（短暂阻塞），可用性略降。

方案二：逻辑过期（保证可用性）

  1. 缓存的 value 里额外存一个「逻辑过期时间」，但物理上不过期（不设 Redis TTL，或设超长 TTL）。
  2. 读取时判断逻辑时间：没过期 → 直接返回；过期了 → 先返回旧数据（保证不阻塞），同时异步开一个线程去查 DB 重建缓存。
  3. 重建用互斥锁防止多个线程同时重建。

特点：请求永远不阻塞（立即返回旧数据），可用性最高。代价：短暂返回旧数据，一致性略降。

本质：一致性 vs 可用性的权衡（呼应 CAP）

维度互斥锁逻辑过期
一致性高（不返回旧数据）低（短暂旧数据）
可用性略降（重建期间等待）高（永不阻塞）
实现复杂度简单较复杂（异步重建）
适用一致性优先（价格、库存）可用性优先（资讯、榜单）
一句话扛住追问：击穿的本质是「热点 key 过期瞬间的流量洪峰」。互斥锁用「只让一个线程重建」保证一致性，但重建期间阻塞；逻辑过期用「返回旧数据 + 异步重建」保证可用性，但短暂不一致。选哪个取决于业务是「一致性优先」还是「可用性优先」，这是 CAP 在缓存场景的具体体现。
缓存雪崩：两种成因 + 分层预防必考已掌握

雪崩的两种成因（要分清，这是追问点）

  • 成因 1 · 缓存集体过期：大量 key 在同一时刻过期（比如批量写入时都设了相同 TTL），缓存瞬间集体失效，流量全打到 DB。
  • 成因 2 · Redis 宕机：缓存服务本身挂了，所有请求直接穿透到 DB。

针对「集体过期」的预防

  • 过期时间加随机值：TTL = base + random(0, 300)，把过期时间打散，避免「同一时刻集体失效」。
  • 热点 key 预热：大促前、活动前，提前把热点数据加载进缓存并设合理 TTL。

针对「Redis 宕机」的预防（多级冗余）

  • Redis 高可用：主从 + 哨兵 / 集群，保证 Redis 不单点，宕机能自动切换。
  • 多级缓存：本地缓存（Caffeine/Guava）作为 Redis 的上一级，Redis 挂了本地缓存兜底，减少直接打 DB。
  • 降级熔断：DB 前面加限流 / 熔断，即使打过来了也挡住，保护 DB 不被压垮。

分层预防的完整链路

「错峰过期（防同时失效）→ 多级缓存（防单点失效）→ 高可用集群（防 Redis 挂）→ 限流熔断（防 DB 被压垮）」，四层层层设防。

一句话扛住追问：雪崩有「集体过期」和「Redis 宕机」两种成因。前者靠「过期时间加随机值 + 预热」解决，后者靠「Redis 高可用 + 多级缓存 + 限流熔断」解决。核心是「错峰 + 冗余 + 兜底」三层，缺一层都可能雪崩。
缓存一致性：为什么「先更新 DB 再删缓存」+ 三种补偿方案必考已掌握

Cache Aside（旁路缓存）模式

  • 读：先查缓存，命中返回；未命中查 DB，把结果写回缓存。
  • 写：先更新 DB，再删除缓存（注意是「删」不是「更新」）。

为什么是「删缓存」而不是「更新缓存」：更新缓存可能造成「并发写覆盖」——两个写请求先后更新 DB，但缓存更新顺序反了，导致缓存是旧值。删缓存让下一次读自然重建，规避了并发写顺序问题。

为什么「先更新 DB，再删缓存」（核心论证）

对比「先删缓存，再更新 DB」：

  • 先删缓存：删完缓存后、更新 DB 前，其他读请求会读到旧数据并把它写回缓存，导致缓存一直是脏的，且这个脏数据要等下次更新才被清。
  • 先更新 DB，再删缓存：也有极小窗口（更新 DB 后、删缓存前，读到旧值），但这个窗口概率更低、影响更小——因为「更新 DB 后马上删缓存」这个动作很快，且读请求通常远多于写请求。

「先更新 DB 再删缓存」仍有缺陷，需要补偿

  • 问题 1 · 删缓存失败：DB 更新成功了，但删缓存失败 → 缓存永远是旧数据。这是最需要处理的。
  • 补偿方案 A · MQ 重试：删缓存失败时，发一条消息到 MQ，由消费者异步重试删除。
  • 补偿方案 B · Canal 监听 binlog：用 Canal 监听 MySQL 的 binlog，DB 一变就自动删缓存，把「删缓存」从业务代码里解耦出来。
  • 补偿方案 C · 延迟双删：先删缓存 → 更新 DB → 延迟几百毫秒再删一次，用「第二次删」兜住「更新 DB 期间有读请求写回旧值」的窗口。

终极认知：缓存一致性没有银弹

  • 缓存和 DB 是两个独立的存储，任何方案都无法做到「绝对实时强一致」，本质是最终一致。
  • 要强一致，只能「读写串行化」（读写都加锁），代价是性能暴跌，一般不用。
  • 工程上最优解：先更新 DB + 删缓存 + 失败补偿（MQ/Canal）+ 兜底对账。
一句话扛住追问：写操作用「先更新 DB 再删缓存」是为了规避「并发写覆盖」和「先删缓存被读请求写回脏数据」。它的软肋是「删缓存失败」，用 MQ 重试 / Canal 监听 binlog / 延迟双删补偿。缓存一致性本质是最终一致，没有银弹，工程上用「更新库 + 删缓存 + 补偿」这个性价比最高的组合。

⑥ 幂等与限流 幂等设计 · 限流算法

接口幂等：五种方案的本质 + 各自适用场景必考已掌握

幂等的精确定义

同一操作执行一次和执行多次，产生的副作用（结果）相同。注意：幂等不是「不重复处理」，而是「重复处理不会造成错误结果」。

产生幂等需求的根源：分布式环境下，「请求超时」无法区分是「没执行」还是「执行了但响应丢了」，客户端只能重试；加上用户重复点击、MQ 重复投递，重复是必然的。

五种方案 + 本质

方案本质适用场景
数据库唯一索引靠「唯一约束」让重复插入失败插入类：下单、注册（订单号唯一）
Token 机制「一次性凭证」用完即失效表单提交、防重复点击
状态机靠「状态合法性」拒绝重复流转订单、审批流程
乐观锁 version靠「版本号」判断是否已被改过更新类：扣库存、改余额
Redis setnx靠「幂等标记」判断是否已处理通用去重标记

每个方案的原理细节

  • 唯一索引：重复请求插入时，主键/唯一键冲突抛异常，捕获后视为「已处理」返回成功。这是最可靠的兜底，因为它由数据库保证原子性。
  • Token：客户端先请求一个 token，提交时带 token，服务端「校验 token 存在 → 删除 token → 执行业务」，第二次提交时 token 已删，直接拒绝。核心是「token 的删除是原子的」。
  • 状态机：如订单「待支付 → 已支付」，重复支付请求发现状态已是「已支付」，直接返回成功，不做二次扣款。
  • 乐观锁：update ... set stock = stock-1, version = version+1 where version = ?，重复执行时 version 已变，影响行数为 0，判断为「已处理」。

组合使用才是正解

真实系统通常是「业务唯一标识 + 唯一索引兜底」：每个请求带一个全局唯一 ID（如订单号、幂等号），服务端先查/靠唯一索引判断是否已处理，再用状态机或乐观锁控制。单靠一种方案往往不够。

一句话扛住追问：幂等的本质是「给请求一个业务唯一标识，让服务端能识别重复，并让重复操作变得无害」。五种方案各有侧重：唯一索引最可靠（DB 保证）、Token 防重复提交、状态机防重复流转、乐观锁防重复更新、Redis setnx 做通用标记。关键场景（支付、下单、扣库存）必须幂等，且通常是「唯一标识 + 唯一索引」组合兜底。
限流算法：令牌桶和漏桶的本质区别 + 固定窗口的临界问题必考已掌握

四种算法对比

算法原理特点 / 缺陷
固定窗口计数器每 N 秒一个窗口，窗口内计数，超阈值拒绝简单，但「临界问题」：窗口交界处会突发 2 倍流量
滑动窗口窗口随时间滑动，统计最近 N 秒的请求数解决临界突刺，精度高，实现复杂
漏桶请求进桶，按固定速率流出，桶满拒绝速率恒定平滑，不能应对突发
令牌桶固定速率放令牌，请求拿令牌通过允许一定突发，最常用

固定窗口的「临界问题」（高频追问）

假设限流「每秒最多 100 次」。攻击者在「第 0.9 秒到第 1 秒」打 100 次、「第 1 秒到第 1.1 秒」再打 100 次——两次都在各自窗口内合规，但「跨窗口」的 0.2 秒内实际打了 200 次，是限流值的 2 倍。这就是固定窗口的临界突刺。滑动窗口（统计最近 1 秒内而非固定区间）能解决。

漏桶 vs 令牌桶的本质区别（面试核心）

  • 漏桶：控制的是「流出速率恒定」。无论请求怎么涌入，处理速率固定，超出的排队或丢弃。所以它「强制平滑」，把突发流量削平，适合需要「稳定输出、保护下游」的场景。
  • 令牌桶：控制的是「平均速率 + 允许突发」。桶里能积累令牌，空闲时攒令牌，突发时一次性消耗。所以它「允许短时突发」，适合「偶尔有尖峰、但平均不超」的场景。

一句话：漏桶「削峰填谷，恒速输出」；令牌桶「允许瞬时突发，控制平均速率」。互联网 API 网关、Sentinel 大多用令牌桶，因为业务流量天然有突发性。

工程落地

  • 单机：Guava RateLimiter（令牌桶实现）。
  • 分布式：Redis + Lua（原子）、Sentinel、Gateway RequestRateLimiter（底层也是 Redis + Lua）。
一句话扛住追问：固定窗口有「临界突刺」缺陷，滑动窗口解决；漏桶「恒速流出、削平突发」，令牌桶「允许突发、控平均速率」。能讲清「漏桶削峰 vs 令牌桶容忍突发」的区别，以及固定窗口的临界问题，就说明你真的懂限流算法。
Redis + Lua 分布式限流：为什么必须 Lua + 滑动窗口实现高频已掌握

为什么必须用 Lua（核心）

限流要「读计数 → 判断 → 自增 → 设过期」多个步骤，如果拆成多条 Redis 命令，中间会被其他请求「插队」，产生竞态（两个请求都读到 count=99，都判断没超，都放行 → 实际放了 101 个）。

Redis 单线程执行 Lua 脚本，脚本内的所有命令是原子的，中间不会被其他客户端命令打断。这就是「用 Lua 保证限流的原子性」的根本原因。

固定窗口实现（最简）

-- KEYS[1]: 限流key, ARGV[1]: 阈值, ARGV[2]: 过期秒数
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return 0  -- 拒绝
end
return 1      -- 放行

注意：INCR 后 EXPIRE 的写法，是为了处理「第一次 INCR 时 key 还没有过期时间」的边界——如果 INCR 后进程挂了没设 EXPIRE，key 就永不过期，所以要「第一次才设过期」。这也是一个容易被问的细节。

滑动窗口实现（解决临界突刺）

用 ZSET 记录每个请求的时间戳，value 用「时间戳 + 随机数」保证唯一：

-- KEYS[1]: 限流key, ARGV[1]: 当前时间戳, ARGV[2]: 窗口毫秒数, ARGV[3]: 阈值
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])  -- 删窗口外的
local count = redis.call('ZCARD', KEYS[1])                      -- 窗口内数量
if count >= tonumber(ARGV[3]) then
  return 0  -- 拒绝
end
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[1] .. '-' .. math.random())  -- 记录本次
redis.call('PEXPIRE', KEYS[1], ARGV[2])                        -- 设过期，防 key 堆积
return 1

权衡：滑动窗口精度高、无临界突刺，但 ZSET 内存和计算开销比计数器大。高并发下要权衡「精度 vs 开销」。

易错点：固定窗口的「INCR 后 EXPIRE」边界要处理（第一次才设过期，否则 key 永不失效）；滑动窗口要记得给 ZSET 设 PEXPIRE，否则窗口外的 key 会一直堆积占内存。

⑦ 高可用与消息可靠 架构高可用 · 消息三重保障

高可用架构：从「冗余 + 故障转移 + 容错」三个维度拆解必考已掌握

高可用的三根支柱（先给框架，面试有条理）

  • 冗余（Redundancy）：任何组件都至少 2 份，消除单点。
  • 故障转移（Failover）：某份挂了，能自动切到另一份。
  • 容错（Fault Tolerance）：故障发生时，能「隔离 + 降级」，不让它扩散。

四层架构逐层拆解

  1. 接入层：DNS（域名解析 + 多机房调度）→ CDN（静态加速 + 边缘缓存）→ LVS/Nginx（四层/七层负载均衡）。要点：无状态，可任意水平扩。
  2. 应用层：多实例水平扩容、无状态化（session 外置到 Redis）、优雅上下线（actuator 健康检查）、异步化（MQ 削峰）、缓存（Redis 抗读）。
  3. 容错层：超时（别让线程无限等）、重试（要幂等）、熔断（快速失败）、降级（兜底）、限流（保护自己）、隔离（线程池/信号量，防止级联）。
  4. 数据层：DB 主从 + 读写分离、分库分表、Redis 哨兵/集群、MQ 集群（多副本）。

高可用的量化指标（高频追问）

  • 可用性 = MTBF / (MTBF + MTTR)：MTBF 平均无故障时间，MTTR 平均修复时间。想提高可用性，要么「少故障」（提 MTBF），要么「快恢复」（降 MTTR）。

「消除单点」的具体清单（面试加分）

  • 应用：多实例 + 负载均衡。
  • Nginx：主备（keepalived 虚拟 IP）。
  • Redis：主从 + 哨兵（高可用）/ 集群（高可用 + 扩展）。
  • MySQL：主从 + 故障切换（MHA/Orchestrator）。
  • MQ：多副本 / 多 Broker 集群。
  • 注册中心：Nacos/Eureka 本身也要集群部署。
一句话扛住追问：高可用 = 冗余 + 故障转移 + 容错。冗余消除单点，故障转移保证自动切换，容错（超时/熔断/降级/限流/隔离）保证故障不扩散。量化看「几个 9」，本质是「降 MTTR + 提 MTBF」。最后一定补一个真实案例（如主库宕机切从库、缓存雪崩降级），这是区分「背答案」和「真做过」的关键。
消息不丢失：生产、存储、消费三段式的完整分析必考已掌握

一条消息从生产到消费，会在三个环节「可能丢失」，要逐段堵住。

第一段：生产端（发消息时丢）

  • 丢的原因：用「异步/单向发送（oneway）」，生产者不确认 Broker 是否收到，网络抖动或 Broker 宕机就丢。
  • 解决（RocketMQ）：用同步发送，拿到 SendResult 状态为 SEND_OK 才算成功；失败则重试。
  • 解决（Kafka）：acks=all（所有副本确认）+ retries 重试 + enable.idempotence=true（幂等，防重试导致的重复）。

第二段：Broker 存储端（存储时丢）

  • 丢的原因：消息写进内存（page cache）就返回，还没落盘就宕机 → 丢；或主节点挂了、从节点还没同步 → 丢。
  • 解决（RocketMQ）：同步刷盘（SYNC_FLUSH，落盘才返回）+ 同步复制（master 同步到 slave 才确认）。
  • 解决（Kafka）：min.insync.replicas 保证最少同步副本数，acks=all 配合。

第三段：消费端（消费时丢）

  • 丢的原因：自动提交 offset——消息一到就自动 ACK，但业务处理失败/进程崩溃，这条消息就被「确认」了，永远不会再消费。
  • 解决：手动提交 offset，业务处理成功后再提交。这样处理失败的消息不会被确认，下次会重新消费。

「不丢」的代价（高频追问）

  • 同步刷盘、同步复制都是「用延迟/吞吐换可靠性」，消息落盘 + 多副本确认都会显著降低吞吐。
  • 所以不是所有消息都要「绝对不丢」：核心业务消息（支付、订单）严格配置，日志、埋点可以异步。
一句话扛住追问：消息不丢要堵三段：生产端「同步发送 + 重试」、Broker 端「同步刷盘 + 主从同步复制」、消费端「手动 ACK，处理成功才提交」。代价是性能下降，所以只对关键消息严格配置。能讲清「每段丢在哪、怎么堵」，比背参数强。
消息不重复、不乱序：为什么「不可兼得」+ 局部有序方案必考已掌握

为什么消息一定会重复（先理解根因）

  • 消息系统的投递语义是 at-least-once（至少一次）：为了保证「不丢」，消费端处理成功后才 ACK，但如果「处理成功了、ACK 还没发出去就网络断了」，Broker 会认为没消费，重新投递 → 重复。
  • 所以「不丢」和「不重」是矛盾的：要「不丢」就得允许重投，重投就必然「可能重复」。重复无法避免，只能靠消费端幂等化解。

如何保证不重复（消费端幂等）

  • 给每条消息一个业务唯一 ID（订单号、消息 key），消费时做去重：
  • 数据库唯一索引（最可靠）、Redis setnx 标记、去重表。
  • 处理逻辑本身幂等（如状态机、乐观锁），重复处理也不会产生错误副作用。

为什么消息会乱序

  • 为了提高吞吐，消息分布在多个队列/分区上并行消费，不同队列的消费速度不同，顺序自然无法保证。
  • 甚至同一队列里，消费者重启、重平衡也可能造成顺序错乱。

如何保证不乱序

  • 全局有序：只用一个队列，FIFO 消费。牺牲吞吐，只适合极少量、强顺序场景，一般不这么做。
  • 局部有序（主流）：把「需要有序的消息」路由到同一个队列，队列内 FIFO 保证顺序。RocketMQ 用 MessageQueueSelector 按业务 key（如订单 ID）选择队列；Kafka 按 key 哈希分区。

核心结论：四者不可兼得

「不丢 + 不重 + 有序 + 高吞吐」无法同时满足：

  • 要「不丢」→ 允许重投 → 可能「重」。
  • 要「有序」→ 限制并发/单队列 → 牺牲「吞吐」。

工程最优组合：至少一次投递（不丢）+ 消费端幂等（化解重复）+ 按业务 key 局部有序（需要顺序的地方保证顺序）。

一句话扛住追问：消息「不丢」和「不重」本质矛盾——保证不丢就必然可能重复，所以重复靠「消费端幂等 + 业务唯一 ID 去重」化解；乱序靠「同一业务 key 路由到同一队列」实现局部有序。能讲清「四者不可兼得 + 各让一步」的权衡，是这道题的高分答法。

先厘清核心：哨兵解决「高可用」，集群解决「高可用 + 水平扩展」，两者解决的问题不完全相同。

哨兵原理（监控 + 选举 + 切换）

  1. 哨兵是独立进程，持续监控主从节点的存活。
  2. 主节点宕机 → 多个哨兵主观下线 → 客观下线（过半哨兵确认才算真的挂，避免误判）。
  3. 哨兵们投票选举一个新主节点（从节点中选数据最新的），通知其他从节点和客户端切换。
  4. 哨兵要部署奇数个（通常 3 个），避免哨兵本身单点，且过半投票才生效。

集群原理（16384 个 slot）

  • 集群把数据分成 16384 个 hash slot，每个 key 通过 CRC16(key) % 16384 算出落在哪个槽。
  • 每个主节点负责一部分槽（如 3 主节点各负责约 5461 个），节点间通过 gossip 协议通信同步元数据。
  • 每个主节点配从节点，主挂掉后从节点自动提升。

集群的两个关键约束（高频追问）

  • 多 key 操作受限：mget、mset、事务、多 key 的 Lua，要求所有 key 在同一个槽，否则报 CROSSSLOT 错误。
  • hash tag 解决：用 {} 包裹的部分参与 hash 计算，{user:1}:name 和 {user:1}:age 会落到同一个槽，从而允许一起操作。
一句话扛住追问：哨兵解决「高可用」（主从自动切换），但数据还是全量复制、受单机内存限制；集群解决「高可用 + 水平扩展」（16384 slot 分片）。选型看「数据量是否超单机」——超了就上集群。能答出「hash slot + hash tag 解决多 key 跨槽问题」，说明你真正用过集群。
