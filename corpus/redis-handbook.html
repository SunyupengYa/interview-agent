概览

学习路径与核心权衡

Redis 是「单线程 + 内存 + IO 多路复用」的内存数据库，知识骨架是「数据结构 → 持久化 → 高可用 → 场景」这条链。面试官通常从「Redis 为什么快」切入，然后沿着这条链往下挖。

模块解决什么问题核心机制代价 / 坑
① 数据结构与底层为什么快、数据怎么存多种编码 + 跳表 + 渐进式 rehash单命令大 key 会阻塞
② 持久化与内存内存易失，重启不丢RDB / AOF / 混合持久化有性能开销和丢数据窗口
③ 高可用与集群不单点、能扩容主从 / 哨兵 / Cluster脑裂、数据一致性、分片迁移
④ 缓存场景缓存用对、用稳穿透/击穿/雪崩防护 + 锁缓存和 DB 不一致、锁失效
学习顺序建议 路径先看这个

按依赖关系学：

  1. 先搞懂「Redis 为什么快」——单线程 + 内存 + IO 多路复用，这是所有后续问题的锚点。
  2. 再学数据结构底层（模块①）——知道每种类型底层是什么、什么时候变，是源码题和高性能题的基础。
  3. 然后学持久化（模块②）——理解「快」和「不丢数据」怎么取舍。
  4. 再学高可用（模块③）——主从/哨兵/Cluster 逐层进阶，脑裂和一致性是难点。
  5. 最后学缓存场景（模块④）——这是落地到业务、面试最爱问的「工程实战」。
面试技巧：被问「讲一下 Redis」时，标准答法是顺着这条链：「Redis 是单线程内存数据库，靠 IO 多路复用 + 高效数据结构做到单机十万 QPS；数据在内存，靠 RDB/AOF 持久化防丢；单机不够用主从/哨兵/Cluster 做高可用和扩容；生产上主要当缓存，要处理穿透/击穿/雪崩和一致性」。能讲出这条链，说明你有完整体系。
①

数据结构与底层

12 题

地基模块。核心抓住一条线：Redis 为什么快 → 单线程 + 内存 + IO 多路复用 → 高效数据结构（SDS/跳表/压缩列表/渐进式 rehash）。底层编码会随数据量「变脸」，这是源码题和高性能题的分水岭。

能脱离资料讲清「单线程为什么还快」+「5 种类型底层各是什么」+「渐进式 rehash 为什么渐进」
必考Redis 为什么快？单线程为什么能支撑高并发？Q1

「快」的原因是多维度的，别只答「内存」：

  • 纯内存操作：数据在内存，读写不碰磁盘（持久化是异步的），纳秒级访问。
  • 单线程，避免上下文切换和锁竞争：没有多线程的线程切换开销，也没有加锁/解锁开销。
  • IO 多路复用：单线程通过 epoll（Linux）同时监听多个连接，一个线程处理成千上万的网络事件，事件驱动而非阻塞等待。
  • 高效的数据结构：SDS、跳表、压缩列表、整数集合等，都是为「快」专门设计的。

「单线程」要精确：指的是命令执行是单线程的（6.0 之前连网络读写都是单线程）。6.0 引入了IO 多线程，但只是网络读写多线程，命令执行仍然是单线程。

追问：单线程为什么不用加锁还快？因为所有命令在一个线程里串行执行，天然没有并发写同一份数据的竞争，不需要锁。多线程快的前提是「无锁」，一旦加锁反而可能更慢。
追问：Redis 6.0 的 IO 多线程是什么？只是把「读请求解析、写响应」这些网络 IO 放到多线程，命令的执行还是单线程。因为执行阶段要保证命令的原子性和顺序性。
踩坑：「Redis 单线程所以快」不完整，会被追问「那多线程岂不是更快」。要补「单线程避免了锁和上下文切换，且瓶颈在网络 IO 不在 CPU」。
必考Redis 有哪些数据类型？各自的底层实现是什么？Q2
类型底层实现（编码）适用场景
String简单动态字符串 SDS（或整数 int、embstr）缓存、计数器、分布式锁、session
Hashziplist（压缩列表）→ hashtable（数据少时用 ziplist 省内存）对象属性、购物车
Listquicklist（ziplist + 双向链表的结合）消息队列、最新列表、时间线
Setintset（整数集合）→ hashtable去重、共同好友、标签
ZSetziplist → skiplist（跳表）+ hashtable排行榜、延迟队列、优先级队列

关键认知：底层编码是动态切换的，数据量小用省内存的紧凑结构（ziplist/intset），大了换成高效结构（hashtable/skiplist），阈值可配（如 hash-max-ziplist-entries）。

追问：为什么小数据用 ziplist，大了要换？ziplist 是连续内存、省内存省指针，但查询要遍历、O(n)；数据大了遍历就慢，换成 hashtable/skiplist 用空间换时间。
踩坑：「ZSet 底层是跳表」只说对一半，它实际是跳表 + 哈希表——跳表管按分数排序，哈希表管按 member 快速定位。漏了哈希表说明没真懂。
必考SDS（简单动态字符串）和 C 字符串有什么区别？Q3

Redis 不用 C 原生的 char*（以 \0 结尾），而是自己实现了 SDS，解决了 C 字符串的几个痛点：

维度C 字符串SDS
获取长度遍历 O(n)记录 len，O(1)
二进制安全遇 \0 截断用 len 定长度，可存任意二进制
拼接/扩容可能缓冲区溢出自动扩容，预分配空间
内存分配每次变更都重新分配预分配 + 惰性释放，减少分配次数

核心三点：O(1) 取长度、二进制安全、减少内存分配。

追问：什么是「二进制安全」？指字符串里可以包含任意字符（包括 \0、换行等），不会因为特殊字符被截断或出错。因为 SDS 用长度字段判断结束，而不是靠 \0 终止符。
必考跳表（skiplist）是什么？为什么 ZSet 用跳表不用红黑树？Q4

跳表：一种「多层索引的链表」结构。底层是完整有序链表，上层是「稀疏索引」，每隔几个节点抽一个到上层。查找时从最高层开始，快速跳过大量节点，再逐层下降，最终在底层定位。

  • 查找 / 插入 / 删除平均 O(log n)，最坏 O(n)。
  • 插入时用随机层数（抛硬币），不需要像平衡树那样旋转调整。

为什么 ZSet 用跳表不用红黑树：

  • 实现简单：跳表代码量远小于红黑树，好维护。
  • 支持范围查询：跳表按 score 有序，天然支持 ZRANGE 这类范围查找，找到起点后顺序遍历即可；红黑树范围查询要中序遍历。
  • 性能相当：两者都是 O(log n)，跳表不输。
追问：跳表的「层」怎么定？插入时随机决定层数（每层 50% 概率往上），保证平均每层节点数是下层的 1/2，形成对数级的稀疏索引。
必考什么是渐进式 rehash？为什么不能一次性 rehash？Q5

背景：Redis 的 hashtable 在元素过多（负载因子超阈值）时会扩容，扩容要重新计算所有 key 的哈希、搬到一个更大的新哈希表里。

问题：如果 key 很多（百万级），一次性 rehash 会阻塞很久，导致 Redis 单线程卡住，其他请求全部排队——这是灾难。

渐进式 rehash 的做法：不一次性搬完，而是：

  1. 维护两个哈希表（ht[0] 旧表、ht[1] 新表），还有一个 rehashidx 游标。
  2. 每次对哈希表的增删改查操作时，顺手把 rehashidx 位置的一小撮桶从 ht[0] 搬到 ht[1]，搬完 rehashidx++。
  3. 同时，后台定时任务也会分批次搬，加速进度。
  4. 搬完所有桶后，ht[1] 变 ht[0]，旧表释放。

效果：把一次性的「大阻塞」摊薄成无数次的「小开销」，rehash 期间 Redis 依然能正常服务。

追问：rehash 期间查询一个 key 怎么办？先查 ht[0]，查不到再查 ht[1]（两个表都查）。新增的 key 只往 ht[1] 加，保证 ht[0] 只减不增，最终搬空。
踩坑：「rehash 会阻塞」是错的，恰恰相反，渐进式 rehash 的目的就是避免阻塞。要说清楚「一次性 rehash 才会阻塞，所以 Redis 用了渐进式」。
高频List 的底层实现是什么？quicklist 是什么？Q6

List 底层经历了演进：早期是 ziplist 或 linkedlist 二选一（小数据 ziplist，大数据 linkedlist），后来统一改成 quicklist。

quicklist：「ziplist + 双向链表」的结合体——一个双向链表，每个节点不是单个元素，而是一个压缩列表（ziplist），ziplist 里装多个元素。

  • 相比纯 linkedlist：减少了指针开销（一个节点装多个元素，指针数量少）。
  • 相比纯 ziplist：避免了超大 ziplist 的连锁更新问题。

为什么这么设计：兼顾「内存紧凑」和「插入删除效率」。

追问：ziplist 有什么问题？ziplist 是连续内存，插入删除元素会导致后面所有元素移动（O(n)）；且如果元素变大触发「连锁更新」，性能会退化。所以不适合太大。
高频String 类型底层有几种编码？为什么要区分？Q7

String 底层有三种编码：

  • int：值能转成整数时用，最省内存（直接存 long）。
  • embstr：短字符串（≤44 字节），SDS 和 RedisObject 分配在连续内存，一次分配、减少内存碎片、读取快（缓存友好）。
  • raw：长字符串，SDS 和 RedisObject 分开分配。

区分的目的：省内存 + 快。整数直接存数字，短字符串用连续内存，都是优化手段。

追问：embstr 修改会怎样？embstr 是只读优化的，一旦修改（如 APPEND）会转成 raw 编码（因为要重新分配内存）。
高频Redis 的过期键是怎么删除的？惰性删除 + 定期删除是什么？Q8

Redis 用「惰性删除 + 定期删除」组合，不是「到期立即删」（立即删要每个 key 一个定时器，开销太大）：

  • 惰性删除：访问某个 key 时，如果发现它过期了，就删除它。缺点：过期的 key 一直没人访问，就一直占内存。
  • 定期删除：每隔一段时间（默认 100ms 一次），随机抽取一批 key 检查是否过期，过期的删掉。缺点：不是全量扫，可能漏。

两者结合：定期删除兜底清理「没人访问的过期 key」，惰性删除兜底清理「刚好被访问的过期 key」。

追问：为什么不扫描全部 key？全量扫描所有 key 判断过期，是个 O(n) 的耗时操作，会阻塞单线程。所以定期删除只随机抽样，控制每次的耗时。
高频什么是 big key？有什么危害？怎么找？Q9

big key：单个 key 的 value 特别大（如一个 String 几十 MB，或一个 Hash 几百万字段）。

危害：

  • 阻塞：对大 key 操作（DEL、GET、遍历）耗时长，阻塞单线程，拖垮整个 Redis。
  • 内存不均衡：Cluster 分片下，big key 导致某个节点内存特别大，热点。
  • 网络开销大：传输大 value 占带宽。

怎么找：用 redis-cli --bigkeys，或用 SCAN 遍历 + MEMORY USAGE 统计。

追问：怎么处理 big key？① 拆分：大 String 拆成多个小 key，大 Hash 按字段拆分；② 删除用 UNLINK（异步删除，不阻塞）；③ 数据压缩或改存对象存储。
踩坑：删除 big key 别用 DEL（同步阻塞），要用 UNLINK（4.0+ 异步删除）。这是很实用的工程细节。
加分RedisObject 是什么？为什么每个 key 都要包一层？Q10

RedisObject：每个 key 的 value 外面都包的一层元数据结构，包含：

  • type：数据类型（String/Hash/List/Set/ZSet）。
  • encoding：底层编码（int/embstr/raw/ziplist/skiplist...）。
  • ptr：指向实际数据的指针。
  • refcount：引用计数（用于共享对象、内存回收）。

为什么包一层：多态——同一个类型可以有多种底层实现（如 Hash 可以是 ziplist 或 hashtable），RedisObject 用 type + encoding 把「逻辑类型」和「物理实现」解耦，实现底层的灵活切换。

加分Redis 是单线程，怎么处理「慢命令」？Q11

单线程最大的软肋是「一个慢命令阻塞所有命令」。所以：

  • 避免 O(n) 命令：KEYS（全量扫，生产禁用，用 SCAN 替代）、SMEMBERS（大集合全取）、FLUSHALL 等。
  • 用 SCAN 代替 KEYS：SCAN 是游标分批遍历，不阻塞。
  • big key 拆分：避免单次操作大 value。
  • 耗时操作异步化：持久化 fork、异步删除 UNLINK 等。
追问：为什么 KEYS 很危险？KEYS 是 O(n) 全量扫描，key 多时一次执行几百毫秒甚至几秒，期间单线程被占用，其他所有请求都堵住。
踩坑：生产上「用 KEYS 找 key」是经典事故。要能立刻说出「用 SCAN 替代」。
加分Redis 里如何实现「排行榜」「延迟队列」？Q12
  • 排行榜：用 ZSet，member 存用户 ID，score 存分数。用 ZADD 更新分数、ZREVRANGE 取 Top N、ZRANK 查名次。
  • 延迟队列：用 ZSet，member 存任务，score 存「到期时间戳」。消费者用 ZRANGEBYSCORE 0 now 取出所有到期的任务执行。比 List 的先进先出更灵活，能精确控制每个任务的执行时间。
追问：延迟队列用 ZSet 有什么要注意的？多个消费者同时取任务会重复消费，需要原子地「取出并删除」（用 ZPOPMIN 或 Lua 脚本保证原子性），否则会重复执行。

持久化与内存

9 题

核心矛盾：「快（内存）vs「不丢（持久化）」。RDB 快但丢得多，AOF 丢得少但慢，混合模式取平衡。内存淘汰和过期删除是「内存不够了怎么办」的两个答案。

能说清「RDB vs AOF 怎么选」「混合持久化为什么好」「内存淘汰策略各自的适用场景」
必考RDB 和 AOF 分别是什么？有什么区别？Q1
维度RDB（快照）AOF（追加日志）
原理某时刻全量快照，二进制文件记录每条写命令，文本日志
文件大小小（压缩的二进制）大（命令明文）
恢复速度快（直接加载）慢（逐条重放命令）
丢数据多（两次快照之间）少（取决于 fsync 策略，默认每秒）
性能影响fork 子进程，父进程不阻塞但 fork 有开销追加写 + fsync，有 IO 开销

一句话：RDB 是「定时拍照」，AOF 是「记账流水」。RDB 恢复快但两次快照间的数据会丢，AOF 丢得少但文件大、恢复慢。

追问：RDB 怎么做到不阻塞主进程？通过 fork 子进程，子进程利用「写时复制（COW）」——fork 瞬间父子进程共享内存，主进程继续改数据时会复制修改的页，子进程看到的是 fork 那一刻的快照，主进程不阻塞。
踩坑：「RDB 会阻塞」不准确。RDB 的 fork 本身有短暂阻塞（复制页表），且 fork 时内存越大阻塞越久，但快照过程不阻塞。要说清「fork 有开销，快照过程靠 COW 不阻塞」。
必考AOF 的三种写回策略（fsync）是什么？怎么选？Q2

AOF 的 appendfsync 决定「什么时候把缓冲区刷到磁盘」，三种：

策略刷盘时机丢数据性能
always每条命令都 fsync不丢最慢
everysec（默认）每秒 fsync 一次最多丢 1 秒适中
no交给操作系统决定丢得多最快

怎么选：生产一般用 everysec——性能和安全的平衡点，最多丢 1 秒数据，可接受。

追问：为什么 always 最安全但没人用？每条命令都刷盘，磁盘 IO 成为瓶颈，性能断崖式下降。Redis 的价值在快，always 把快的优势抵消了。
必考AOF 重写（rewrite）是什么？为什么要重写？Q3

问题：AOF 是追加日志，一个 key 反复修改会累积大量冗余命令（如 INCR 100 次就有 100 条），文件越来越大。

重写：把 AOF 里冗余的命令合并压缩成最小集合（100 次 INCR 合并成一条 SET 最终值），生成新的、更小的 AOF 文件。

关键点：重写不是读旧 AOF 文件，而是直接读当前内存里的数据，生成对应的写入命令。也是 fork 子进程做，靠 COW 不阻塞主进程。

追问：重写期间有新命令写入怎么办？重写期间的新命令会同时写到「旧的 AOF 文件」和「一个重写缓冲区」，子进程重写完后，把缓冲区里的增量命令追加到新 AOF 文件末尾，然后原子替换旧文件。
必考混合持久化是什么？有什么好处？Q4

混合持久化（Redis 4.0 引入）：AOF 重写时，前半段用 RDB 格式存快照，后半段用 AOF 格式存增量命令，拼成一个文件。

  • 好处：既享受 RDB 的快速恢复（前半段直接加载快照），又享受 AOF 的低丢失（后半段增量命令补上重写后的变更）。

一句话：混合模式 = 「RDB 的速度 + AOF 的安全性」的折中。

追问：混合持久化文件格式兼容吗？不兼容老版本 Redis。4.0 之前无法识别混合格式（RDB 开头 + AOF 结尾），所以升级要注意。
踩坑：生产一般建议「开启 AOF + 混合持久化」，既保证低丢失又保证恢复快。单纯用 RDB 会丢数据，单纯用 AOF 恢复慢。
高频内存淘汰策略有哪些？各自适用什么场景？Q5

当内存满了（达到 maxmemory），Redis 按淘汰策略处理。策略分两类：

不淘汰：

  • noeviction（默认）：内存满了直接报错，不删任何数据。适合「数据不能丢」的场景。

淘汰（针对带过期时间的 key）：

  • volatile-lru：淘汰「有过期时间」里最久未用的。
  • volatile-lfu：淘汰「有过期时间」里使用频率最低的。
  • volatile-ttl：淘汰「有过期时间」里最快过期的。
  • volatile-random：随机淘汰「有过期时间」的。

淘汰（针对所有 key）：

  • allkeys-lru：淘汰所有 key 里最久未用的。
  • allkeys-lfu：淘汰所有 key 里使用频率最低的。
  • allkeys-random：随机淘汰所有 key。

缓存场景通常用 allkeys-lru 或 allkeys-lfu——淘汰最不常用的，把内存留给热点。

追问：LRU 和 LFU 的区别？LRU（最近最少使用）看「多久没被访问」，LFU（最不经常使用）看「访问频率」。LRU 的盲点是「偶尔被访问一次的冷数据」可能赖着不走；LFU 更关注频率，适合「有明显冷热之分」的场景。
踩坑：默认 noeviction 在缓存场景会「内存满了直接报错」，所以当缓存用一定要显式配置淘汰策略（通常 allkeys-lru），否则线上会莫名报 OOM。
高频Redis 的 LRU 是严格的 LRU 吗？Q6

不是严格的 LRU。严格 LRU 需要维护一个精确的「最近使用」有序结构，内存开销大。Redis 用的是近似 LRU：

  • 每个 key 记录一个「最近访问时间戳」（存在 RedisObject 里，只占一点内存）。
  • 淘汰时，随机抽样 N 个 key（默认 5 个），从中挑「最久没访问」的那个淘汰。

为什么近似：用「抽样 + 时间戳」近似「全局最久未用」，牺牲一点精确度换内存和性能。抽样数 maxmemory-samples 越大越接近严格 LRU，但开销也越大。

追问：近似 LRU 会不会淘汰错？会，有概率淘汰掉「不是最久未用」的 key。但通过调大抽样数（如 10）可以让准确度足够高，实际影响很小。
高频Redis 挂了（进程崩溃）会丢多少数据？Q7

取决于持久化配置：

  • 只有 RDB：丢「上次快照到现在」的所有数据（可能几分钟甚至更久，看快照频率）。
  • 只有 AOF（everysec）：最多丢「最后 1 秒」的数据。
  • 混合持久化：丢「最后 1 秒」（因为混合的增量部分是 AOF 语义）。
  • 完全没开持久化：全丢。

关键认知：Redis 本质是内存数据库，持久化是「尽量不丢」而非「绝对不丢」。对数据绝对敏感的场景（如账户余额），Redis 不适合当唯一存储源。

追问：Redis 能保证「零丢失」吗？不能。即使 always 策略也有极小的窗口（命令执行完但没刷盘就崩溃）。Redis 定位是缓存/高性能中间层，不是强一致存储。
加分为什么 AOF 文件会越来越大？怎么控制？Q8

原因：AOF 是追加日志，只增不减，重复修改会累积冗余命令，文件持续变大。

控制手段：

  • AOF 重写（rewrite）：合并冗余命令，缩小文件。可手动 BGREWRITEAOF 或配置自动触发（如 auto-aof-rewrite-percentage 文件增长到一定比例时自动重写）。
  • 混合持久化：重写时用 RDB 格式，进一步缩小。
追问：AOF 文件损坏了怎么办？用 redis-check-aof --fix 修复工具，会截断损坏的部分（牺牲损坏点之后的数据）。
加分为什么 Redis 用「fork + 写时复制」做持久化？Q9

目的：让「快照」过程不阻塞主进程。

原理：

  1. fork 一个子进程，fork 瞬间父子进程共享同一份内存（页表复制，很快）。
  2. 子进程负责把内存快照写到磁盘（RDB）。
  3. 主进程继续处理请求，当要修改某个内存页时，靠「写时复制 COW」——先复制一份再改，子进程看到的始终是 fork 那一刻的旧数据。

效果：主进程只在「修改页」时有额外复制开销，快照过程不阻塞。

追问：fork 有什么风险？fork 本身要复制页表，内存越大，fork 越慢（可能阻塞几十毫秒到几百毫秒）。所以大内存实例 fork 是有代价的，这也是为什么超大内存要谨慎。
③

高可用与集群

10 题

逐层进阶：主从复制（读写分离）→ 哨兵 Sentinel（自动故障切换）→ Cluster（分片扩容）。难点在脑裂和数据一致性——这和 MySQL 集群高度相似，可以对照着理解。

能说清「主从 vs 哨兵 vs Cluster 各解决什么」「哨兵怎么选主」「Cluster 的槽位和脑裂」
必考Redis 主从复制是什么？全量同步和增量同步的区别？Q1

主从复制：一个主节点（master）多个从节点（slave），数据从主复制到从，实现读写分离 + 数据备份。

两种同步：

  • 全量同步（首次或差距太大）：主节点 bgsave 生成 RDB 快照，发给从节点，从节点加载。之后主节点把「快照期间的新命令」也发给从节点补齐。
  • 增量同步（日常）：主节点把后续的写命令持续发给从节点（基于偏移量 offset 或 repl backlog 缓冲区）。

关键点：Redis 复制是异步的，主节点写完就返回，不等从节点确认（和 MySQL 异步复制一样）。

追问：主从断开重连后走全量还是增量？看 repl backlog 缓冲区——如果断连期间主节点的写命令还在 backlog 里（没被覆盖），就走增量（补 offset 之后的）；否则走全量。backlog 太小容易触发全量同步。
踩坑：Redis 主从是异步复制，主库挂了可能丢「已写但没同步到从库」的数据。这和 MySQL 主从复制的问题一模一样。
必考哨兵（Sentinel）是什么？工作机制？怎么选主？Q2

Sentinel：Redis 官方的高可用方案，是独立进程，负责：

  • 监控：不断 ping 主从节点，判断是否存活。
  • 自动故障转移：主节点挂了，自动从从节点里选一个提升为新主。
  • 通知：切换后通知客户端新主地址。

选主流程：

  1. 多个哨兵通过投票确认主节点真的挂了（主观下线 → 客观下线，需要多数哨兵同意）。
  2. 选一个哨兵作为 leader 执行故障转移。
  3. 从所有从节点里按优先级选新主：先排除「断连太久」的，再按 slave-priority（配置的优先级）、复制偏移量最大（数据最新）、runid 最小的顺序选。
  4. 让其他从节点改认新主。
追问：主观下线和客观下线有什么区别？主观下线（SDOWN）是单个哨兵认为节点挂了（可能是哨兵自己网络问题误判）；客观下线（ODOWN）是多个哨兵（多数）都认为挂了，才真认为挂了。客观下线避免单个哨兵误判。
踩坑：哨兵本身要集群部署（奇数个，如 3 个），否则单哨兵挂了就没高可用了。且哨兵要多数派投票，奇数个才能避免平票。
必考Redis Cluster 是什么？怎么分片？Q3

Cluster：Redis 官方的分布式集群方案，解决「单机存不下、写不下」的问题——数据分片到多个节点，每个节点只存一部分。

分片机制：16384 个槽（slot）：

  • 整个集群分成 16384 个哈希槽。
  • 每个 key 通过 CRC16(key) % 16384 算出属于哪个槽。
  • 槽平均分配给各主节点（如 3 个主节点，每个分约 5461 个槽）。

客户端访问：客户端先查「key → 槽 → 节点」映射，直接连目标节点。如果 key 不在该节点，节点返回 MOVED 重定向。

追问：为什么是 16384 个槽？够用（节点数远小于这个数）、心跳消息里位图大小适中（16384 bit = 2KB）。槽太多心跳包太大，太少分片不够细。
踩坑：Cluster 分片下，跨槽的操作受限——如 mget、mset、事务、多 key 操作要求所有 key 在同一个槽（可用 hash tag {} 强制同槽）。这是 Cluster 最大的使用约束。
必考Redis Cluster 的脑裂问题？怎么解决？Q4

脑裂场景：主节点和集群其他节点网络分区，主节点还活着但和其他节点失联。此时：

  • 主节点自己以为自己还是主，继续接受写。
  • 集群其他节点以为主挂了，从从节点里选一个新主。
  • 结果两个主节点，数据分叉。

解决：

  • min-replicas-to-write + min-replicas-max-lag：配置主节点「至少要有 N 个从节点，且延迟不超过 X 秒」才接受写。网络分区后，旧主节点发现从节点都失联了，自动拒绝写，避免数据分叉。
追问：这个配置的代价是什么？如果从节点都挂了（或都延迟超时），主节点会拒绝所有写，牺牲可用性保一致性。这是 CAP 里「选 C 弃 A」的体现。
踩坑：Redis 脑裂的核心危害是「旧主还活着继续写，切换后数据丢失」。要用 min-replicas 配置让旧主自动禁写，而不是指望客户端自觉。
高频哨兵和 Cluster 的区别？怎么选？Q5
维度哨兵 SentinelCluster
解决的问题高可用（主挂自动切换）高可用 + 分片扩容
数据分布所有节点存全量数据数据分片到不同节点
容量受单机内存限制可横向扩展
复杂度低高（跨槽限制、数据迁移）

怎么选：数据量单机能放下、只要高可用 → 哨兵；数据量大要横向扩展 → Cluster。

追问：能不能「哨兵 + Cluster」一起用？不能，二选一。Cluster 自带高可用（主从 + 自动切换），不需要哨兵。哨兵只管「不分片」的主从架构。
高频Redis Cluster 数据是怎么迁移的？（扩容时）Q6

Cluster 扩容（加节点）时，需要把一部分槽从老节点迁到新节点，用 redis-cli --cluster reshard 或自动 rebalance。

迁移原理（按槽迁移）：

  1. 目标槽设置为「迁移中」状态。
  2. 把槽里的 key 逐个搬到新节点（MIGRATE 命令）。
  3. 迁移期间访问该槽：节点返回 ASK 重定向，告诉客户端去新节点找。
  4. 搬完一个槽，更新槽的归属，广播给所有节点。

关键点：迁移是在线的，不停服；迁移期间该槽的 key 通过 ASK 重定向保证能找到。

追问：MOVED 和 ASK 有什么区别？MOVED 是「永久」重定向——槽已经永久归别的节点，客户端要更新本地映射；ASK 是「临时」重定向——槽正在迁移，只是这次请求去目标节点，客户端不更新映射。
高频Redis 主从复制的数据一致性如何？会丢数据吗？Q7

Redis 主从复制是异步的，是最终一致，可能丢数据。

丢数据场景：

  • 主节点写完、还没同步到从节点就崩溃，这段数据丢了。
  • 主从切换时（哨兵），新主的数据可能不是最新的（因为异步，新主落后于旧主）。

减少丢失的手段：

  • min-replicas-to-write：要求有 N 个从节点才接受写，间接提高同步概率。
  • WAIT 命令：让写命令「等待从节点确认」再返回，类似 MySQL 半同步。
追问：Redis 能不能做到强一致？原生主从不能（异步）。要强一致得牺牲性能（WAIT 等），或换强一致方案（如 Redlock 只是锁层面，数据层面 Redis 本身不强一致）。Redis 定位是高性能缓存，不是强一致存储。
加分什么是 hash tag？为什么需要它？Q8

hash tag：在 key 里用 {} 包裹一段字符串，让 Redis 只用 {} 里的内容计算槽位，而不是整个 key。

例如 user:{1001}:info 和 user:{1001}:profile，都按 1001 计算，会落到同一个槽。

为什么需要：Cluster 下多 key 操作（mget、事务、Lua 脚本）要求所有 key 在同一个槽。用 hash tag 把相关 key 强制放同槽，就能用这些多 key 操作了。

追问：hash tag 有什么副作用？可能导致数据倾斜——如果 {} 里的内容分布不均（如都用 {hot}），会全落到同一个槽，造成热点。
加分为什么哨兵推荐部署 3 个或 5 个（奇数）？Q9

原因：哨兵判断节点「客观下线」、选 leader 都需要多数派投票（N/2+1）。

  • 奇数个能避免「平票」（如 3 个，多数派是 2，明确；2 个的话，一个挂了就没多数派了）。
  • 容错能力：3 个哨兵容 1 个挂，5 个容 2 个挂。偶数个（如 4 个）容错和 3 个一样，还多一个成本，不划算。

这和 MySQL MGR「要求奇数节点」是同一个道理（多数派判断）。

加分Redis 主从 + 哨兵架构下，客户端怎么知道新主地址？Q10

故障切换后，主节点 IP 变了，客户端要感知到。几种方式：

  • 哨兵发布订阅：客户端订阅哨兵，哨兵切换后广播新主地址，客户端更新连接。
  • 客户端库自动感知：如 Jedis 的 SentinelPool、Lettuce 的哨兵模式，库内部订阅哨兵、自动切换。
  • Proxy 层：引入代理（如 Codis、Twemproxy），客户端连代理，代理感知后端切换，客户端无感知。
追问：切换期间客户端请求会怎样？切换有几秒的窗口，期间客户端可能连不上或写到旧主（旧主已只读）。客户端库一般会重试、重新获取新主地址。

缓存场景与经典问题

10 题

落地到业务的「工程实战」，面试最爱问。核心三连：穿透/击穿/雪崩（缓存失效的三种经典灾难）、缓存一致性（和 DB 怎么对齐）、分布式锁（并发控制）。

能区分「穿透/击穿/雪崩」并说出各自解法，能讲清「先删缓存还是先更新库」，能写对分布式锁
必考缓存穿透、击穿、雪崩分别是什么？怎么解决？Q1

三个概念经常混，本质区别是「请求打到哪里」：

问题场景危害解法
穿透查不存在的数据（缓存和 DB 都没有）每次请求都打到 DB，恶意攻击可打垮 DB缓存空值、布隆过滤器、参数校验
击穿某个热点 key 过期的瞬间，大量请求同时打 DB瞬时 DB 压力剧增互斥锁（只让一个去查 DB）、热点 key 不过期/逻辑过期
雪崩大量 key 同时过期或缓存服务宕机DB 被瞬间打垮，级联故障过期时间加随机值、多级缓存、限流降级、高可用

一句话区分：穿透是「查的东西本来就没有」，击穿是「一个热点 key 没了」，雪崩是「一大批 key 一起没了」。

追问：缓存空值解决穿透有什么问题？① 空值本身占内存，且大量不存在的 key 会塞满缓存；② 空值要设个短过期时间，避免「数据其实有了但缓存还存着空值」。所以通常空值 + 短过期 + 布隆过滤器组合用。
踩坑：这三个词面试必考，答混了是硬伤。先记死区别：穿透 = 数据不存在，击穿 = 单热点过期，雪崩 = 批量过期/宕机。
必考布隆过滤器是什么？怎么解决缓存穿透？Q2

布隆过滤器（Bloom Filter）：一种空间效率极高的「判断某元素是否可能存在」的概率数据结构。

  • 底层是一个位数组 + 多个哈希函数。
  • 插入：对元素算多个哈希，把对应位置置 1。
  • 查询：算同样哈希，看对应位是否都是 1。都是 1 → 「可能存在」；有 0 → 「一定不存在」。

特点：不会漏报（一定不存在时很准），会误报（可能把不存在的误判为存在），且删除困难。

解决穿透：把 DB 里所有存在的 key 提前放进布隆过滤器。请求来了先查布隆过滤器——「一定不存在」就直接拒绝，不打 DB；「可能存在」才继续查缓存和 DB。

追问：布隆过滤器的误判率怎么控制？通过「位数组大小」和「哈希函数个数」调节，数组越大、哈希越多，误判率越低，但空间和时间开销越大。可按业务容错设定。
踩坑：布隆过滤器不能删除元素（删了会影响其他元素），所以数据有删改时要重建或换「计数布隆过滤器」。这是它的主要局限。
必考如何保证缓存和数据库的一致性？Q3

核心难点：缓存和 DB 是两套存储，更新时操作顺序不当就会不一致。常用方案：

方案一：Cache Aside（旁路缓存，最常用）

  • 读：先查缓存，命中直接返回；未命中查 DB，写回缓存。
  • 写：先更新 DB，再删除缓存（注意是「删除」不是「更新」缓存）。

为什么先更新 DB 再删缓存：如果先删缓存再更新 DB，中间有个窗口——别的线程读旧 DB 又写回旧缓存，导致缓存一直是旧值。先更新 DB 再删缓存，能把这个窗口缩到最小。

为什么删而不是更新：更新缓存容易出现「更新顺序错乱」和「写无意义数据」（比如这个 key 根本没人读，白写）。删除更简单可靠，让下次读时按需重建。

追问：先更新 DB 再删缓存，还是可能不一致吗？可能。极端情况：线程 A 更新 DB 后，删缓存前，线程 B 读到旧缓存；或删缓存失败。要彻底解决用「延迟双删」（删两次，中间隔一点时间）或「订阅 binlog（Canal）异步删缓存」。
追问：能不能做到强一致？不能（缓存和 DB 是分布式两套系统）。只能做到最终一致。要强一致就别用缓存，或引入分布式事务/可靠消息保证。
踩坑：「先删缓存再更新库」是经典错误顺序，会被追问击穿。标准答法是「先更新库、再删缓存」，并说明为什么。
必考用 Redis 实现分布式锁？要注意哪些问题？Q4

基本实现：用 SET key value NX PX 过期时间（原子地「不存在才设置 + 设过期时间」），拿到锁执行，执行完删锁。

必须注意的坑：

  • 加锁和设过期要原子：不能「先 SET 再 EXPIRE」两步（中间挂了锁就永不过期），要一条命令 SET ... NX PX。
  • 锁要设过期时间：防止拿到锁的线程崩溃，锁永远不释放（死锁）。
  • 删锁前要校验是不是自己的锁：防止「我的锁过期了，别人的锁被我不小心删了」。用唯一 value（如 UUID）标识，删时用 Lua 脚本「判断 value 相等才删」保证原子。
  • 锁过期但业务没执行完：业务耗时超过锁的过期时间，锁提前释放，别人拿到锁，并发执行。要用「看门狗（watchdog）自动续期」（Redisson 已实现）。
追问：为什么删锁要用 Lua 脚本？因为「判断 value 相等」和「删除」是两个操作，不用 Lua 就不是原子的——判断完、删除前，锁可能刚好被别人拿到，导致误删。Lua 脚本保证两步原子执行。
踩坑：手写分布式锁最容易翻车的是「删了别人的锁」和「锁过期业务没做完」。生产上直接用 Redisson（封装了看门狗、可重入、自动续期），别自己造轮子。
高频Redisson 的分布式锁和手写锁有什么区别？看门狗是什么？Q5

Redisson：成熟的 Redis 客户端，封装了健壮的分布式锁，解决了手写锁的所有坑：

  • 看门狗（watchdog）自动续期：默认锁 30 秒过期，如果业务没执行完，看门狗线程会自动续期（每 10 秒续到 30 秒），避免「锁过期业务没做完」。
  • 可重入：同一个线程可以重复加锁（内部记录重入次数）。
  • 自动释放：业务执行完或异常，自动删锁。
  • 加锁逻辑用 Lua 脚本：保证原子性。
追问：Redisson 的看门狗怎么实现的？加锁时如果没指定过期时间，会启动一个定时任务，定期（默认 1/3 过期时间）检查锁是否还被持有，是就续期。业务结束释放锁时关闭看门狗。
踩坑：生产上推荐直接用 Redisson，不要手写分布式锁——手写锁的边界情况（续期、重入、误删）太多，容易踩坑。
高频Redis 怎么实现「缓存击穿」的互斥锁方案？Q6

击穿的本质是「热点 key 过期瞬间，大量请求同时回源 DB」。互斥锁方案：只让一个请求去查 DB，其他请求等待。

流程：

  1. 请求来了，缓存未命中。
  2. 尝试用 SETNX（或 SET NX）抢一把「重建锁」。
  3. 抢到锁的请求：去查 DB，重建缓存，释放锁。
  4. 没抢到锁的请求：等一小会儿，重试读缓存（或直接返回旧值/降级）。

效果：DB 只被查一次，其他请求都等缓存重建。

追问：互斥锁方案有什么缺点？① 加了锁，请求有等待，可能积压；② 锁本身也可能成为瓶颈。更优的方案是「热点 key 不过期」（物理不过期）+「逻辑过期」（后台异步刷新），彻底避免击穿。
高频什么是「逻辑过期」？和「物理过期」的区别？Q7
  • 物理过期：key 设了 TTL，到期 Redis 自动删除（这就是「过期」的本义）。
  • 逻辑过期：key 不设 TTL（永不过期），但在 value 里存一个「过期时间戳」字段。读取时判断时间戳是否过期——过期了就「后台异步刷新」，但当前请求仍然返回旧值。

解决击穿的妙处：热点 key 永远不会「物理消失」，所以不会有「缓存 miss 后大量回源」的瞬间。即使逻辑上过期了，请求也能拿到旧值兜底，由后台线程慢慢刷新。

追问：逻辑过期会不会一直返回旧值？刷新期间会短暂返回旧值（可接受的最终一致），后台刷新完成后就返回新值。关键点是「保证一直有值可读，永不击穿」。
高频什么是热 key？怎么发现和解决？Q8

热 key：被大量访问的 key（如爆款商品、明星微博），单个 key 的 QPS 极高。

危害：

  • 单机瓶颈：所有请求压到同一个节点，即使集群也可能热点。
  • 网络和 CPU 压力集中在一点，可能拖垮该节点。

发现：监控统计各 key 的访问频率（如 redis-cli --hotkeys、或业务埋点、或用 proxy 统计）。

解决：

  • 本地缓存（多级缓存）：把热 key 缓存在应用本地内存（如 Caffeine），减少对 Redis 的请求。
  • 读写分离：热 key 的读走从节点。
  • key 拆分：把热 key 复制成多个副本 key（如 hot_0、hot_1），请求随机分布到不同副本。
追问：多副本 key 怎么保证一致？写的时候要同时更新所有副本，或副本只用于读、写统一走主。副本方案本质是「用空间换分散热点」。
加分Redis 做「延迟队列」和「消息队列」可靠吗？Q9

Redis 可以做简单的消息/延迟队列（List 或 Stream），但可靠性弱：

  • List 实现队列：LPUSH + BRPOP（阻塞读）。缺点：没有 ACK 机制，消费者取走消息但处理失败，消息就丢了。
  • Stream（5.0+）：更完善的队列，支持消费者组、ACK、消息持久化，比 List 强很多。
  • 延迟队列：用 ZSet（score 存到期时间），见模块① Q12。

结论：Redis 做「轻量、可容忍丢失」的队列可以；要做「高可靠、不丢消息、严格顺序」的队列，还是用 RabbitMQ / Kafka 这类专业 MQ。

追问：Redis 队列和 Kafka 的本质区别？Kafka 有「持久化 + 分区 + 消费位移 + 多副本」的完整可靠性设计，消息不丢、可重放；Redis 队列本质是内存结构，掉电可能丢（即使持久化也有窗口），可靠性差一截。
加分如何设计一个「缓存 + 数据库」的计数/排行榜场景？Q10

计数场景（如点赞数、浏览量）：

  • 用 INCR 原子自增，高性能。
  • 一致性：计数允许短暂不一致（最终一致），可以「先 Redis 计数，异步批量落 DB」。
  • 关键：Redis 是「热点计数的缓存/加速层」，DB 是「持久化真源」，用异步刷回保证最终一致。

排行榜场景：

  • 用 ZSet（member 存 ID，score 存分数），ZINCRBY 实时更新。
  • 读榜用 ZREVRANGE 取 Top N。

设计要点：这类场景的核心是「容忍最终一致，用 Redis 抗住高并发写，DB 异步兜底」。要能说出「哪里用 Redis、哪里用 DB、怎么保证最终一致」。

追问：Redis 挂了计数会丢吗？会（如果没持久化或还没刷 DB）。所以关键计数要「Redis + 异步落 DB + 对账」，Redis 挂时从 DB 恢复。
