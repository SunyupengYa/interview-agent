学习路径与核心权衡

四层不是并列的四个知识点，而是一条「单机撑不住 → 加副本 → 副本要容错 → 容量到顶就拆」的演进链。面试官会按这个顺序层层追问，你也要按这个顺序建立心智模型。

方向解决什么问题核心机制代价 / 坑
① 主从复制读多写少，单机读扛不住binlog 异步复制主从延迟、数据可能丢
② 高可用切换主库挂了业务全停自动选主 + VIP 切换脑裂、选主误判、数据不一致
③ 分库分表单库数据量/写入到顶水平拆分 + 路由跨库事务/join 失效、分布式 ID
④ 一致性副本之间数据要一致共识协议（Paxos/Raft）写性能大幅下降、需多数派存活
学习顺序建议 路径先看这个

按依赖关系学，不要跳：

  1. 先吃透 binlog 和复制原理（模块①）——这是后面所有东西的地基，MHA/MGR/Orchestrator 都建立在对复制的理解上。
  2. 再学高可用切换（模块②）——理解「主挂了怎么办」，顺便把脑裂、选主这些分布式概念先建立直觉。
  3. 然后学分库分表（模块③）——这是「拆数据」，和「复制数据」是正交的两件事，别混。
  4. 最后学一致性（模块④）——MGR 本质是「复制 + 共识」，没前面的基础会学得很虚。
面试技巧：被问「你们线上 MySQL 怎么部署的」，标准答法是顺着这条链讲：「单主 + 一主两从读写分离 → 高可用用 MHA/Orchestrator 做自动切换 → 数据量大了再考虑分库分表」。能把这个演进讲清楚，就证明你不是只背过单个知识点。
①

主从复制（Replication）

12 题

地基模块。所有高可用方案都建立在对复制的理解上。核心抓住一条线：主库写 binlog → 从库 IO 线程拉取 → 从库 SQL 线程回放，再沿着「异步 → 半同步 → 延迟 → 数据一致性」层层追问。

能脱离资料画出「主库写 binlog → IO 线程 → relay log → SQL 线程」完整链路，并说出每个线程的作用
必考说说 MySQL 主从复制的原理和完整流程Q1

复制是异步的、基于 binlog的，核心三个角色、两个线程：

  1. 主库（Master）：所有写操作记录到 binlog（二进制日志），按事务提交顺序写入。
  2. 从库（Slave）上有两个线程：
    • IO 线程：主动连接主库，请求主库从某个 binlog 位点开始发送日志，主库通过 dump 线程 推送，从库收到后写入本地 relay log（中继日志）。
    • SQL 线程：读取 relay log 并回放执行，把主库的变更在从库重做一遍。

所以本质是「主库记录 → 从库拉取 → 从库重放」。

关于「谁主动」——要区分两个动作，别混：① 连接和请求是从库主动发起的（从库拨号连主库、报自己的位点/GTID，这就是 pull 的含义）；② 连接建立后，数据流是主库持续推给从库的。所以准确说是「从库主动拉位点，主库被请求后持续推增量」。关键证据：主库的 dump 线程是为每个连上来的从库临时开的，从库一断它就结束，主库不保存任何「从库追到哪了」的状态；从库断了要自己重连、自己重新报位点。若真是「主库主动推」，主库就得记住每个从库的地址和进度——MySQL 不是这种架构。

追问 1：为什么从库要两个线程而不是一个？IO 线程负责网络拉取（慢，可能被网络阻塞），SQL 线程负责本地执行（慢，可能被慢 SQL 阻塞）。分开后两者解耦，拉取和回放可以并行，否则网络卡一下回放就全停。
追问 2：主从复制的数据是怎么保证顺序的？靠 binlog 里的 GTID 或 文件名+偏移量 定位。每个事务有一个全局唯一 ID，从库按顺序消费，保证执行顺序和主库一致。
踩坑：别把「主从复制」说成「数据同步备份」。它是异步的最终一致，不是同步的强一致，主库提交后从库可能还没执行，主库一挂这部分数据可能丢。这个区别面试官特别爱追问。
必考binlog 有三种格式，区别是什么？怎么选？Q2
格式记录内容优点缺点
STATEMENTSQL 语句原文日志小、省空间主从不一致风险高（含 now()、limit 无 order by、UUID 等不确定函数时结果会不同）
ROW（默认）每行数据变化的前后镜像精确、不会出现不一致，利于恢复日志量大，尤其批量 update/delete
MIXED多数用 statement，不确定时自动转 row折中依然有边界，需理解判断逻辑

现在线上默认 ROW 格式（MySQL 5.7+ 默认就是 ROW）。选 ROW 的原因：精确可靠，配合 binlog_row_image=FULL 可以做闪回、数据订正。

追问：ROW 格式日志量太大怎么办？用 binlog_row_image=MINIMAL（只记录变化列）、binlog_rows_query_log_events 控制、或对批量操作分批执行。
踩坑：MIXED 格式下，一条语句里既有确定部分又有 now()，MySQL 会整条转 ROW，但判断逻辑复杂，出问题难排查。所以主流做法是直接全 ROW，不要 MIXED。
必考主从延迟是怎么产生的？怎么监控和排查？Q3

延迟的本质：从库 SQL 线程是单线程回放（5.7 之前），主库可以多线程并发写，从库只能串行执行，主库写太快从库就跟不上。此外还有：

  • 从库机器性能差：CPU/IO 不如主库，回放慢。
  • 大事务：一个大事务在从库回放要很久，阻塞后续所有事务。
  • 慢 SQL：主库上能走索引，从库因为统计信息不同走了全表扫描。
  • 锁冲突：从库上还跑着只读查询/备份，抢锁。

监控指标：Seconds_Behind_Master（从库落后主库的秒数，最常用，但不精确）、relay log 堆积、GTID 差异。

排查链路：看 SHOW SLAVE STATUS → 看 Seconds_Behind_Master 是否持续增长 → 抓当前正在执行的 relay log 事件 → 定位是哪个慢 SQL / 大事务。

追问：Seconds_Behind_Master 为 0 就代表没延迟吗？不是。它是「从库已回放到的时间戳」与「主库当前时间戳」之差，但主库可能有一段时间没写数据了，这个值会显示 0 或负数，实际可能积压了没回放。更准确看 relay log 的堆积和 GTID 集合差异。
踩坑：别在从库上跑大查询或备份，否则会和回放抢资源，进一步放大延迟。延迟敏感的业务要「读主库」或做「读写分离 + 强制读主」。
必考半同步复制是什么？和异步、全同步的区别？Q4

三种复制模式对比，核心是「主库提交前要不要等从库确认」：

模式主库行为数据安全性性能
异步写完 binlog 就返回，不等从库可能丢数据最高
半同步等至少一个从库收到并写入 relay log 后返回（5.7+ 是 AFTER_SYNC）不丢已提交数据（从库可能没回放完）中等，有网络开销
全同步等所有从库都回放执行完才返回最强一致最低，基本不用

半同步的价值：在「性能」和「数据不丢」之间取平衡——主库挂掉时，至少有一个从库已经收到了最新数据，切换过去不丢已提交的事务。

追问：半同步如果从库迟迟不确认，主库会怎样？会等到超时（rpl_semi_sync_master_timeout，默认 10 秒），超时后降级为异步复制，避免主库被一个慢从库拖死。降级后数据安全性回到异步水平。
踩坑：半同步只能保证「从库收到」，不保证「从库执行完」。所以从库上读到的数据可能还不是最新的——这依然是最终一致，不是强一致。要强一致得用 MGR/PXC（见模块④）。
高频读写分离怎么实现？会带来什么问题？Q5

实现方式：

  • 应用层：用中间件（ShardingSphere、MyCat）或 ORM 插件（如 MyBatis 的读写分离插件），按 SQL 类型路由——写走主库、读走从库。
  • 数据库中间件层：引入 Proxy（如 ProxySQL、MySQL Router），对应用透明。

核心问题：主从延迟导致「刚写完读不到」。用户刚写入一条数据，立刻查询却查不到（因为读走了延迟的从库）。

解决方案：

  • 强制读主：写操作后的关键读（如「写后立即读」）强制走主库。
  • 半同步复制：降低延迟窗口。
  • 延迟容忍：允许读从库但接受短暂不一致（适合对一致性要求低的场景）。
追问：怎么判断一个读能不能走从库？看业务语义——「用户刚提交订单，立即跳转到订单详情页」这种写后读必须走主库；「列表页浏览」「报表统计」这类不关心实时性的可以走从库。
踩坑：不要把「事务内」的读也路由到从库。一个事务里前面写主库、后面读从库，会因为主从延迟读到旧数据，造成逻辑错误。事务内的读要跟着事务的写库走。
高频GTID 是什么？和传统位点复制比有什么优势？Q6

GTID（Global Transaction Identifier）：每个事务在全局范围内有一个唯一 ID，格式 server_uuid:transaction_id，随 binlog 一起记录。

传统位点复制的痛点：靠「binlog 文件名 + 偏移量」定位，主从切换后从库要重新找位点，容易出错，尤其在级联复制、多从库场景下。

GTID 的优势：

  • 切换简单：从库知道「我已经执行过哪些 GTID」，切换后自动找没执行过的继续拉，不用手工算位点。
  • 故障恢复容易：新主库能判断哪些事务从库已执行，避免重复或遗漏。
  • 主从一致校验方便：对比两边 GTID 集合即可知道差异。
追问：GTID 有什么限制？某些操作不支持（如 CREATE TABLE ... SELECT 这种非事务性语句），且要求所有事务都用 GTID 模式，不能混用。另外 GTID 模式下 SQL 线程回放遇到未知事务会报错。
高频主从复制的数据一致性怎么保证？Q7

主从复制是最终一致，无法做到强一致。要保证「尽量不丢数据、尽量一致」，靠几个手段叠加：

  • ROW 格式 binlog：避免 statement 格式的不确定函数导致不一致。
  • 半同步复制：保证已提交事务至少有一个从库收到。
  • GTID：精确判断两边事务差异，方便补数据。
  • 定期校验：用 pt-table-checksum 对比主从数据差异，pt-table-sync 修复。
追问：如果发现主从数据已经不一致了，怎么排查修复？用 pt-table-checksum 找出不一致的表和行，再用 pt-table-sync 生成修复 SQL，或直接重做从库（全量备份 + 恢复 + 重新挂复制）。
踩坑：「主从复制保证数据一致」是错误说法。正确说法是「主从复制是异步的最终一致，配合半同步 + ROW 格式 + 校验工具可以接近一致但不保证强一致」。
高频主库挂了，怎么从从库恢复出一个新主库？Q8

手工切换步骤（理解了这个流程，就理解了高可用工具在自动化什么）：

  1. 确认主库状态：是真挂了还是网络抖动，避免误切（双主脑裂）。
  2. 选一个数据最全的从库：比较各从库的 GTID / relay log 位点，选执行到最远的那个。
  3. 让该从库追平：把 relay log 里还没回放完的部分全部回放完（否则会丢数据）。
  4. 提升为新主库：STOP SLAVE; RESET SLAVE ALL; 停止它作为从库的角色，开始接受写。
  5. 其他从库改指向新主库：CHANGE MASTER TO 指到新主库，用 GTID 自动找位点。
  6. 切换应用入口：VIP 漂移或配置改成新主库地址。
追问：这个流程有哪些风险点？① 误判主库挂了导致双主（脑裂）；② 选的从库数据不是最新的导致丢数据；③ 切换过程中业务还在写老主库导致数据分叉。这正是 MHA/MGR/Orchestrator 这些工具要解决的问题（见模块②）。
高频MySQL 5.7 的多线程复制（MTS）解决什么问题？Q9

问题：传统复制从库 SQL 线程是单线程，主库多线程并发写，从库单线程回放，成为性能瓶颈，导致主从延迟。

MTS（Multi-Threaded Slave）：从库 SQL 线程变成多个 worker 线程并行回放。

并行回放的前提：要保证「不破坏事务执行顺序」。5.7 用 LOGICAL_CLOCK（逻辑时钟）方式，主库给事务打上「基于组提交」的序号，同一组的事务可以并行回放（因为它们在主库就是并行提交的，没有冲突）。

追问：并行回放会不会导致执行顺序错乱？不会。只有「在主库上就是同一组提交、没有依赖关系」的事务才会被并行回放，有依赖的（同一行数据的先后修改）会按顺序执行。
加分级联复制和多源复制是什么？Q10
  • 级联复制：A → B → C，B 既是 A 的从库，又是 C 的主库。用于减轻主库 dump 线程压力（一主多从时主库要给每个从库推送，从库多了压力大，用中间层从库转发）。
  • 多源复制：一个从库同时作为多个主库的从库，把多个主库的数据汇聚到一个从库（用于数据汇总、报表、分库合并场景）。
踩坑：级联复制会放大延迟——每一层都多一跳。多源复制要注意不同主库的库名/表名冲突。
加分如何搭建一主一从？（部署步骤速记）Q11
  1. 主库配置 server-id、开启 log-bin、binlog_format=ROW、gtid_mode=ON。
  2. 从库配置不同的 server-id。
  3. 主库创建复制账号：GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%' IDENTIFIED BY '...'。
  4. 主库全量备份（mysqldump --single-transaction --master-data=2 或 xtrabackup），记录 GTID 位点。
  5. 从库导入备份，执行 CHANGE MASTER TO ... MASTER_AUTO_POSITION=1，然后 START SLAVE。

验证：SHOW SLAVE STATUS\G 看 Slave_IO_Running 和 Slave_SQL_Running 都是 Yes。

加分relay log 和 binlog 有什么区别？Q12
  • binlog：主库产生的、记录自己所有变更的日志，是复制的「源」。
  • relay log（中继日志）：从库 IO 线程把主库 binlog 拉下来后存在本地的中转日志，SQL 线程从 relay log 读取并回放。

本质：relay log 是 binlog 在从库上的一份「本地缓存副本」。两者格式一样，但 relay log 回放完就可以清理（relay_log_purge）。

追问：为什么要有 relay log，直接从网络读到就执行不行吗？解耦网络和回放——IO 线程只管拉、SQL 线程只管执行，relay log 是中间的缓冲，避免网络抖动直接卡住回放。
②

高可用切换（HA）

8 题

解决「主库挂了怎么办」。核心矛盾是「快速切换」和「避免误切」——切慢了业务长时间不可用，切错了（脑裂）数据分叉更致命。理解 MHA/MGR/Orchestrator 各自的取舍。

能说清「脑裂为什么危险」「选主凭什么」这两个高可用的核心问题
必考脑裂是什么？为什么危险？怎么避免？Q1

脑裂（Split-Brain）：主从之间网络分区后，从库以为主库挂了，把自己提升为新主库；但老主库其实还活着，还在接受写入。结果两个节点都认为自己是主库，各自接受写，数据分叉，且无法合并。

为什么危险：数据分叉后两条数据线各自演进，切换回来自动合并几乎不可能，会造成数据丢失或覆盖，且用户写入的数据会「消失」。

如何避免：

  • 引入第三方仲裁（Quorum）：让多数派节点投票决定谁是主，少数派自动「自杀」或停止服务（如 MGR 的多数派机制）。
  • Fencing（隔离）：切换前先把老主库「隔离」掉（切断它的写能力），比如通过存储锁、或让老主库「自杀」（MGR 的做法）。
  • 人工确认 + 心跳：判断主库真挂需要多路心跳（网络、进程、磁盘），避免单一判断误判。
追问：MHA 为什么可能脑裂，MGR 为什么不会？MHA 靠一个管理节点（Manager）单点判断，如果 Manager 和主库之间的网络断了但主库还活着，Manager 可能误判主库挂了去切从库，造成脑裂。MGR 靠组内多数派投票（Paxos），少数派无法达成共识就不能成为主，从机制上避免脑裂。
踩坑：「脑裂就是主从网络断了」说得太浅。要讲到「两个节点都认为自己是主，各自接受写，数据分叉无法合并」这个本质危害，以及「用多数派/隔离机制让其中一方自动退出」这个解法。
必考MHA 是什么？工作原理？有什么优缺点？Q2

MHA（Master High Availability）：基于主从复制的外置高可用方案（第三方开源，日本 DeNA 开发），核心是一个 Manager 管理节点 + 多个 Node 部署在每台 MySQL 上。

工作原理：

  1. Manager 定期检测主库心跳。
  2. 发现主库挂了，从所有从库中选一个数据最新的（比较 relay log 位点）。
  3. 让其他从库的差异数据（它们各自 binlog 里比新主库多的部分）补到新主库上，实现「数据补齐」，尽量不丢。
  4. 提升新主库，其余从库改指新主库，VIP 漂移。

优点：切换速度快（通常 10-30 秒）、能补数据减少丢失、成熟稳定。

缺点：Manager 是单点（本身要 HA）；靠位点判断可能误判；只支持一主多从、主从复制，不支持 MGR。

追问：MHA 的「数据补齐」怎么做到的？切换时，MHA 会把「其他从库有、但新主库没有」的 binlog 事件识别出来，应用到新主库上，让新主库追上最新，减少切换丢数据。前提是从库的 binlog 都还在（没被清理）。
踩坑：MHA 已经不再积极维护（作者停更），新项目一般不选它，更多用 MGR 或 Orchestrator。但面试问「用过哪些 HA 方案」时，能讲清 MHA 原理说明你有老项目经验。
必考MGR（组复制）是什么？和传统主从复制的本质区别？Q3

MGR（MySQL Group Replication）：MySQL 官方 5.7.17 引入的内置高可用 + 强一致方案，基于 Paxos 变体（XCom）实现。

本质区别：传统主从是「异步复制」，主库提交后从库慢慢追；MGR 是「同步复制」，一个事务要在组内多数派节点都确认后才能提交（group_replication_consistency 控制）。

维度传统主从MGR
复制方式异步同步（Paxos 共识）
选主人工/外置工具自动（多数派投票）
脑裂可能发生机制上避免（少数派自动退出）
数据一致性最终一致强一致
写性能高较低（要多数派确认）
部署复杂度低高

MGR 有单主（single-primary）和多主（multi-primary）两种模式，生产一般用单主模式，避免多主写冲突。

追问：MGR 为什么能自动选主、避免脑裂？因为它用 Paxos 达成共识——只有拿到多数派（N/2+1）投票的节点才能当选主库。网络分区后，少数派（拿不到多数票）自动退出组，不能成为主，从而避免双主。
踩坑：MGR 的「同步」不是「全同步」，而是「多数派确认」。3 节点时只要 2 个确认就能提交，所以强一致但允许一个节点落后。另外 MGR 要求节点数通常是 3 或 5 的奇数。
高频Orchestrator 是什么？和 MHA/MGR 的区别？Q4

Orchestrator：GitHub 开源的 MySQL 拓扑管理 + 高可用工具（后被 Vitess/PlanetScale 采用）。

核心能力：

  • 拓扑发现与可视化：自动发现并维护整个复制拓扑，提供 Web 界面。
  • 自动故障切换：检测主库故障，自动选主、切换、通知。
  • 人工操作辅助：拖拽式切换主从、重搭从库等。

和 MHA 的区别：MHA 只做「主库挂了的切换」，Orchestrator 管的是整个拓扑（包括中间层、级联、故障恢复后的重建），能力更全面，且是活跃维护的开源项目。

和 MGR 的区别：MGR 是「数据库内置的一致性方案」，Orchestrator 是「外置的、基于普通主从复制的运维工具」，它不提供强一致，但更灵活，可以管复杂的异构拓扑。

追问：什么时候选 Orchestrator，什么时候选 MGR？已经有大量普通主从架构、不想大改、且能接受最终一致 → Orchestrator；新建系统、要强一致、能接受写性能损失 → MGR。很多公司是「MGR 做核心库 + Orchestrator 管周边从库」组合。
高频VIP（虚拟 IP）在高可用里起什么作用？怎么漂移？Q5

VIP 的作用：让应用连接一个固定的虚拟 IP，而不是具体某台 MySQL 的 IP。主库切换时，VIP 漂移到新主库，应用无感知，不用改连接配置。

漂移机制：用 keepalived 或 MHA 自带的 VIP 脚本，检测到主库切换后，把 VIP 从老主库摘除、绑定到新主库，通过 ARP 广播让同网段的机器更新路由。

另一个方案：不用 VIP，用 Proxy。引入 MySQL Router / ProxySQL 作为连接入口，由 Proxy 感知后端主从变化，应用连 Proxy 即可，比 VIP 更灵活（还能做读写分离、连接池）。

追问：VIP 漂移的隐患？① 如果老主库还活着但网络分区，VIP 可能还在老主库上，新主库抢 VIP 会冲突；② ARP 缓存更新不及时，部分客户端还在连老主库。所以 VIP 通常配合「隔离老主库」一起用。
高频主从切换时，怎么做到「数据零丢失」？Q6

完全零丢失做不到（异步复制下主库已提交但没同步到从库的数据，主库一挂就丢了），但可以尽量逼近：

  • 半同步复制：已提交事务至少有一个从库收到，切换过去不丢已提交数据。
  • MHA 数据补齐：切换时把其他从库多余的 binlog 补到新主库。
  • 用 MGR/强一致：多数派确认后才提交，从机制上保证不丢（但要接受写性能代价）。

关键认知：数据零丢失是「CAP 里的一致性」问题，代价是性能。生产上常见做法是「半同步 + MHA/Orchestrator」，在性能和丢数据之间取平衡。

踩坑：别夸口「我们的切换零丢失」。除非用了强一致方案，否则严格说都存在「主库挂了那一瞬间已提交未同步的数据会丢」的窗口。诚实说清楚这个窗口，比吹牛更显专业。
加分什么是「双主」架构？M-M 有什么坑？Q7

双主（Master-Master）：两台机器互为主从，各自都能写，都复制对方的数据。

坑：

  • 写冲突：两边同时写同一行，复制到对端会冲突（主键冲突、数据覆盖）。
  • 自增 ID 冲突：两台都用 auto_increment 会生成相同 ID，要配置 auto_increment_increment=2 + auto_increment_offset 错开。
  • 脑裂风险：和所有「双活写」一样，网络分区后数据分叉。

实际用法：双主常用于「主备切换演练」或「单向写」（平时只写一台，另一台备用），真正「双活双写」很少用（除非 MGR 多主模式 + 冲突检测）。

踩坑：「双主就是两台都能写」是危险的理解。生产上双主绝大多数是「备用写」，不是同时写，否则写冲突和 ID 冲突会让你头疼。
加分PXC（Percona XtraDB Cluster）和 MGR 的区别？Q8
  • PXC：基于 Galera 的多主强一致集群，Percona 出品，事务提交前要在所有（或多数）节点「写入集验证 + 同步」，是同步复制。
  • MGR：MySQL 官方方案，基于 Paxos，多数派确认即可提交。

主要区别：

维度PXC（Galera）MGR
出品方Percona / CodershipMySQL 官方
复制机制写入集同步（全同步）Paxos 多数派
多主写入原生支持多主单主为主，多主需额外处理冲突
成熟度更早、更成熟官方持续演进
追问：为什么说 PXC 是「全同步」？因为它要求事务的「写入集」在提交前被所有节点确认（可配 wsrep_sync_wait 控制），比 MGR 的「多数派确认」更强，但写延迟也更高、对网络要求更苛刻（不适合跨机房）。
③

分库分表（Sharding）

8 题

解决「单库数据量/写入到顶」。核心矛盾是「拆了以后查询和事务变难」——分片键设计决定一切。注意区分「分库」和「分表」是两件事，也别忘了「先优化再拆分」。

能说清「分片键怎么选」「拆分后跨库 join/事务怎么办」「分布式 ID 怎么生成」三大难点
必考分库分表解决什么问题？什么时候才需要分？Q1

解决两个瓶颈：

  • 单库数据量太大：一张表几千万上亿行，查询/DDL 越来越慢，索引也扛不住。
  • 单库写入到顶：写入 QPS 超过单库承载，或单库磁盘/连接数打满。

但「先别急着分」——分库分表代价很大（跨库 join/事务失效、运维复杂度暴涨）。拆分前先做：

  1. SQL 和索引优化：慢 SQL 是不是没走索引？
  2. 读写分离：读压力大先加从库。
  3. 冷热分离 / 归档：历史数据移走，只留热数据。
  4. 缓存：热点数据加 Redis。

这些都做完了还是扛不住，才考虑拆分。

追问：单表多大算「该分了」？经验值（非绝对）：单表超过 1000 万 ~ 5000 万行、或单库超过 几十 GB、或写入/查询 QPS 到顶，开始评估拆分。但要看硬件和业务，不是死数字。
踩坑：面试一上来就说「我们数据量大所以分库分表」会显得没经验。要体现「先优化，拆是最后手段」的判断力，面试官很看重这个。
必考分库和分表有什么区别？水平拆分 vs 垂直拆分？Q2

分库 vs 分表：

  • 分库：数据分散到不同数据库实例，解决单库写入/容量瓶颈，但跨库 join/事务直接失效。
  • 分表：数据分散到同一个库里的多张表（如 order_0 ~ order_7），解决单表数据量大的查询慢问题，仍在同一个库里，还能用库内 join（需指定表）。

水平拆分 vs 垂直拆分：

类型怎么拆解决的问题例子
水平拆分按行拆，同一张表的数据按某个字段分散到多张表/多库单表数据量大、写入瓶颈订单表按 user_id 拆 16 张表
垂直拆分按列/按业务拆，把不同业务或不同字段分到不同表/库表字段太多、不同业务耦合用户信息拆成「基础信息表 + 扩展信息表」；订单库和用户库分开
追问：什么时候垂直拆、什么时候水平拆？先垂直拆（按业务拆分，降低耦合、各库独立扩展），再对单库内的大表做水平拆分。通常是「垂直拆业务 → 水平拆数据」两步走。
必考分片键（sharding key）怎么选？选错了会怎样？Q3

分片键的选择原则：

  • 尽量让查询都带上分片键：这样能精确路由到单个分片，避免全分片扫描。
  • 分布均匀：避免热点（某几个分片数据特别多、请求特别集中）。
  • 避免用自增 ID / 时间戳直接做键：会数据倾斜（新数据全落到最后一个分片）。

常见分片键：user_id（用户维度，电商最常用）、order_id（订单维度）、tenant_id（多租户）。

选错的后果：

  • 热点问题：某分片被大量访问，其他分片闲置。
  • 跨分片查询：大部分查询不带分片键，每次都要扫所有分片再聚合，性能反而更差。
  • 数据倾斜：分片数据量不均，某分片先到顶。
追问：如果业务查询就是不带分片键怎么办？两种思路：① 建全局二级索引（用 ES 或单独索引表，先查索引定位分片再回表）；② 用基因法/冗余，把可能被查的字段也编码进分片键。
踩坑：「分片键选 user_id，但按订单号查询就要扫全表」——这类矛盾要在设计阶段就识别。分片键一旦定了，后期改动的代价极大（要全量迁移数据）。
必考ShardingSphere 是什么？架构和工作原理？Q4

ShardingSphere：Apache 开源的分布式数据库中间件生态，核心组件 ShardingSphere-JDBC 和 ShardingSphere-Proxy。

  • ShardingSphere-JDBC：以 jar 包形式嵌入应用，在应用层做 SQL 解析、路由、改写、结果归并。应用无感知，性能好（无额外网络跳转）。
  • ShardingSphere-Proxy：独立的数据库代理进程，对应用表现为一个 MySQL 服务，适合多种语言、集中管理，但多一跳网络。

核心工作流程（一条 SQL 怎么被处理）：

  1. SQL 解析：解析成 AST，识别表名、分片键、条件。
  2. 路由：根据分片键 + 分片算法，算出要路由到哪个（些）分片。
  3. 改写：把逻辑表名 order 改写成真实表名 order_3，聚合查询改写等。
  4. 执行：把改写后的 SQL 下发到目标分片执行。
  5. 归并：多个分片的结果合并（排序、分页、聚合）。
追问：JDBC 版和 Proxy 版怎么选？单语言 Java 栈、追求性能、想少一层运维 → JDBC 版；多语言、要集中管控、已有中间件团队 → Proxy 版。
踩坑：归并阶段的「跨分片排序、分页、聚合」是性能重灾区。比如 ORDER BY ... LIMIT 跨分片时，要把每个分片的前 N 条都取出来再全局排序，分片越多开销越大。
必考分布式 ID 怎么生成？雪花算法是什么？Q5

为什么需要分布式 ID：分库分表后，每个分片的 auto_increment 会从 1 开始重复，需要全局唯一的 ID。

几种方案：

方案优点缺点
UUID简单、无中心无序，作为主键会导致索引页分裂，且太长
数据库自增简单、有序单点瓶颈、有性能上限
Redis INCR性能好依赖 Redis 持久化，重启可能重复
雪花算法（Snowflake）高性能、趋势递增、无中心依赖时钟，时钟回拨会重复

雪花算法（Snowflake）：64 位长整型，分四段：

  • 1 位符号位（固定 0）
  • 41 位时间戳（毫秒级，可用约 69 年）
  • 10 位机器 ID（5 位机房 + 5 位机器，最多 1024 台）
  • 12 位序列号（同一毫秒内递增，最多 4096 个）

优点：趋势递增（时间戳在前），作为主键利于索引；本地生成无网络开销。

追问：雪花算法的「时钟回拨」问题怎么解决？时钟回拨会导致生成的 ID 比之前小、可能重复。解法：① 回拨时等待时钟追回；② 用「上次时间戳」缓存，回拨时用备份序列号；③ 用美团 Leaf 等方案，靠 ZK 协调；④ 检测到回拨直接抛异常拒绝服务。
踩坑：别用 UUID 做主键（无序导致 B+ 树频繁页分裂，插入性能暴跌）。要「趋势递增」的 ID。
高频分库分表后，跨库 join 和事务怎么办？Q6

跨库 join：分库后不同库的数据无法直接 SQL join。解法：

  • 字段冗余：把要 join 的字段冗余到同一张表，避免 join。
  • 应用层组装：拆成多个查询，在应用层合并结果（最常见）。
  • 全局表（广播表）：把每个分片都要用的小表（如字典表）在每个库都放一份。
  • 宽表 / 汇总表：按查询维度预聚合。

跨库事务：本地事务无法跨库。解法：

  • 避免跨库事务：设计时让「需要事务的操作都落在同一分片」（分片键选好）。
  • 柔性事务 / 最终一致：如本地消息表、可靠消息、TCC、Seata 的 AT 模式。
  • 分布式事务框架：Seata、ShardingSphere 的 XA。
追问：Seata 的 AT 模式怎么做到跨库事务？Seata AT 是「两阶段 + 自动补偿」：一阶段各分支执行本地事务并记录 undo log，二阶段全局提交或回滚（回滚时用 undo log 生成反向 SQL 补偿）。本质是最终一致，不是强一致，中间态对别的事务可见。
踩坑：不要试图用「跨库分布式事务」硬扛所有场景，代价极大。正确的思路是「能避免就避免」——通过分片键设计、字段冗余，让绝大多数事务落在单分片内。
高频分库分表后，分页、排序、聚合查询怎么做？Q7

这些问题都源于「数据分散了，但查询要全局结果」，需要「归并」。

  • 分页（LIMIT）：跨分片分页不能直接 LIMIT 0,10，因为每个分片的前 10 条不是全局前 10 条。正确做法：每个分片取 LIMIT 0, offset+limit，再全局排序取 [offset, offset+limit]。深分页性能差（要取大量数据），要用「游标分页」（记录上一页最后一条的主键，用 WHERE id > last_id）替代。
  • 排序（ORDER BY）：每个分片各自排序，再归并排序。
  • 聚合（COUNT / SUM / MAX）：每个分片算局部聚合，再全局汇总。注意 COUNT 是加和、MAX 是取最大、AVG 不能简单平均（要 sum/count）。
追问：为什么 AVG 不能把各分片的平均值再平均？因为各分片行数不同，加权不同。正确做法是各分片返回 SUM 和 COUNT，全局用 总 SUM / 总 COUNT。
踩坑：深分页（翻到第 100 页）在分库分表下是灾难，尽量用游标分页或限制最大页数。这是面试里体现工程经验的好点。
加分分库分表后怎么做平滑扩容（数据迁移）？Q8

从「8 库」扩到「16 库」，需要数据重新分布 + 平滑切换，常用「双写 + 灰度 + 对比 + 切流」：

  1. 建新分片：按新分片规则建好新库新表。
  2. 双写：新数据同时写老分片和新分片（通过中间件路由或应用双写）。
  3. 历史数据迁移：用工具把存量数据按新规则迁移到新分片。
  4. 数据校验：对比老新数据一致性（行数、抽样校验）。
  5. 灰度切读：先切一部分读流量到新分片，验证无误。
  6. 全量切流：读写都切到新分片，下线老分片。
追问：双写期间数据不一致怎么办？双写天然有「两边写成功但另一条失败」的窗口。方案：① 双写走同一事务（不跨库则不行）；② 迁移完成前以老分片为准，用对账/补偿任务修复不一致；③ 用 binlog 订阅（如 Canal）同步增量。
踩坑：扩容一定要「可回滚」——切流前保留老分片一段时间，出问题能切回去。一次性切死没有退路。
④

分布式一致性（Consensus）

8 题

最高阶模块，是 MGR/PXC 的底层原理。核心抓住一条线：CAP 不可兼得 → 用共识算法（Paxos/Raft）在分区容错前提下选一致性 → 落地到 MGR。这部分答好了是加分项。

能讲清 CAP 三选二、Raft 的选主与日志复制、以及「强一致为什么慢」
必考CAP 理论是什么？为什么说「P 必须选」？Q1

CAP：一个分布式系统在一致性（Consistency）、可用性（Availability）、分区容错（Partition tolerance）三者中，最多只能同时满足两个。

  • C 一致性：所有节点同一时刻读到相同的数据。
  • A 可用性：每个请求都能在合理时间内得到响应（不一定是最新数据）。
  • P 分区容错：网络分区（节点间通信中断）时系统仍能继续工作。

为什么 P 必须选：因为网络分区是不可避免的（网络不可靠是客观事实，不是你能选的）。所以实际是在「分区发生时，选 C 还是 A」之间做权衡：

  • 选 CP：分区时放弃可用性，保证一致（如 MGR、ZooKeeper、etcd）。
  • 选 AP：分区时保证可用，容忍不一致（如传统主从、Eureka）。
追问：MySQL 主从复制是 AP 还是 CP？是 AP——主从复制是异步的，网络分区时从库依然可读（可用），但可能读到旧数据（不一致）。而 MGR 是 CP——分区时少数派自动退出，宁可不可用也不返回不一致数据。
踩坑：「CAP 只能三选二」的严格表述有争议（P 其实必须选），正确的说法是「网络分区发生时，只能在 C 和 A 之间二选一」。能说出这个 nuance，说明你不是死记硬背。
必考强一致、弱一致、最终一致的区别？Q2
  • 强一致：写入后，任何后续读都能读到最新值（如 MGR 多数派确认后提交）。
  • 弱一致：写入后不保证能立刻读到，可能读到旧值，也没有「最终会一致」的保证。
  • 最终一致：弱一致的特例——保证在没有新写入的情况下，经过一段时间后，所有副本会收敛到一致（如传统主从复制）。

核心区别在「读写的先后保证」：强一致保证「写后读一定最新」，最终一致只保证「最终会一样，但中间可能读到旧数据」。

追问：MySQL 主从是「最终一致」，那它能做到「读自己刚写的」吗？不能直接保证。写主库后立刻读从库，可能读到旧值（主从延迟）。要「读己之写」，要么读主库，要么用半同步 + 延迟控制。这是「最终一致」和「强一致」的实际差距。
必考Raft 共识算法怎么工作的？（选主 + 日志复制）Q3

Raft：一种「易于理解」的共识算法（相对 Paxos），把问题拆成两个子问题：选主（Leader Election）和日志复制（Log Replication）。节点有三种角色：Leader（主）、Follower（从）、Candidate（候选）。

选主：

  1. 所有节点初始是 Follower，有个随机的选举超时时间。
  2. 超时没收到 Leader 心跳，Follower 变 Candidate，任期号 +1，给自己投票并请求其他节点投票。
  3. 拿到多数派（N/2+1）投票的 Candidate 当选 Leader。
  4. 如果两个 Candidate 同时选举、票数都没过半，则各自超时重来（随机超时避免冲突）。

日志复制：

  1. Leader 收到写请求，追加到本地日志。
  2. 把日志发给所有 Follower。
  3. 收到多数派确认后，Leader 提交（commit），返回客户端。
  4. Follower 在下次心跳时知道日志已提交，再应用到状态机。
追问：Raft 怎么保证「已提交的日志不会丢」？因为提交需要多数派确认，任意两个「多数派」集合必有交集，所以即使 Leader 挂了，新 Leader 一定包含所有已提交的日志。
踩坑：别把「日志复制到 Follower」和「日志已提交」混为一谈。Raft 里日志是先复制、后提交，只有 Leader 收到多数派确认才 commit，此时才对外可见。
高频Paxos 和 Raft 有什么区别？为什么大家都用 Raft？Q4
  • Paxos：提出更早（Lamport），理论完备但难理解、难实现，且只解决「单值共识」，做多值共识（连续日志）要叠加 Multi-Paxos，工程落地困难。
  • Raft：专门为「易理解、易实现」设计，把共识拆成「选主 + 日志复制 + 安全性」几个清晰模块，直接支持「连续日志」（多值共识），工程上容易落地。

为什么都用 Raft：工程可用性。etcd、TiKV、Consul 等都用了 Raft。Paxos 虽然理论上更早，但实现难度高，业界很少直接按原始 Paxos 落地。

追问：Raft 相比 Multi-Paxos 本质优势是什么？Raft 通过「强 Leader + 任期号 + 日志连续性」把「选主」和「日志复制」解耦并强制了更强的约束，使得「哪个日志能提交、谁有最新日志」一目了然，而 Paxos 的这两个问题纠缠在一起，实现极易出错。
高频MGR 是怎么用 Paxos 实现强一致和选主的？Q5

MGR（组复制）底层用 XCom（一个 Paxos 变体）实现组通信和共识。

事务提交流程（强一致）：

  1. 主节点执行事务，把「写集（write-set）」广播给组内所有节点。
  2. 各节点对写集做冲突检测（多主模式下）并投票。
  3. 拿到多数派确认后，事务才正式提交。
  4. 各节点本地应用这个写集。

选主 / 脑裂避免：

  • 节点靠组通信维持成员关系，网络分区后，只有能组成多数派的组才能继续服务。
  • 少数派（凑不齐多数派）自动「停止服务」（宁可不可用，也不接受写），从而避免脑裂。
  • 多数派组内重新选主。
追问：MGR 为什么要求奇数节点（3/5/7）？为了多数派判断。3 节点多数派是 2（容 1 台挂），5 节点是 3（容 2 台挂）。偶数节点（如 4 节点多数派 3）容错能力和 3 节点一样，反而多一台成本，所以用奇数。
踩坑：MGR 的「强一致」代价是写性能下降——每个事务都要跨节点广播 + 等多数派确认，跨机房部署时网络延迟会放大这个代价。所以 MGR 不适合跨地域大延迟场景。
高频为什么强一致方案写性能会差？「多数派」是什么？Q6

强一致写性能差的原因：一个写事务要「跨节点网络广播 + 等待多数派确认」才能提交，多了至少一次网络往返（RTT），且要等最慢的那个「多数派成员」确认。对比异步主从「写本地 binlog 就返回」，性能差距明显。

多数派（Quorum）：N/2 + 1 个节点。3 节点就是 2 个，5 节点就是 3 个。

为什么用多数派：

  • 任意两个多数派集合必有交集（所以已提交数据不会丢，见 Raft 那题）。
  • 一个集群最多容 N/2 - 1 台节点故障（3 节点容 1 台，5 节点容 2 台）。
  • 分区后，只能有一个多数派组，天然避免双主。
追问：3 节点集群挂 2 台还能服务吗？不能。只剩 1 台，凑不齐多数派（2），会停止服务（CP 选择，宁可不一致也不可用）。这就是「多数派决定了可用节点下限」。
加分什么是「脑裂」在共识系统里的处理？和主从的脑裂有何不同？Q7

共识系统（Raft/MGR）里的脑裂：网络分区后可能出现「两个 Leader」——但这在 Raft 里被任期号 + 多数派机制天然解决：

  • 分区后，旧 Leader 在少数派侧，收不到多数派确认，无法提交任何新日志（等于失去写能力）。
  • 多数派侧会重新选出一个新 Leader（任期号更高）。
  • 旧 Leader 恢复通信后，发现新 Leader 任期号更高，自动降级为 Follower。

和主从脑裂的本质不同：

  • 主从：靠外置工具判断，可能「两个节点都认为自己能写」，数据真分叉。
  • 共识系统：靠「任期号 + 多数派」从机制上保证同一时刻只有一个 Leader 能提交，旧 Leader 无法写入，所以不会真分叉，只是短暂「旧 Leader 以为自己还是主，但写不进去」。
踩坑：要能区分「旧 Leader 以为自己还是主」和「两个主都能写」——前者是共识系统里无害的短暂幻觉，后者是主从架构里危险的真脑裂。
加分如何给一个系统选「复制方案」？（决策框架）Q8

没有银弹，按业务对「一致性 vs 可用性 vs 性能」的取舍选：

场景推荐方案理由
读多写少、能接受秒级延迟主从复制 + 读写分离性能最好、最成熟、成本低
要快速自动切换、数据尽量不丢半同步 + MHA/Orchestrator平衡性能和可用性
强一致、零丢失、能接受写性能损失MGR / PXC金融、账户等一致性敏感场景
数据量到顶、写入瓶颈分库分表 + 中间件和复制正交，可叠加

决策要点：先问「能接受多少数据丢失 / 多长不一致窗口」，再问「写性能要求多高」，两者决定选异步、半同步还是强一致。

追问：如果老板说「既要零丢失又要高性能」怎么办？诚实告诉他这两者在 CAP 下不能兼得，需要做取舍：要么接受性能损失用强一致，要么接受极小丢失窗口用半同步。硬要两者都占，只能分层——核心数据强一致、边缘数据异步。
踩坑：这是面试的「架构判断题」，答「看情况，没有银弹，先问一致性要求」比直接甩一个方案高级得多。体现的是架构权衡能力。
