① Docker 核心 原理 · 容器 vs 虚拟机

Docker 是什么？容器和虚拟机的区别？必考已掌握

一句话

Docker 是容器化平台，把应用 + 依赖打包成一个「可移植的镜像」，在任何装了 Docker 的机器上都能一致运行。

容器 vs 虚拟机

维度容器虚拟机
隔离层级进程级（共享宿主机内核）硬件级（每个 VM 有独立 OS）
启动速度秒级分钟级
资源占用小（MB 级）大（GB 级）
隔离性较弱（共享内核）强（完全隔离）
性能接近原生有虚拟化损耗

核心原理（三个关键技术）

  • Namespace（命名空间）：隔离进程、网络、文件系统等，让容器「看不见」其他容器。
  • Cgroup（控制组）：限制 CPU、内存等资源使用。
  • UnionFS（联合文件系统）：镜像分层叠加，实现镜像复用和快速构建。
追问：「容器不是虚拟机」——容器共享宿主机内核，所以 Linux 容器不能跑 Windows 应用。这是理解容器本质的关键。
Docker 镜像的分层结构？为什么分层能加速构建？必考已掌握

分层原理

Dockerfile 的每条指令（FROM、RUN、COPY 等）生成一个只读层，层与层叠加成完整镜像。最终在只读层之上加一个可写容器层。

为什么加速构建

  • 层缓存：某层没变化，直接复用缓存，不用重新执行。
  • 层共享：多个镜像可以共享相同的基础层（如都基于 ubuntu），节省存储和传输。

优化技巧

  • 顺序：变化少的层放前面（如依赖安装），变化多的放后面（如代码 COPY），充分利用缓存。
  • 合并 RUN：多条 RUN 合并成一条，减少层数。
坑：「先 COPY 代码再 RUN npm install」会导致代码一变，依赖层缓存全失效。正确做法是「先 COPY package.json 再 install，最后 COPY 代码」，把依赖安装层缓存住。

镜像与运行

docker build -t my-app:v1.0 .          # 构建镜像（-t 打标签）
docker images                            # 查看本地镜像
docker rmi <image>                        # 删除镜像
docker tag <src> <dst>                    # 重新打标签

docker run -d -p 8080:8080 -v /data:/data --name app my-app:v1.0
# -d 后台运行；-p 宿主机:容器端口映射；-v 挂载卷；--name 命名

容器生命周期

docker ps            # 运行中的容器
docker ps -a         # 所有容器（含已停止）
docker start/stop/restart <id>
docker rm <id>        # 删除容器
docker inspect <id>   # 查看容器详细配置

进入容器（排障核心）

docker exec -it <id> /bin/bash    # 交互式进入，退出用 exit（不影响容器）
docker exec -it <id> sh           # 精简镜像无 bash 时用 sh
docker exec <id> <命令>            # 非交互执行单条命令（如 ls、ps、top）

注意：docker attach 是连到容器主进程的 stdin/stdout，退出会导致容器停止；排障一律用 exec 而非 attach。

看日志

docker logs <id>            # 查看全部日志
docker logs -f <id>         # 实时跟踪（tail -f 效果）
docker logs --tail 100 <id> # 只看最后 100 行
docker logs --since 30m <id>  # 最近 30 分钟
docker logs -t <id>         # 带时间戳

复制文件

docker cp <id>:/path/file ./local      # 容器 → 宿主机（导出日志/配置）
docker cp ./local <id>:/path/file      # 宿主机 → 容器（注入配置）
追问：生产环境容器多了，怎么统一看日志？—— 靠 docker logs 一个个看不现实，要用集中式日志（EFK / Loki + Grafana），容器日志经 json-file 驱动或 stdout 采集到外部。
坑：容器是无状态的，容器删除后内部数据丢失。要持久化的数据（数据库、日志、上传文件）必须用 -v 挂载到宿主机卷，否则容器一重建数据就没了。

② 镜像与优化 Dockerfile · 瘦身 · 多阶段

一个 Java 应用的 Dockerfile 怎么写？有哪些优化点？必考已掌握

基础版 Dockerfile

FROM openjdk:17-jdk-slim
COPY target/app.jar /app/app.jar
WORKDIR /app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

优化点（面试加分项）

  1. 多阶段构建：构建阶段用大镜像（含 Maven），运行阶段用小镜像（只含 JRE），减小体积。
  2. 用 JRE 而非 JDK：运行只需要 JRE，用 eclipse-temurin:17-jre 更小。
  3. 基础镜像选 slim/alpine：减小体积，但 alpine 用 musl libc，某些依赖可能不兼容，要测试。
  4. 健康检查：HEALTHCHECK 配合 K8s 探针。

多阶段构建示例

# 阶段1：构建
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# 阶段2：运行（小镜像）
FROM eclipse-temurin:17-jre
COPY --from=build /src/target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
核心：「构建用大镜像，运行用小镜像」的多阶段构建是标配。能说出「镜像体积从几百 MB 优化到几十 MB」就是加分。
Java 应用在容器里内存怎么配置？为什么会有 OOM 问题？必考已掌握

容器里的内存坑（经典问题）

Java 8 早期版本（< 8u131）读的是宿主机内存而非容器内存限制，导致 JVM 堆设太大，容器 OOM 被杀。

解决方案

  • 用容器感知的 JVM：Java 10+ 默认感知容器限制，Java 8u131+ 加 -XX:+UseContainerSupport。
  • 显式设堆：-Xmx 设为容器内存的 50~70%，留出堆外内存（元空间、线程栈、直接内存）。
  • K8s 资源限制：设置 resources.limits.memory，别让容器超限。

内存分配原则

JVM 内存 = 堆 + 元空间 + 线程栈 + 直接内存 + 代码缓存。堆只是其中一部分，别把容器内存全分给堆，要留余量给堆外。

核心：「容器内存 ≠ JVM 堆」。容器限制 2G，堆设 2G 必然 OOM。堆设 1.2~1.4G，剩下的给堆外。这是容器化 Java 最常见的坑。

瘦身手段

手段效果说明
多阶段构建去掉构建工具最终镜像不含 Maven/Gradle

distroless 镜像

Google 的 distroless 镜像只含运行时，连 shell 都没有，体积极小、攻击面小，但没法 exec 进去排查，适合生产无状态服务。

核心：镜像瘦身不只是「省空间」，更是「减小攻击面 + 加速部署」。生产镜像追求「够用最小」，去掉 shell、编译工具、无关文件。

③ K8s 核心概念 Pod · Deployment · Service · Ingress

Pod、Deployment、Service、Ingress 分别是什么？什么关系？必考已掌握

四者关系（核心）

Deployment 管理 Pod，Service 给 Pod 提供稳定入口，Ingress 把外部流量路由到 Service。

对象作用关键点
Pod最小调度单元，跑容器一个 Pod 可含多个共享网络的容器
Deployment管理 Pod 副本数、滚动更新、回滚声明式，定义「期望状态」
Service给一组 Pod 提供稳定的 VIP + 负载均衡Pod 重启 IP 会变，Service 不变
Ingress七层路由（域名/路径 → Service）类似 Nginx，对外暴露 HTTP

为什么需要 Service

Pod 是易失的（重启、扩容、故障都会重建，IP 会变）。Service 通过 Label Selector 关联一组 Pod，提供稳定的虚拟 IP，客户端只访问 Service，不关心具体 Pod。

核心：「Deployment 管数量、Service 管访问、Ingress 管路由」。这是 K8s 最核心的抽象分层，面试必问。
Deployment 的滚动更新是怎么工作的？怎么回滚？必考已掌握

滚动更新原理

  1. 更新 Deployment 的镜像版本。
  2. 创建一个新的 ReplicaSet，逐步增加新 Pod。
  3. 同步减少旧 ReplicaSet 的 Pod。
  4. 新旧交替，直到全部替换完成，全程不停机。

关键参数

  • maxSurge：更新时最多额外新建几个 Pod（峰值超出期望数的量）。
  • maxUnavailable：更新时最多几个 Pod 不可用。

回滚

kubectl rollout undo deployment/my-app          # 回滚到上一版本
kubectl rollout undo deployment/my-app --to-revision=2   # 回滚到指定版本
kubectl rollout history deployment/my-app       # 查看历史版本
核心：Deployment 的滚动更新 + 回滚，是「零停机发版」的基础。配合「就绪探针」（新 Pod 就绪才接入流量），实现无感发布。

④ K8s 调度与网络 调度 · 探针 · 服务发现

K8s 的三种探针（liveness/readiness/startup）分别是什么？必考已掌握
探针作用失败后果
livenessProbe（存活）判断容器是否「活着」重启容器（治死循环/死锁）
readinessProbe（就绪）判断容器是否「能接流量」从 Service 摘除，不再路由
startupProbe（启动）判断容器是否「启动完成」启动慢的应用，保护不被误杀

关键区分

  • liveness 管「重启」：应用死循环、卡死，重启救活。
  • readiness 管「流量」：应用启动中、依赖没连上、内存高，摘流量，但不重启。
  • startup 管「启动期」：启动慢的应用（如 Spring Boot 启动 60s），防止 liveness 在启动期就误杀。
坑：liveness 和 readiness 要区别对待。readiness 探测失败只是摘流量，容器还活着；liveness 失败会重启。别把「依赖服务挂了」配成 liveness，否则会无限重启。
Pod 调度到哪个节点是怎么决定的？资源怎么限制？高频已掌握

调度流程

  1. 过滤（Predicates）：排除不满足条件的节点（资源不够、有污点、节点标签不匹配）。
  2. 打分（Priorities）：对剩余节点打分（资源均衡、亲和性），选最高分。

资源限制

resources:
  requests:        # 调度时保证的最小资源
    cpu: "500m"
    memory: "512Mi"
  limits:          # 运行时的最大上限
    cpu: "1"
    memory: "1Gi"
  • requests：调度依据，保证 Pod 至少拿到这么多资源。
  • limits：资源上限，超出 CPU 会被限流（throttle），内存超出会 OOM 被杀。

高级调度

  • nodeSelector / 亲和性（affinity）：指定 Pod 跑在特定节点（如 GPU 节点）。
  • 污点（taint）+ 容忍（toleration）：标记特殊节点，只有容忍的 Pod 才能调度上去。
核心：「requests 决定调度，limits 决定上限」。合理设置能避免「资源竞争」和「OOM 被杀」。这是 K8s 资源管理的核心。
K8s 里服务间怎么互相发现和调用？高频已掌握

两种服务发现方式

方式原理适用
K8s 原生（DNS）Service 名解析为 ClusterIP（my-svc.default.svc.cluster.local）K8s 内部服务互调
注册中心（Nacos/Eureka）应用自己注册到 Nacos，客户端拉取实例列表Spring Cloud 微服务

Spring Cloud + K8s 的冲突与解决

Spring Cloud 有 Nacos 做服务发现，K8s 也有 Service 做服务发现，两者会重复。常见做法：

  • 保留 Nacos：微服务治理（熔断、限流、配置）依赖 Nacos，K8s 只做部署。
  • 或用 K8s 原生：Spring Cloud Kubernetes 项目，用 K8s Service 替代 Nacos 做服务发现。
核心：「Nacos 管服务治理，K8s 管部署」是常见分工。面试要能说清「为什么有了 K8s 还要 Nacos」——因为 K8s Service 只解决「发现」，不解决「熔断/限流/灰度/配置」这些治理能力。

⑤ CICD 流水线 Jenkins · GitLab CI · 自动化

CICD 是什么？一条完整的发布流水线包含哪些步骤？必考已掌握

CI / CD 概念

  • CI（持续集成）：代码提交后自动构建、测试，尽早发现问题。
  • CD（持续交付/部署）：自动化把构建产物发布到环境，减少人工。

完整流水线步骤

  1. 代码提交：push 到 Git，触发流水线（webhook）。
  2. 构建：拉代码 → 编译 → 打包（Maven/Gradle）。
  3. 测试：单元测试 → 静态扫描（SonarQube）→ 可选集成测试。
  4. 打包镜像：Docker build → 推送到镜像仓库（Harbor/阿里云 ACR）。
  5. 部署：更新 K8s Deployment 镜像版本（kubectl / Argo CD）。
  6. 验证：健康检查、冒烟测试。
  7. 通知：成功/失败通知（钉钉/邮件）。
核心：「提交即触发，自动构建 → 测试 → 打包 → 部署 → 验证」，目标是「人工只做审批和确认，重复劳动全自动化」。
Jenkins 和 GitLab CI 怎么选？常用的 CICD 工具有哪些？高频已掌握
工具类型特点
JenkinsCI 服务器最流行、插件丰富、灵活，需自维护
GitLab CI集成在 GitLab和代码托管一体，配置用 yaml，省心

  • 代码在 GitLab → 用 GitLab CI（省得维护 Jenkins）。
  • 复杂流水线、多工具集成 → Jenkins（插件生态强）。
  • K8s 部署 → 结合 Argo CD 做 GitOps（声明式，配置即代码）。
核心：面试要能说出「用过 Jenkins/GitLab CI，理解流水线阶段」，并能讲清「构建 → 测试 → 镜像 → 部署」每个阶段做了什么。
什么是 GitOps？和传统 CI/CD 有什么区别？加分已掌握

GitOps 概念

把「部署配置（yaml）也存到 Git 仓库」，以 Git 作为「单一事实来源」。改部署 = 改 Git 配置，Argo CD 等工具自动同步到集群。

传统 CI/CD vs GitOps

维度传统 CI/CD（Push）GitOps（Pull）
部署方式CI 主动推（kubectl apply）Agent 主动拉（对比 Git 和集群状态）
事实来源CI 配置Git 仓库
回滚重新部署Git revert，天然可追溯
审计较弱强（Git 提交记录）

GitOps 优势

  • 可审计：所有变更都有 Git 提交记录。
  • 可回滚：git revert 即可回滚。
  • 声明式：集群状态始终和 Git 配置一致。
加分：能说出「Argo CD / Flux + GitOps」，体现对现代部署实践的了解，是 K8s 方向面试的加分项。

⑥ 发版策略 灰度 · 蓝绿 · 金丝雀 · 回滚

滚动、蓝绿、灰度（金丝雀）三种发版策略怎么选？必考已掌握
策略原理优点缺点
滚动发布逐个替换 Pod，新旧并存过渡零停机、简单回滚慢，过渡期新旧混合
蓝绿部署两套完整环境，流量一键切换秒级回滚、隔离彻底资源翻倍
灰度（金丝雀）先放量给少量用户，验证后全量风险可控、逐步验证实现复杂，需流量控制

选型建议

  • 日常发布：滚动发布（K8s Deployment 默认）。
  • 需秒级回滚、重大变更：蓝绿部署。
  • 高风险、要逐步验证：灰度（金丝雀），配合 Istio / 网关按比例分流。
核心：「滚动省资源、蓝绿快回滚、灰度控风险」。面试要能结合业务说选型，而不是背定义。
灰度发布怎么实现？流量怎么按比例/按用户切？必考已掌握

灰度发布的三种实现

方式原理粒度
网关层灰度网关按 Header/用户 ID 路由到灰度版本按用户
Service Mesh（Istio）按权重分流（如 10% 新版本）按比例
K8s IngressIngress 配 Canary 规则分流按 Header/权重

典型灰度流程

  1. 部署新版本（灰度 Deployment，少量副本）。
  2. 按用户 ID 哈希 / Header 切 5~10% 流量到灰度版本。
  3. 观察指标（错误率、RT、业务指标），对比基线。
  4. 没问题逐步放量（10% → 30% → 100%）。
  5. 出问题立即切回旧版本。
坑：灰度要保证「同一用户始终路由到同一版本」（会话粘滞），否则用户刷新页面可能跳到不同版本，体验割裂。用用户 ID 哈希实现。
发版失败怎么回滚？数据库变更能回滚吗？必考已掌握

应用回滚

  • K8s：kubectl rollout undo 回滚到上一版本。
  • 镜像：回滚 = 重新指定旧版本镜像 tag。
  • GitOps：git revert 提交，Argo CD 自动同步。

数据库变更回滚（核心难点）

「代码能回滚，数据回不了」。数据库变更要「向后兼容」，用「先扩展、后收缩」策略：

  1. 扩展阶段：只加字段/表，不删不改，旧版本代码还能跑。
  2. 稳定阶段：新旧代码共存，观察没问题。
  3. 收缩阶段：确认新版本稳定后，再删旧字段/表。
核心：「数据库变更要能兼容新旧两个版本」。直接改字段类型/删字段，会导致回滚后旧代码报错。这是发版最容易出事故的地方。
怎么保证发版「用户无感」？优雅上下线怎么做？高频已掌握

优雅下线（K8s）

  1. 收到终止信号（SIGTERM）。
  2. 从 Service 摘除（readiness 探针失败，不再接新流量）。
  3. 等待在途请求处理完（terminationGracePeriodSeconds，如 30s）。
  4. 释放资源后真正退出。

Spring Boot 侧配置

server:
  shutdown: graceful          # 优雅停机
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 最多等 30s

配合 preStop 钩子

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 10"]  # 摘流量后等 10s 再退出
核心：优雅下线 = 「摘流量 → 等在途请求 → 退出」三步。配合滚动发布 + 就绪探针，实现「用户无感发版」。

多环境（dev/test/prod）怎么用 K8s 管理？高频已掌握

多环境管理方案

方式原理适用
Namespace 隔离一个集群分多个 namespace（dev/test/prod）小团队，资源有限
多集群隔离每个环境独立集群生产要强隔离，安全要求高

环境差异管理

  • ConfigMap/Secret 按环境分：app-config-dev、app-config-prod。
  • Helm 或 Kustomize：用模板管理不同环境的差异配置。
坑：「生产环境必须和测试隔离」。用同一个 namespace 管 dev/prod，稍有不慎就会把测试配置/操作误用到生产。生产环境建议独立集群或至少强隔离的 namespace + 权限控制（RBAC）。
Pod 起不来 / 反复重启怎么排查？常用排障命令？必考已掌握

排障思路（从上到下）

  1. 看状态：kubectl get pods（Pending / CrashLoopBackOff / ImagePullBackOff）。
  2. 看事件：kubectl describe pod <name>（Events 里看拉镜像失败、调度失败、探针失败）。
  3. 看日志：kubectl logs <pod>（应用报错）。
  4. 进入容器：kubectl exec -it <pod> -- /bin/bash 排查环境。

常见问题对照

状态原因排查
Pending资源不足 / 无法调度describe 看调度失败原因
ImagePullBackOff镜像拉不下来检查镜像名/tag/仓库权限
CrashLoopBackOff容器启动后崩溃logs 看启动报错
OOMKilled内存超限看 limits 设置，调大或查内存泄漏
核心：排障顺序「get → describe → logs → exec」，从状态到事件到日志到容器内部，逐层深入。这是 K8s 排障的标准路径。
容器里应用日志怎么收集？日志丢失怎么办？高频已掌握

日志收集方案

  • 标准输出 + 采集器：应用日志打到 stdout，Filebeat/Fluentd 采集到 ES。
  • Sidecar 容器：一个日志采集 sidecar 和应用同 Pod，采集文件日志。

容器日志的坑

  • 容器重建日志丢失：容器删除后，stdout 日志和容器内文件都没了 → 日志必须实时采集到外部（ES/Loki），不能只存容器内。
  • 日志过大：控制日志级别 + 采样，避免日志量压垮存储。
核心：「容器是易失的，日志不能只存在容器里」。最佳实践是「应用输出 stdout → 采集器实时采集 → 集中存储（ES/Loki）→ 可视化（Kibana/Grafana）」。丢失日志 = 无法排查问题。
Helm 是什么？为什么要用 Helm 管理应用？加分已掌握

Helm 概念

Helm 是 K8s 的包管理器，像「apt/yum」之于 Linux。用 Chart（模板 + 值）定义一套应用的所有资源。

解决的问题

  • 管理复杂应用：一个应用有 Deployment、Service、ConfigMap、Ingress 等一堆资源，Helm 打包成一个 Chart 统一管理。
  • 参数化部署：用 values.yaml 区分环境，同一 Chart 部署到不同环境。
  • 版本管理 + 回滚：helm rollback 一键回滚。
helm install my-app ./chart -f values-prod.yaml   # 安装
helm upgrade my-app ./chart -f values-prod.yaml    # 升级
helm rollback my-app 1                              # 回滚
加分：「用 Helm 管理应用，Kustomize 做环境差异化」是现代 K8s 部署的标配认知。面试能说出 Helm 的「模板化 + 版本管理 + 回滚」价值即可。
