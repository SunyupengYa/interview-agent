必考IoC 是什么？解决了什么问题？

IoC（控制反转）：对象的创建、组装、生命周期管理的控制权，从程序员手里（new）反转给 Spring 容器。你只声明"我需要什么"（@Autowired），不负责"怎么造出来"。

解决的核心问题：

  • 解耦：上层依赖接口，具体实现由容器注入。换实现类（如 MySQL 换 PG）不用改业务代码，改配置即可。
  • 统一管理生命周期：单例复用、销毁回调，不用自己管对象创建销毁。
  • 便于测试：测试时注入 Mock 对象，天然支持替换。

DI 和 IoC 的关系：IoC 是思想（控制权反转），DI（依赖注入）是实现手段（容器把依赖"注入"进来）。构造器注入、Setter 注入、字段注入都是 DI 的形式。构造器注入最推荐——依赖不可变、必填、不会 NPE，且能暴露循环依赖。

追问：为什么说字段注入不好？不能设 final、脱离容器无法用（纯 new 单测直接 NPE）、隐藏依赖关系（类签名上看不出依赖了谁）、掩盖循环依赖。
// ❌ 字段注入：不能 final、纯单测 new 出来直接 NPE、类签名看不出依赖了谁
@Service
public class OrderService {
    @Autowired
    private UserService userService;
}

// ✅ 构造器注入（Spring 4.3+ 单构造器可省 @Autowired）：不可变、必填、依赖显式
@Service
public class OrderService {
    private final UserService userService;
    public OrderService(UserService userService) {
        this.userService = userService;
    }
}
记忆点：IoC=创建权反转给容器DI 是 IoC 的手段构造器注入最稳
必考讲一下 Bean 的完整生命周期

按 实例化 → 属性注入 → 初始化 → 使用 → 销毁 五大阶段讲，细节环节见流程图：

最容易加分的点：说出 BeanPostProcessor 的两个钩子位置——AOP 的代理对象正是在 postProcessAfterInitialization（AnnotationAwareAspectJAutoProxyCreator）里创建的。这一句能引出后面"三级缓存为什么要提前暴露工厂"的问题。

追问：@PostConstruct 和 afterPropertiesSet 谁先执行？@PostConstruct 先（CommonAnnotationBeanPostProcessor 处理），再 afterPropertiesSet，最后 init-method。三个都配，按这个顺序全执行。
踩坑：别把"生命周期"答成"单例池存取"。面试官等着你提 BeanPostProcessor 和 AOP 代理生成时机，漏了这两点等于只背了一半。
@Component
public class CacheWarmUp implements BeanNameAware, InitializingBean, DisposableBean {

    @Autowired
    private CacheClient cache;                    // ② 属性注入

    @Override
    public void setBeanName(String name) { ... }  // ③ Aware 回调

    @PostConstruct
    public void warmUp() { ... }                  // ⑤ 初始化①：先执行

    @Override
    public void afterPropertiesSet() { ... }      // ⑤ 初始化②

    @PreDestroy
    public void cleanUp() { ... }                 // ⑧ 销毁：先执行
}
// ④⑥ BeanPostProcessor 不需要你写也能讲：容器回调它，
//     AOP 代理正是在 postProcessAfterInitialization 里生成的
记忆点：造（实例化）装（属性注入）醒（Aware）前洗（BPP-before）启用（初始化三连）后洗（BPP-after→AOP）上岗（单例池）退休（销毁三连）
必考什么是循环依赖？Spring 怎么用三级缓存解决？

循环依赖：A 依赖 B，B 又依赖 A。手动 new 必死锁，Spring 靠"提前暴露半成品"解决 单例 + Setter/字段注入 的循环依赖。

三级缓存（DefaultSingletonBeanRegistry 里三个 Map）：

缓存存什么作用
一级 singletonObjects完整的成品 Bean正常获取单例的地方
二级 earlySingletonObjects提前暴露的半成品（已实例化、未完成属性注入）循环依赖时快速取，避免重复创建
三级 singletonFactoriesObjectFactory 工厂（能产出早期引用或代理）关键：按需决定给"原始对象"还是"AOP 代理"
// DefaultSingletonBeanRegistry#getSingleton（简化）——三级缓存的取值顺序
Object o = this.singletonObjects.get(beanName);            // ① 查一级：成品？
if (o == null) {
    o = this.earlySingletonObjects.get(beanName);          // ② 查二级：半成品？
    if (o == null) {
        ObjectFactory<?> factory = this.singletonFactories.get(beanName); // ③ 查三级
        if (factory != null) {
            o = factory.getObject();                       // 调工厂：按需给原始对象或代理
            this.earlySingletonObjects.put(beanName, o);   // 工厂降级进二级
            this.singletonFactories.remove(beanName);      // 保证代理只建一次
        }
    }
}
记忆点：三级缓存=提前暴露工厂成品·半成品·工厂B 借工厂拿 A
必考为什么必须三级缓存？二级缓存不够吗？

这是三级缓存的高阶追问，答好直接拉开差距。

结论：如果没有 AOP，二级缓存完全够用（半成品放二级，循环依赖时取半成品）。三级缓存的唯一价值是 AOP——保证"循环依赖场景下注入的也是最终代理对象"，且"代理只生成一次"。

推理过程：

  1. 正常流程：AOP 代理在初始化之后（postProcessAfterInitialization）才生成。
  2. 但循环依赖要求 A 在属性注入前就把自己借给别人。此时 A 还没初始化，不该提前生成代理（破坏生命周期语义，且无法确定是否真的需要代理）。
  3. 折中方案：三级缓存存的是工厂（ObjectFactory），不是对象。B 真来借的时候，工厂里的 getEarlyBeanReference 才按需决定：无 AOP → 给原始对象；有 AOP → 此刻生成代理并返回。
  4. 同时把工厂从三级缓存降级为二级缓存里的对象，保证同一条消息"代理只建一次"，A 初始化完成时不会二次生成代理。
追问：直接在实例化后就生成代理放二级缓存不行吗？功能上能解决循环依赖，但违反了 Spring 的设计原则——代理生成必须留在初始化后这一标准时机；而且不循环依赖的对象也被强制提前代理，白白改变所有 Bean 的行为。三级缓存的工厂实现了"只有真发生循环依赖才提前代理"的按需语义。
踩坑：只背"三个 Map 存什么"讲不出"为什么存工厂"是高频丢分点。核心关键词：延迟、按需生成代理。
// AbstractAutoProxyCreator#getEarlyBeanReference（简化）——工厂里真正干活的逻辑
public Object getEarlyBeanReference(Object bean, String beanName) {
    Object cacheKey = getCacheKey(bean.getClass(), beanName);
    this.earlyProxyReferences.put(cacheKey, bean);    // 记下"已提前代理"，防止初始化后再代理一次
    return wrapIfNecessary(bean, beanName, cacheKey); // 有切面匹配→此刻生成代理；没有→返回原始对象
}
// 这就是"存工厂不存对象"的意义：不发生循环依赖，这方法永远不会被调，
// 代理生成时机照旧在初始化后——只有真循环了才提前代理
记忆点：二级够用没 AOP三级为代理而生工厂=按需延迟
高频构造器注入的循环依赖为什么解决不了？

根本原因：三级缓存的解法依赖"先实例化（毛坯）→ 再注入属性"这两步分离。构造器注入时，创建 A 就必须先有 B，还没实例化完 A 就要去拿 B，毛坯根本不存在，没有任何东西可以提前暴露。

getBean(A) → 构造 A 需要 B → getBean(B) → 构造 B 需要 A → getBean(A)（一级二三级都没有）
→ BeanCurrentlyInCreationException

Spring 的防护：用 singletonsCurrentlyInCreation 集合记录"正在创建中"的 Bean 名，重复进入直接抛异常（防死循环）。

解决手段：① 改成 Setter/字段注入（不推荐回头路）；② @Lazy 注入——注入一个代理，真正调用方法时才初始化目标 Bean，把"创建时依赖"推迟到"使用时依赖"。

@Service
public class AService {
    private final BService bService;
    // 注入的是 B 的代理，真正调 bService 方法时才触发 B 的创建
    // ——把"创建时依赖"推迟成"使用时依赖"，循环被绕开
    public AService(@Lazy BService bService) {
        this.bService = bService;
    }
}
记忆点：构造器循环=没毛坯可暴露@Lazy=用时才建
高频BeanFactory 和 FactoryBean 的区别？

名字像、完全两码事，经典陷阱题：

BeanFactoryFactoryBean
是什么Spring IoC 容器的顶层接口，是"工厂本身"一个特殊的 Bean——这个 Bean 能生产别的对象
角色容器的根接口（ApplicationContext 的父接口）复杂对象的构建器，用户实现
getBean 语义getBean("x") 返回 x 对应的 BeangetBean("x") 返回 FactoryBean 生产出的对象；getBean("&x") 才返回 FactoryBean 自身

典型应用：MyBatis 的 SqlSessionFactoryBean、Feign 的 FeignClientFactoryBean——复杂对象不适合用 XML/注解直接声明，就写个 FactoryBean 在 getObject() 里手工构建。Spring Boot 自动装配大量依赖它。

追问：getObject() 返回的对象会被 Spring 管理生命周期吗？会，FactoryBean 生产出的对象照样受容器管理（单例池等），这正是它比静态工厂方法灵活的地方。
// MyBatis-Spring 里的经典实现（简化）
public class SqlSessionFactoryBean implements FactoryBean<SqlSessionFactory> {
    @Override
    public SqlSessionFactory getObject() {   // getBean("sqlSessionFactory") 返回的是它
        return buildSqlSessionFactory();     // 复杂构建逻辑手工写在 getObject 里
    }
    @Override
    public Class<?> getObjectType() { return SqlSessionFactory.class; }
}
// context.getBean("&sqlSessionFactory") —— 加 & 才拿到 FactoryBean 本身
记忆点：BeanFactory 是厂FactoryBean 是厂里的机器人&拿机器人本身
高频Spring Bean 有哪些作用域？单例 Bean 线程安全吗？

五种作用域（前两个必背）：

作用域含义注意
singleton容器内唯一实例（默认）全容器共享
prototype每次 getBean 新建容器只创建不销毁（销毁回调不生效）
request每个 HTTP 请求一个Web 环境
session每个会话一个Web 环境
application每个 ServletContext 一个Web 环境

单例 Bean 线程安全吗？不保证。单例 = 多线程共享同一个实例；如果 Bean 有可变的成员变量（如 private int count），并发修改就出问题。Spring 不管这事，责任在使用者。

  • 为什么实际很少出事：绝大多数 Bean（Service/Controller）是无状态的——成员只有注入的其他单例 Bean，没有可变字段，天然线程安全。
  • 不安全的典型反例：SimpleDateFormat 当成员变量（这就是 Java 手册里那个事故案例）、计数器、可变缓存对象。
  • 解法：设计成无状态；必须共享可变状态则用 ThreadLocal / Concurrent 容器 / 加锁；或改 prototype 作用域。
@Service  // 默认单例：全容器共享这一个实例
public class CounterService {
    private int count = 0;            // ❌ 可变成员变量，多线程共享
    public void inc() { count++; }    // count++ 非原子，并发必丢更新
}

// ✅ 解法：绝大多数 Service 本就该无状态（成员只有注入的其他单例 Bean）
// 确需计数 → 原子类
private final LongAdder count = new LongAdder();
public void inc() { count.increment(); }
记忆点：安全与否看状态不看单例无状态=安全SimpleDateFormat=反例
必考@Autowired 和 @Resource 的区别？
@Autowired@Resource
来源Spring 自带JDK 规范（JSR-250）
默认匹配byType（按类型）byName（按名称）
多实现冲突配合 @Qualifier 指定名字；或 @Primary 标首选name 属性直接指定
requiredrequired=false 允许注入失败无此属性（必须找到）

关键理解：byType 找到多个候选时的裁决顺序——先 @Primary，再 @Qualifier/name 指定，再按字段名/参数名与 Bean 名匹配，还不行就抛 NoUniqueBeanDefinitionException。

踩坑：@Resource 匹配规则是"先按 name 找，找不到退回 byType"，不是纯 byName。答"按名字注入"没错但不完整，说出回退机制更显理解。
@Service
public class PayService {
    @Autowired                          // 先 byType；多个实现 → 再按字段名匹配
    @Qualifier("alipayService")         // 仍冲突 → @Qualifier 指名裁决
    private PayChannel alipay;

    @Resource(name = "wxPayService")    // 先按 name 找，找不到退回 byType
    private PayChannel wxPay;
}
记忆点：A 按 typeR 按 name多实现靠 Qualifier/Primary 裁决
必考AOP 是什么？底层怎么实现的？

AOP（面向切面编程）：把横切关注点（日志、事务、权限、限流）从业务代码中抽离，用切面统一织入，业务类保持纯净。核心价值：业务解耦 + 复用。

底层实现 = 动态代理。Spring AOP 在运行时为目标 Bean 生成代理对象，代理里包着"业务方法 + 切面逻辑"。两种代理：

JDK 动态代理CGLIB
实现方式Proxy + InvocationHandler，基于接口反射生成继承目标类，字节码生成子类，覆写方法
前提目标必须实现接口不能代理 final 类 / final 方法（覆写不了）
Spring 规则有接口时（Spring 5 默认）无接口时；Spring Boot 2.x 起默认全用 CGLIB（proxy-target-class=true）

代理生效时机：容器启动、Bean 初始化后（postProcessAfterInitialization）由 AnnotationAwareAspectJAutoProxyCreator 判断"是否匹配切点"，匹配就生成代理放进单例池——容器里放的是代理，你注入的也是代理。

执行链：调用代理方法 → 走拦截器链（MethodInterceptor）：前置 @Before → 目标方法 → 后置 @After → 返回 @AfterReturning / 异常 @AfterThrowing，@Around 环绕在最外层可控制全流程。

追问：@Around 和 @Before+@After 什么关系？@Around 最强大——手动调 proceed() 决定目标方法是否执行，可改参数、改返回值、吞异常；@Before/@After 只是通知钩子，不能阻止执行。优先级：@Around 包在最外。
踩坑：别答"AOP 用反射实现"就完了——反射只是 JDK 代理的实现细节，本质是动态代理 + 拦截器链。另外 Spring Boot 2.x 默认 CGLIB 这个变化常被追问（因为 JDK 8+ 接口 default 方法变多、且 CGLIB 不再强依赖接口）。
@Aspect
@Component
public class LogAspect {

    @Pointcut("execution(* com.demo.service..*(..))")
    public void svc() {}

    @Around("svc()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();       // proceed() 放行：走拦截器链直到目标方法
        } finally {
            log.info("{} 耗时 {}ms", pjp.getSignature(),
                     System.currentTimeMillis() - start);
        }
    }
}
// @Before/@After 只是钩子；@Around 能改参数、改返回值、甚至不调 proceed() 阻止执行
记忆点：AOP=动态代理织入有接口 JDK 无接口 CGLIBBoot2 全 CGLIB代理生于初始化后
必考AOP 在什么情况下失效？（自调用问题）

根因只有一个：绕过了代理对象。AOP 靠代理拦截方法调用，凡是"调用没有经过代理"的场景，切面都失效：

  1. 自调用（最典型）：同一个类里 this.methodB()——this 是原始对象不是代理，B 上的切面/事务全失效。
  2. 方法不是 public：CGLIB 继承覆写不了？非 public 方法 Spring AOP 直接不拦截（事务对非 public 方法无效）。
  3. final / static 方法：CGLIB 覆写不了 final；static 方法属于类不属于实例，代理无能为力。
  4. new 出来的对象：绕开容器，根本没有代理。
  5. 内部类调用外部类方法：同样是 this 引用问题。

自调用的三种解法：

  1. 注入自己：@Autowired private XxxService self;（用代理调）——注意配合 @Lazy 防止循环依赖问题。
  2. AopContext.currentProxy()：需要 @EnableAspectJAutoProxy(exposeProxy = true)。
  3. 拆类：把要被增强的方法挪到另一个 Bean（最干净，架构上消除了自调用）。
@Service
public class OrderService {

    public void create() {
        this.saveLog();          // ❌ this 是原始对象不是代理 → saveLog 的切面/事务全失效
    }

    @Transactional
    public void saveLog() { ... }

    // ✅ 解法1：注入自己（拿到的是代理），配合 @Lazy 防循环依赖
    @Autowired @Lazy
    private OrderService self;
    public void create2() { self.saveLog(); }   // 走代理，生效

    // ✅ 解法2（最干净）：把 saveLog 挪到 LogService，拆类消除自调用
}
记忆点：失效=绕过代理this 不是代理final/static/new 全失效
必考Spring 事务在哪些场景下失效？（高频中的高频）

和 AOP 失效同根——@Transactional 靠 AOP 代理实现，所有"绕过代理"的场景都失效，再加上事务自身的几个坑：

  1. 自调用：同类 this 调用带 @Transactional 的方法（最高频，根源同 AOP 自调用）。
  2. 方法非 public：Spring 事务切面只增强 public 方法（protected/private 直接失效，Boot 下不报错、静默失效最可怕）。
  3. 异常被吞：try-catch 把异常吃掉不抛，切面感知不到 → 不回滚。
  4. 异常类型不匹配：默认只回滚 RuntimeException 和 Error，抛受检异常（如 Exception）不回滚——需 rollbackFor = Exception.class。
  5. 类没被 Spring 管理：new 出来的对象，注解是摆设。
  6. 数据库引擎不支持事务：MyISAM 表直接没有事务。
  7. 传播行为设错：内层 NOT_SUPPORTED 挂起外层事务、或 REQUIRES_NEW 各自独立，外层回滚内层不跟着回——不是失效，是"没按你以为的方式回滚"。
  8. 多线程：事务上下文（ThreadLocal 绑定的 Connection）不跨线程，子线程的 DB 操作不在事务里。

速记口诀（首字串联）："私吞自异非" + 引擎 + 线程 → 私有方法、吞异常、自调用、受检异常默认不回滚、非 Spring 管理的对象，加上 MyISAM 引擎和多线程。

追问：为什么默认不回滚受检异常？设计哲学：受检异常（如 IOException）被视为"业务可预期、调用方应处理"的情况，不等于数据一致性被破坏。所以显式 rollbackFor 是生产代码标配。
踩坑：只答"自调用失效"太薄。至少说出 5 条 + 给出口诀，并强调"静默失效不报错"——这比失效本身更危险。
@Service
public class StockService {

    // ❌ 自调用：deduct 里 this.deductDb()，事务失效
    public void deduct() { deductDb(); }
    @Transactional
    public void deductDb() { ... }

    // ❌ 吞异常：catch 后不抛，切面感知不到 → 不回滚
    @Transactional
    public void pay() {
        try { doPay(); } catch (Exception e) { log.error("pay fail", e); }
    }

    // ❌ 受检异常默认不回滚
    @Transactional
    public void refund() throws Exception { doRefund(); }

    // ✅ 正确姿势：public 方法 + rollbackFor + 异常继续抛
    @Transactional(rollbackFor = Exception.class)
    public void payV2() throws Exception { doPay(); }
}
记忆点：私吞自异非默认只回滚 RuntimeException事务不跨线程
高频讲一下事务的传播行为（Propagation）

传播行为定义：一个事务方法被另一个事务方法调用时，内层方法怎么对待外层的事务。七种，重点记前三种：

传播行为外层有事务时外层无事务时一句话
REQUIRED（默认）加入外层事务新建事务有就蹭，没有就开
REQUIRES_NEW挂起外层，自己开新事务新建事务各玩各的，互不影响
NESTED在外层事务里开保存点（Savepoint）同 REQUIRED内层可独立回滚到保存点，外层整体回滚则全回
SUPPORTS加入非事务执行可有可无
NOT_SUPPORTED挂起外层，非事务执行非事务执行坚决不要事务
MANDATORY加入抛异常必须被事务调用
NEVER抛异常非事务执行有事务就翻脸

REQUIRES_NEW vs NESTED 的区别（最常追问）：REQUIRES_NEW 是两个独立事务——内层提交后外层回滚，内层不回滚；NESTED 是一个事务的子事务——外层回滚，内层跟着回滚。NESTED 依赖数据库 Savepoint，且两者占用的数据库连接数不同（REQUIRES_NEW 要两条连接）。

踩坑：REQUIRES_NEW 高并发下是连接池杀手——外层事务占一条连接不放，内层又要新连接；并发一上来，连接池被"外层挂起 + 内层新开"双倍占满，直接拖垮。这是中厂最爱考的实战坑。
@Service
public class OrderService {
    @Transactional
    public void createOrder() {
        orderMapper.insert(order);
        logService.record();      // 内层传播行为在这里起作用
    }
}

@Service
public class LogService {

    // REQUIRES_NEW：挂起外层、另开新事务——日志成败与订单事务互不影响
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record() { ... }

    // NESTED：外层事务内设保存点——内层回滚只回滚到保存点，外层可继续
    @Transactional(propagation = Propagation.NESTED)
    public void recordNested() { ... }
}
// 区别：REQUIRES_NEW 两条独立连接（连接池杀手）；NESTED 一条连接靠 Savepoint
记忆点：REQUIRED 蹭REQUIRES_NEW 分家NESTED 存档点REQUIRES_NEW 杀连接池
高频事务里开异步线程 / 发 MQ，事务还没提交就执行了怎么办？

问题本质：@Transactional 方法里 executor.submit(...) 或发 MQ 消息——事务上下文用 ThreadLocal 绑定 Connection，不跨线程；MQ 更是立即发出。结果是：事务还没 commit，异步任务/消费者已经在读"旧数据"。

解法（按推荐度）：

  1. TransactionSynchronizationManager.registerSynchronization：注册 afterCommit 回调，事务真提交后再发 MQ / 触发异步。最正统。
  2. 事务提交后移出方法体：外层非事务方法先调事务方法，返回后再发 MQ（方法边界控制，简单但容易被人改坏）。
  3. 事务消息 / 本地消息表（MQ 手册方案）：不追求"提交后立刻发"，追求"最终一定发"——事务和发消息的原子性由消息表保证。
踩坑：面试答"把发 MQ 放到事务方法最后一行"是错误答案——最后一行代码执行完不等于事务已提交（commit 发生在代理层、方法返回之后）。必须用 afterCommit 回调或消息表方案。
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);

    // ❌ mqSender.send(msg);   最后一行≠已提交：commit 发生在代理层、方法返回之后

    // ✅ 注册事务同步：提交成功后才回调
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                mqSender.send(buildMsg(order));   // 此刻数据对外可见
            }
        });
}
记忆点：ThreadLocal 不跨线程最后一行≠已提交afterCommit 回调

模块② Spring Boot（自动装配 · 启动 · 配置）0%

核心就一句话：Spring Boot = Spring + 自动装配 + 内嵌容器。所有题都从这句话往外延伸。
必考Spring Boot 解决了什么问题？核心特性是什么？

解决的问题：Spring 时代配置地狱——XML/JavaConfig 写到吐、依赖版本自己协调、部署还要外挂 Tomcat。Spring Boot 用三个特性终结：

  • 自动装配：约定大于配置，常见组件开箱即用（引依赖即生效）。
  • starter 起步依赖：一个 starter 打包一组兼容依赖，版本冲突由 Spring Boot 统一仲裁（parent 里管版本）。
  • 内嵌容器：内嵌 Tomcat/Jetty/Undertow，java -jar 直接跑，天然适配容器化。

本质：Spring Boot 没有发明新 IoC，它是 Spring 的脚手架和最佳实践打包。

记忆点：自动装配·starter·内嵌容器约定大于配置
必考自动装配的原理是什么？（最高频）

完整链路（顺着这条链讲，一步步推）：

口述版本（背这段）：@EnableAutoConfiguration 通过 @Import 引入 AutoConfigurationImportSelector，它读取 classpath 下的自动配置清单（旧版 spring.factories，2.7+ 换成 AutoConfiguration.imports 文件），拿到上百个候选配置类，再用 @Conditional 系列条件注解逐个筛选——类路径有 Redis 依赖、你没自己配 RedisTemplate，那默认的 RedisAutoConfiguration 才生效。最终符合条件的配置类把 Bean 注册进容器。

追问：为什么我自定义了一个 RedisTemplate，默认的就"消失"了？自动配置类的方法上几乎都标了 @ConditionalOnMissingBean——容器里已有用户定义的同类型 Bean，默认配置就让位。这就是"用户配置优先"的实现。
踩坑：只答「spring.factories 加载」不给筛选环节是半分答案。三个关键点缺一不可：清单文件、条件注解筛选、用户配置优先（@ConditionalOnMissingBean）。
# 文件：META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
# （Boot 2.7 前：META-INF/spring.factories 里 EnableAutoConfiguration=全类名）
com.demo.starter.DemoAutoConfiguration
@AutoConfiguration
@ConditionalOnClass(DemoService.class)              // 类路径有 DemoService 才生效
@EnableConfigurationProperties(DemoProperties.class)
public class DemoAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                       // 用户自己定义了就让位（"用户优先"）
    public DemoService demoService(DemoProperties props) {
        return new DemoService(props.getPrefix());
    }
}
记忆点：Import 选择器读清单条件注解做筛选OnMissingBean 让位用户2.7 后清单换文件
必考@SpringBootApplication 由哪三个注解组成？
  1. @SpringBootConfiguration：本质是 @Configuration，声明这是配置类。
  2. @ComponentScan：扫描主类所在包及子包的组件——所以主类必须放根包，放深了别的包扫不到。
  3. @EnableAutoConfiguration：自动装配总开关（上一题的链路）。
追问：主类为什么放根包？@ComponentScan 默认只扫「主类所在包及子包」。放根包保证所有组件覆盖；想破例就显式 scanBasePackages。
记忆点：配置·扫描·自动装配主类放根包
高频常见的条件注解有哪些？
注解生效条件典型用途
@ConditionalOnClass类路径存在指定类引了 redis 依赖才配 Redis
@ConditionalOnMissingBean容器没有该 Bean用户配置优先（核心）
@ConditionalOnBean容器已有该 Bean依赖某个前置 Bean
@ConditionalOnProperty配置属性满足条件功能开关 enable.xxx=true
@ConditionalOnWebApplication是 Web 应用Web 相关默认配置

全部基于 @Conditional(XxxCondition.class) 扩展——自定义 starter 时也可以写自己的 Condition。

@Bean
@ConditionalOnProperty(name = "demo.audit", havingValue = "true", matchIfMissing = false)
public AuditRunner auditRunner() { return new AuditRunner(); }
// application.yml 配 demo.audit: true 才注册；不配/配 false 都没有这个 Bean
记忆点：OnClass 看依赖OnMissingBean 让位OnProperty 开关
必考starter 是什么？怎么自定义一个 starter？

starter = 依赖聚合 + 自动配置。把"某功能的全部依赖 + 默认配置类"打包，使用方引一个坐标即得全套能力。命名约定：官方 spring-boot-starter-xxx，三方 xxx-spring-boot-starter。

自定义步骤（五步）：

  1. 建 autoconfigure 模块，写核心 Bean（XxxService）+ 配置属性类（@ConfigurationProperties）。
  2. 写自动配置类 XxxAutoConfiguration，方法标 @Bean @ConditionalOnMissingBean，类上标 @ConditionalOnClass 等。
  3. 注册清单：2.7+ 在 META-INF/spring/...AutoConfiguration.imports 写入配置类全名（旧版写 spring.factories）。
  4. 打两个 jar：xxx-spring-boot-starter（空壳只聚合依赖）+ xxx-spring-boot-autoconfigure（配置逻辑）。
  5. 使用方引 starter → 依赖进来 → 条件满足 → Bean 自动注册。
// ① 配置属性类：application.yml 里 demo.prefix 可覆盖默认值
@ConfigurationProperties("demo")
public class DemoProperties {
    private String prefix = "default";
    // getter / setter
}

// ② 自动配置类：条件装配 + 用户可覆盖
@AutoConfiguration
@ConditionalOnClass(DemoService.class)
@EnableConfigurationProperties(DemoProperties.class)
public class DemoAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public DemoService demoService(DemoProperties p) {
        return new DemoService(p.getPrefix());
    }
}

// ③ 注册清单：META-INF/spring/...AutoConfiguration.imports 写入本类全名
// ④ 打两个 jar：demo-spring-boot-starter（空壳聚合依赖）+ demo-spring-boot-autoconfigure（上面逻辑）
记忆点：依赖聚合+自动配置五步：Bean·属性·条件·清单·双jar
高频Spring Boot 的启动流程（run 方法里发生了什么）？

按顺序答七个阶段：

  1. new SpringApplication：推断应用类型（Servlet/Reactive）、加载 ApplicationContextInitializer 和 ApplicationListener、推断主类。
  2. prepareEnvironment：加载 application.yml/环境变量/命令行参数，封装成 Environment。
  3. createApplicationContext：按应用类型创建容器（Servlet 场景是 AnnotationConfigServletWebServerApplicationContext）。
  4. prepareContext：把主类注册为配置类（加载 BeanDefinition），执行 Initializer。
  5. refreshContext：调 Spring 的 refresh()——这是 IoC 容器启动的核心：onRefresh() 里创建内嵌 Web 服务器（Tomcat）并启动，finishBeanFactoryInitialization 里实例化全部单例 Bean。
  6. afterRefresh / 回调 runners：执行 CommandLineRunner / ApplicationRunner。
  7. 发布started/ready事件，启动完成。

最值得主动提的点：内嵌 Tomcat 是在 refresh() 的 onRefresh 阶段创建的（ServletWebServerFactoryAutoConfiguration 提供 TomcatServletWebServerFactory）——这句话能同时串起「启动流程」和「内嵌容器」两道题。

记忆点：建环境→建容器→refresh（内嵌Tomcat在此起）→跑 Runner
高频配置文件的加载优先级？

优先级从高到低（高的覆盖低的）：

  1. 命令行参数（--server.port=8081，最高）
  2. JVM 系统属性（-D 参数）
  3. 操作系统环境变量
  4. profile 专属配置（application-prod.yml）
  5. application.yml / properties
  6. @PropertySource 指定的文件

同是 application.yml 时：config/ 目录 > classpath 根目录（外置覆盖内置，方便不改包只改配置）。

踩坑：环境变量在 yml 之上——K8s 里用环境变量覆盖镜像内配置是常规操作，但很多人误以为 yml 优先，排查半天"为什么配置不生效"。
记忆点：命令行>系统>环境变量>profile>yml外置覆盖内置
高频多环境配置（profile）怎么用？
  • 文件拆分：application-dev.yml / application-test.yml / application-prod.yml，主文件 spring.profiles.active=dev 指定激活哪个。
  • 启动时切换：命令行 --spring.profiles.active=prod 优先级高于文件内声明。
  • 分组（2.4+）：spring.profiles.group.prod=db-prod,mq-prod——激活 prod 时同时激活一组。
  • Bean 级：@Profile("prod") 注解控制某个 Bean 只在某环境注册。
追问：激活多个 profile 冲突怎么办？后面声明的覆盖前面（active=dev,prod 时 prod 优先）；且 profile 专属文件整体优先于 application.yml。

  profiles:
    active: dev          # 本地默认 dev；生产用命令行 --spring.profiles.active=prod 覆盖
---
# application-prod.yml（或同文件 --- 分隔）
spring:
  config:
    activate:
      on-profile: prod
server:
  port: 8080

模块③ MyBatis（执行链路 · 代理 · 缓存）0%

MyBatis 的三根主线：执行链路（四大对象）、Mapper 动态代理、两级缓存。
必考讲一下 MyBatis 的一次完整执行链路

从 SqlSession 到数据库，核心是四大对象的接力：

口述版：Mapper 代理把方法调用路由到 SqlSession → SqlSession 委托给 Executor（先查一级缓存，没有才执行）→ Executor 创建 StatementHandler → 由 ParameterHandler 设参、执行 JDBC、ResultSetHandler 映射结果。整个过程每个环节都能被插件拦截。

记忆点：代理→Session→Executor→StatementHandler→参数/结果两助手
必考Mapper 只是接口，没有实现类，为什么能调通？

JDK 动态代理 + MapperProxy。启动时 MyBatis 用 MapperScan 扫描接口，为每个接口注册 MapperProxyFactory；getMapper 时生成 JDK 代理对象，方法调用统一进入 MapperProxy#invoke：

  1. 根据「接口全限定名 + 方法名」定位到 MappedStatement（XML 里 id = namespace.method 的那条 SQL）。
  2. 把方法参数包装成参数 Map。
  3. 转发给 SqlSession 对应的增删改查方法。

所以"没有实现类"的原因：实现被动态代理在运行时统一接管了——所有接口共用一个 MapperProxy 逻辑，SQL 真身在 XML/注解里，不需要手写实现。

追问：方法重载会怎样？定位靠「namespace + 方法名」，不看你参数——重载会定位歧义，所以 Mapper 接口禁止方法重载。
// MapperProxy#invoke（简化）——所有 Mapper 方法调用都进这里
public Object invoke(Object proxy, Method method, Object[] args) {
    // "com.demo.mapper.UserMapper.selectById" = namespace + 方法名 → 定位 MappedStatement
    MapperMethod mapperMethod = cachedMapperMethod(method);
    return mapperMethod.execute(sqlSession, args);   // 转发给 SqlSession 的对应增删改查
}
记忆点：JDK 代理 MapperProxy全限定名+方法名=定位 SQL禁止重载
必考#{} 和 ${} 的区别？
#{}${}
实现预编译占位符 ?，PreparedStatement 设参字符串直接拼接进 SQL
安全防 SQL 注入有注入风险
性能同 SQL 可复用执行计划每次拼接 SQL 不同，无法复用
适用所有传值场景（默认用它）表名/列名/ORDER BY 字段等不能参数化的结构

${} 唯一的合理使用：动态表名、动态排序列这类"结构"场景——但值必须来自白名单校验，绝不能直接接用户输入。

踩坑：说"永远用 #{}"不严谨——ORDER BY 动态列用 #{} 会变成字符串常量 'col_name' 排序失效。正确表述：值用 #{}，结构用 ${} + 白名单。
<!-- #{}：预编译占位符 ?，值安全、执行计划可复用 —— 传值一律用它 -->
<select id="getById" resultType="User">
    SELECT * FROM user WHERE id = #{id}
</select>

<!-- ${}：字符串直接拼接，有注入风险 —— 只用于表名/列名等结构，且必须白名单校验 -->
<select id="listByOrder" resultType="User">
    SELECT * FROM user ORDER BY ${orderColumn} ${orderDir}
    <!-- orderColumn 绝不能直接接用户输入 -->
</select>
记忆点：# 预编译防注入$ 拼接有风险表名列名才用 $ 且白名单
必考一级缓存和二级缓存的区别？生产怎么用？
一级缓存二级缓存
范围SqlSession 内（默认开启）namespace 级（Mapper 级）
结构PerpetualCache（HashMap）默认 PerpetualCache，可接 Redis/Ehcache
失效时机session 内增删改、clearCache、session 关闭namespace 内任何增删改触发整体清空
整合点Executor（BaseExecutor）里CachingExecutor 装饰器包在 Executor 外层
生产态度与 Spring 整合后每请求一个 session，作用≈请求内小缓存基本关闭（生产慎用）

二级缓存为什么生产慎用（三个硬伤）：

  1. 跨实例脏读：多实例部署时各节点缓存独立，A 节点改库清自己的缓存，B 节点还拿着旧值——分布式下必然脏读。
  2. namespace 粒度太粗：一条 SQL 更新就清空整个 namespace，命中率低；多表关联查询缓存在 A namespace，B namespace 更新表时 A 的缓存感知不到，直接脏读。
  3. 序列化开销：二级缓存存的是序列化副本，对象大时得不偿失。

正确姿势：缓存需求交给 Redis 等专业缓存，自己控制 key/过期/一致性（见缓存一致性专题），MyBatis 二级缓存保持关闭。

<settings>
    <!-- 一级缓存默认开启（SESSION 级） -->
    <setting name="localCacheScope" value="SESSION"/>
    <!-- 二级缓存生产保持关闭：多实例脏读 + namespace 粒度太粗 -->
    <setting name="cacheEnabled" value="false"/>
</settings>
记忆点：一级 session 默认开二级 namespace 生产关多实例必脏读
高频resultMap 和 resultType 的区别？什么时候必须用 resultMap？
  • resultType：按列名 = 属性名自动映射，简单查询够用（列名转驼峰可开 mapUnderscoreToCamelCase）。
  • resultMap：手动指定列↔属性映射，四种场景必须用：① 列名和属性名对不上且没开驼峰；② association 一对一；③ collection 一对多；④ 需要列别名复用同一映射。
追问：一对一用联表还是 N+1 单查？联表一次查完（分页友好但 SQL 复杂）；N+1 是每行再发一条 SQL——数据量大时性能灾难，MyBatis 的 association select 写法天然是 N+1，需配合延迟加载缓解。分页场景必须联表。
<resultMap id="OrderMap" type="Order">
    <id column="order_id" property="id"/>
    <result column="user_name" property="userName"/>
    <!-- 一对一：联表查下单用户 -->
    <association property="user" javaType="User">
        <id column="u_id" property="id"/>
        <result column="u_name" property="name"/>
    </association>
    <!-- 一对多：订单明细列表 -->
    <collection property="items" ofType="OrderItem">
        <result column="item_name" property="name"/>
        <result column="price" property="price"/>
    </collection>
</resultMap>
记忆点：同名自动映射关联映射必须 resultMapN+1 是性能坑
高频MyBatis 的延迟加载原理是什么？

原理：查主对象时，关联属性先用代理对象占位（cglib 或 javassist 生成子类代理）；等真正调用关联属性的 getter 时，代理拦截，此时才发 SQL 查关联数据。

  • 配置：lazyLoadingEnabled=true，aggressiveLazyLoading=false（3.4.1+ 默认按需）。
  • 作用：只查主表场景省掉关联查询的 SQL 开销。
踩坑：延迟加载对象脱离 SqlSession 后再访问会报错（LazyInitializationException）——session 关了代理没法发 SQL。配合 Spring 整合时要注意返回给前端的 DTO 如果带懒代理，序列化（Jackson）可能踩空字段。
mybatis:
  configuration:
    lazy-loading-enabled: true        # 关联属性先用代理占位
    aggressive-lazy-loading: false    # 按需触发：调 getter 才发 SQL 查关联
记忆点：代理占位·用时才查session 关了就炸
高频MyBatis 插件机制是什么？能拦截什么？

Interceptor 接口 + 责任链 + 动态代理：插件实现 Interceptor，用 @Intercepts 声明拦截哪个对象的哪个方法，MyBatis 在创建四大对象时用代理层层包裹（TargetProxy 链），调用时按注册顺序依次穿过插件。

  • 可拦截四大对象：Executor、StatementHandler、ParameterHandler、ResultSetHandler。
  • 经典应用：PageHelper（拦截 Executor 改写分页 SQL + count）、慢 SQL 监控、SQL 打印、数据权限改写、字段加解密。
追问：PageHelper 的原理？拦截 Executor 的 query，先执行一条 count SQL，再在原 SQL 后面拼 LIMIT 执行分页查询——靠 ThreadLocal 传递分页参数，所以 PageHelper.startPage 必须紧贴查询、用完要清理，否则 ThreadLocal 残留会让下一条无辜 SQL 被分页。
@Intercepts({
    @Signature(type = Executor.class, method = "query",
               args = {MappedStatement.class, Object.class,
                       RowBounds.class, ResultHandler.class})
})
@Component
public class SlowSqlPlugin implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();     // 放行：下一个插件 → 目标对象
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (cost > 1000) log.warn("慢SQL: {} ms", cost);
        }
    }
}
记忆点：四大对象可拦代理责任链PageHelper=改写 SQL+ThreadLocal
必考逻辑分页和物理分页的区别？为什么用 PageHelper 而不用 RowBounds？
逻辑分页（RowBounds）物理分页（LIMIT / PageHelper）
实现查全部结果到内存，再游标截取SQL 里拼 LIMIT，数据库只返回该页
内存大表直接 OOM只占一页
网络全量传输只传一页

结论：数据量小的场景 RowBounds 才可用；生产一律物理分页。PageHelper 本质是把物理分页做成了插件（自动拼 LIMIT + 自动 count），兼得便利与性能。深分页问题（LIMIT 1000000,10）另议——用游标/延迟关联优化，那是 SQL 优化专题的事。

// startPage 必须紧贴下一条查询（靠 ThreadLocal 传分页参数），中间不能插别的 SQL
PageHelper.startPage(pageNum, pageSize);
List<Order> list = orderMapper.selectList(query);   // 被插件改写成 LIMIT 物理分页
PageInfo<Order> page = new PageInfo<>(list);        // 总数、页数都在这里
// 若 startPage 后没执行查询，ThreadLocal 残留会污染下一条无辜 SQL
记忆点：RowBounds 全捞内存生产物理分页
高频MyBatis 和 JPA/Hibernate 怎么选？
MyBatisJPA/Hibernate
SQL 控制SQL 全手写，精细可控自动生成，复杂查询要 HQL/原生 SQL 绕
开发效率简单 CRUD 也要写 XML（MP 缓解）CRUD 飞快、跨库迁移容易
学习成本低（本质是 SQL 映射）高（一级缓存、脏检查、N+1 陷阱多）
国内主流互联网/业务系统事实标准外企、规范型项目多

面试答法：MyBatis 适合SQL 优化空间大、查询复杂、表结构灵活的互联网业务；JPA 适合领域模型稳定、CRUD 为主的项目。团队技术栈和复杂查询占比决定选型，没有绝对优劣。

记忆点：MyBatis 管 SQLJPA 管模型复杂查询选 MyBatis
高频MyBatis 的动态 SQL 有哪些标签？<where><if> 组合有什么坑？
  • 核心标签：<if>、<where>（自动去开头 AND/OR）、<set>（自动去尾逗号，update 用）、<choose>/<when>/<otherwise>（switch 语义）、<foreach>（in 条件/批量插入）、<trim>（万能前后缀裁剪）、<bind>。
  • <foreach> 的坑：in 列表过大（上千元素）SQL 超长、执行计划劣化——分批（每批 500~1000）；批量插入同理。
  • <if test> 的坑：test 里对 Integer 判断 != ''，值为 0 时被 OGNL 当空串误判为 false——数值类型判断别拼空串比较。
  • <where> 救不了的：条件全为空时 where 整个消失 → 全表扫，业务上要兜底（比如强制一个恒真条件或前置校验）。
<select id="query" resultType="Order">
    SELECT * FROM t_order
    <where>
        <!-- 数值类型别拼 != ''：type=0 时 OGNL 把 0 当空串判 false -->
        <if test="status != null">AND status = #{status}</if>
        <if test="userId != null">AND user_id = #{userId}</if>
    </where>
    <if test="ids != null and ids.size() > 0">
        AND id IN
        <!-- in 列表过大要分批（每批 500~1000）：SQL 超长且执行计划劣化 -->
        <foreach collection="ids" item="id" open="(" separator="," close=")">
            #{id}
        </foreach>
    </if>
</select>

<!-- <set>：update 自动去尾逗号 -->
<update id="update">
    UPDATE t_order
    <set>
        <if test="status != null">status = #{status},</if>
        <if test="amount != null">amount = #{amount},</if>
    </set>
    WHERE id = #{id}
</update>
记忆点：where 去头 set 去尾foreach 分批Integer 0 被当空串
